# Decisions: network capture

Why the network probe is layered the way it is, what it deliberately does not capture, and which alternatives were rejected. Process-level and loss-accounting decisions shared with the other probes are in [probes.md](probes.md).

**Numbering.** The five decisions resolved on 2026-09-14 were numbered D1 to D5 in the Tier 3 design. They are renamed N-D1 to N-D5 here so they do not clash with the integration decisions D1 to D14 in [integration.md](integration.md). Other network decisions are numbered from N-6.

Entries carry their own dates. Statuses reconciled with the code at commit d223e7d on 2026-10-28. Original sources: docs/archive/06_tier3_network_design.md, docs/archive/network_implementation_choices.md, docs/archive/04_design_tradeoffs.md, docs/archive/03_tiers_3_to_6.md (all local only). As-built description: [../architecture/13_probe_net.md](../architecture/13_probe_net.md).

Evidence labels: **Verified** (measured on the development machine), **Reported** (from vendor documentation or third-party source code), **Unverified** (hypothesis).

## Resolved Tier 3 decisions (2026-09-14)

### N-D1: The write bracket is abandoned
Status: Accepted, implemented (`tls.bpf.c` emits `ssl_frame` only; no `active_write`, no `NET_BIND`).
Date: 2026-09-14.
Context: The design joined plaintext to a socket by catching the `write`/`sendmsg` that fires inside the `SSL_write` entry-to-return window. An experiment showed Bun queues encrypted bytes asynchronously, so the socket write does not happen inside that window.
Decision: Drop the bracket. The correlator parses HTTP from the plaintext, takes the target from the `Host:` header and joins with the process's known connections.
Consequences: No `SSL*`-to-fd join; attribution relies on Host headers and per-thread reassembly (per `SSL*` since N-30).
Alternatives rejected: The uretprobe bracket.

### N-D2: HTTP/2 content is out of scope
Status: Accepted.
Date: 2026-09-14.
Context: h2 needs HPACK decoding and frame reassembly.
Decision: A connection negotiating `h2` through ALPN is counted as `ContentUnsupported` and its frames are not parsed.
Consequences: Offset validation needs an HTTP/1.x request line, so an h2-only target cannot be validated. Claude Code offered only `http/1.1` in every fully captured ClientHello in one traced run on 2026-10-02 (strong evidence, not proof; the negotiated protocol was not observed).
Alternatives rejected: An h2 parser before any target needs it.

### N-D3: Plaintext is hashed, never retained
Status: Accepted, implemented in the correlator (`RequestHash`).
Date: 2026-09-14.
Context: Captured requests carry OAuth tokens and JWTs.
Decision: Frame bytes are hashed in memory to compute `RequestHash`. Raw plaintext is not stored in a `GroundTruthEvent` or written to disk.
Consequences: Ground truth files can be shared without leaking credentials. Debugging a content mismatch cannot inspect the bytes.
Alternatives rejected: Retaining plaintext by default. A debug-only retention flag was left as a possible later addition.

### N-D4: Runtime validation is authoritative for TLS offsets
Status: Accepted, implemented in `net.Observer` (`attachAndValidateTLS`) and `pkg/tlsoffset`. Amended 2026-10-17: `New` attaches the uprobe at the first candidate, and validation in `Start` reads the frames it captured since then, so a request a tracked process sends between `New` and `Start` validates the offset instead of being missed; validation stays the only thing that accepts an offset.
Date: 2026-09-14.
Context: A static heuristic on function shape picked the wrong candidate in the offset experiment.
Decision: The scanner (symbols, then cross-references to the `ssl_lib.cc` string) returns ranked candidates only. The observer attaches to each and accepts the first whose first captured frame parses as an HTTP/1.x request line within a timeout. A validated offset is cached by GNU build ID.
Consequences: An offset is never used unvalidated. The method survives toolchain changes better than byte prologues. x86-64 only.
Alternatives rejected: Trusting the static heuristic; byte-prologue matching per build as in AgentSight.

### N-D5: A faulting buffer read warns, it does not mismatch
Status: Accepted, implemented (`FaultedReads` counter, a note in `Assess`).
Date: 2026-09-14.
Context: `bpf_probe_read_user` can fault on a paged-out buffer.
Decision: Drop the frame, count it, and warn. The missing content compares as a probe gap.
Consequences: An agent could in principle exploit faults to hide content; the counter makes it visible (P-11 in [probes.md](probes.md)). Amended 2026-10-14: the same rule covers the ClientHello read in `net.bpf.c`. A faulted hello read marks the connection written (`NET_SEND`, N-23) and is counted in `HelloFaults`, a note in `Assess`: the hostname is missing, no event is.
Alternatives rejected: Reporting a mismatch for unreadable content.

## Architecture and scope

### N-6: Four capture layers, and only two can see plaintext
Status: Accepted (design premise).
Date: 2026-09-12.
Context: TLS encryption happens in userspace inside the agent before any socket syscall.
Decision: Classify capture points as L1 in-process HTTP client (plaintext, requires modifying the agent), L2 the TLS library boundary `SSL_read`/`SSL_write` (plaintext, needs a function address), L3 a terminating proxy at the network edge (plaintext, needs CA trust), L4 socket and packet layer (ciphertext only, needs nothing). L1 is excluded permanently because it violates agent independence (P4). Content can come only from L2 or L3.
Consequences: No socket-level probe will ever read request bodies.
Alternatives rejected: Socket-level plaintext capture, which does not exist.

### N-7: Layered capture: N0 identity everywhere, N1 and N2 content where feasible
Status: N0 and N1 Accepted and implemented (`net.bpf.c`, `tls.bpf.c`); N2 Accepted as design, not built.
Date: 2026-09-12; built 2026-09-14 and 2026-09-15.
Context: Closed agents defeat symbol-based uprobes by three routes: Bun single-file builds (Claude Code, static BoringSSL, Verified), Chromium bundling (Electron IDEs), static Rust (Codex 0.154.0, Verified 2026-10-03). The syscall boundary is the only point stable across the target set.
Decision: N0, built first and unconditionally: tracepoints on `connect` plus the SNI parsed from the first bytes written, giving process, peer and hostname for every target with no cooperation. N1: `SSL_write` uprobe where an offset can be found and validated. N2: a transparent proxy, only for targets whose trajectory claims more than a hostname.
Consequences: N0 satisfies omission and fabrication for network events and substitution at host granularity. Content coverage is partial, per target and request-side, and is reported that way.
Alternatives rejected: A proxy as the primary layer (N-17); a single technique for all targets.

### N-8: The evasion-aware agent is out of scope
Status: Accepted (threat-model assumption).
Date: 2026-09-12.
Context: The threat model is post-hoc misrepresentation of real actions in the trajectory (omission, fabrication, substitution). A different class detects the recorder and changes behaviour or interferes with it, so ground truth itself is wrong.
Decision: Assume the agent misreports its trajectory but does not try to detect or subvert the recorder. State it explicitly wherever results are reported.
Consequences: This makes a proxy a legitimate ground-truth source under the stated model. Evasion resistance is a spectrum: the kernel probes leave no in-process artifact, a proxy announces itself in every certificate chain.
Alternatives rejected: Claiming evasion resistance for all layers.

### N-9: Cooperative configuration is not ground truth
Status: Accepted.
Date: 2026-09-12.
Context: `HTTPS_PROXY`, `SSLKEYLOGFILE` and Chromium's net log look cheap.
Decision: Each requires the target to honour a setting it can ignore, which makes the result agent self-reporting. Never use such evidence for detection-rate claims. It remains valid for false-positive measurement on honest runs if labelled cooperative.
Consequences: A proxy, if built, uses forced routing (iptables REDIRECT or TPROXY), never an environment variable.
Alternatives rejected: Cooperative capture for adversarial evaluation.

### N-10: Routing and trust are separately (non-)cooperative
Status: Accepted.
Date: 2026-09-12.
Context: A transparent proxy forces routing without consent, but trust is injected into a store the agent can inspect.
Decision: Describe a proxy as non-cooperative in routing only. The agent can detect interception from the certificate chain and defeat it by pinning.
Consequences: N2-sourced evidence is recorded as in-path and detectable. A pinned target is occurrence-only.
Alternatives rejected: Calling the proxy fully non-cooperative; defeating pinning by binary patching (breaks agent independence).

### N-11: The response side is not hash-verifiable
Status: Accepted (scope boundary: the response side is attested by status, volume and timing, never hashed). Amended 2026-10-17 by N-29: a response's body is hashed to identify it, and that hash is never compared with a trajectory.
Date: 2026-09-12.
Context: For `WebFetch`-style tools the trajectory holds a model-written summary of the response, not the body (measured on a local transcript corpus, design input only (local only: docs/research/harness_corpus.md)). Comparing a summary with a page is entailment, not equality.
Decision: Verify the request side by hash. Treat response capture, if any, as attestation of status, volume and timing, never as content to hash. Shelled-out `curl` is the exception: the raw body is on stdout.
Consequences: Perfect plaintext from any layer does not close the gap. Summary faithfulness is a separate study, outside this system.
Alternatives rejected: "Hash of request body plus response body", the original plan's wording for network content verification.

### N-12: Shelled-out network commands need no network probe for their target
Status: Accepted.
Date: 2026-09-12.
Context: `curl`, `git push`, `pip install` and `gh` put the full URL in `execve` argv.
Decision: The process probe's argv capture is path-level ground truth for that class. N0 only corroborates the host; N1 and N2 add nothing.
Consequences: The residual case for content capture is narrow: in-binary HTTP where the trajectory records more than a hostname (a `WebFetch` URL).
Alternatives rejected: Content capture for every network action.

### N-13: Port 53 is filtered from emitted events
Status: Superseded by N-20 on 2026-10-11: a connection to port 53 is emitted as `net_dns` capability evidence and counted. Kept as taken; it was questioned as O-15, which N-20 decided.
Date: 2026-09-15 (the privileged integration step of the network probe, commit de08b88).
Context: DNS lookups are triggered implicitly by hostname resolution, and no trajectory records them, so every DNS connection would read as an omission.
Decision: `net.Observer.emit` drops any connection to port 53 before it becomes an event.
Consequences: DNS exfiltration is invisible by design, and the drop has no counter, so nothing in the coverage record says it happened.
Alternatives rejected: None recorded at the time. The later proposal is to record DNS as unclaimable capability evidence (O-20).

### N-14: In-process fetch in simagent, then descendant tracking in the net probe
Status: Accepted, implemented (`simagent --fetch-url`, `--fetch-via-curl`; `task_newtask` in `net.bpf.c` and `tls.bpf.c`).
Date: 2026-09-15 (commits de08b88, 22763f5).
Context: The Tier 3 end-to-end tests first used an in-process `net/http` fetch so the probe, then scoped to one PID, would see it. Real agents and `curl` act from child processes.
Decision: Keep the in-process mode, and track descendants in the net and tls programs the same way the proc probe does, so a forked `curl` is captured with content.
Consequences: Under the forest model a forked `curl` is a level-1 subtree, so its request is attributed, not claimed (D3).
Alternatives rejected: In-process only.

### N-15: Uprobes on rustls are feasible per build, not sustainable
Status: Accepted (not on the critical path).
Date: 2026-10-03.
Context: The earlier record said rustls uprobes were not feasible. AgentSight attaches by byte prologue for rustls 0.23 builds (Reported).
Decision: Feasible per build by prologue matching, request side only, pinned to one rustls and rustc version. Verified on Codex 0.154.0 (rustls 0.23.36, rustc 1.95.0): the `write_vectored` pattern does not match this build, and the `write` prefix has 10 candidates that cannot be told apart statically (whether any is the right function is Unverified). The same reasoning applies to Claude Code by offset.
Consequences: One of two patterns already fails on a current build, which is direct evidence of drift.
Alternatives rejected: Putting per-build prologues on the critical path.

### N-16: Content capture is request-side only (`SSL_write`)
Status: Superseded by N-29 on 2026-10-17: `SSL_read` is hooked by a uprobe and uretprobe pair, and responses are recorded as `net_response` attestation. Kept as taken. Amended 2026-10-27: the write is copied at its return since N-37.
Date: 2026-09-14.
Context: The request side is what a trajectory states verbatim (N-11). `SSL_read` needs a uretprobe that stashes the buffer at entry.
Decision: Hook `SSL_write` at entry only, up to 16 KiB per frame.
Consequences: The model API response stream, where a server-side web search lives, cannot be read (O-14, O-19).
Alternatives rejected: Both directions in the first implementation.

## Rejected alternatives (from the September 2026 trade-off study)

### N-17: mitmproxy as the primary network layer
Status: Superseded by N-7.
Date: recommended early September 2026, superseded 2026-09-12.
Context: The trade-off study recommended a transparent mitmproxy first, with uprobes as fallback and pcap as backup.
Decision (historical): Primary capture through a TLS-terminating proxy.
Why superseded: CA injection differs per runtime and is impossible for compiled-in roots; pinning fails it outright; it is in-path and detectable; it needs per-container network setup. N0 covers every target with none of these costs, and the content a proxy adds is useful only for the narrow request-side case (N-12).

### N-18: Packet, kernel-TLS and full-system alternatives
Status: Rejected.
Date: 2026-09.
Context: Alternatives considered for network capture or as a replacement of the whole probe stack.
Decision and reasons:
- pcap or tcpdump: ciphertext only, high volume, L7 reconstruction. N0 gives the same occurrence data per process.
- eBPF TC hooks: same encryption problem at L3/L4, no process identity.
- Sidecar proxy (Envoy, Linkerd): same pinning problem as a proxy, heavy for a prototype.
- Kernel TLS (kTLS): rarely enabled; Python, Go and rustls do not use it by default.
- gVisor: total syscall interception, but 2 to 11 times I/O overhead (Reported), incomplete syscall coverage, and no eBPF inside the sandbox.
- Tetragon, Tracee, Falco: built for alerting; content capture limited or absent; customizing them costs as much as custom probes.
- Firecracker or Kata microVMs: block-level and L2/L3 visibility, the wrong abstraction for paths and plaintext.
Consequences: Custom eBPF probes plus fanotify remain the stack.

### N-19: Port-0 connects are not emitted
Status: Accepted, implemented (`net.Observer.emit`, `TestEmitSkipsAddressSelectionAndReportsDNS`). Amended 2026-10-11 (commit 4343878): port-0 connects are now counted in `Coverage.AddressProbes`, and port 53 is no longer dropped (N-20), so the comparisons with the DNS drop and the last consequence (no counter) no longer hold.
Date: 2026-10-07.
Context: In a paired capture of Claude Code every real connection was preceded by connects to port 0 of the destination's IPv4 and IPv6 addresses, and nothing was sent on them. The resolver connects a datagram socket to each candidate address to ask the kernel which source address it would use (RFC 3484 address selection; **Reported**, glibc behaviour; the twin pattern is **Verified** in that capture). They name addresses that change with DNS, so no trajectory can claim them and a baseline cannot list them. A fetch of a new host left one as an unrecorded action.
Decision: `emit` drops a connection to port 0, like port 53 (N-13), and marks it emitted so its close does not retry.
Consequences: Ground truth no longer holds the `IP:0` events, so baselines measured earlier carry rules that match nothing (harmless). A real connection to port 0 does not exist, so nothing legitimate is hidden. Like the DNS drop it has no counter.
Alternatives rejected: Dropping them in the adapter (it is resolver behaviour, not a harness property); recording them as capability evidence (they carry no information about what the agent did).

### N-20: A connection to port 53 is capability evidence, not a dropped event
Status: Accepted, implemented (`emit` in `pkg/probe/net/observer.go`, `models.NetDNS` unclaimable). Decides O-15, removed from open.md on 2026-10-11. Supersedes N-13. Amended by N-27 (2026-10-15): a DNS query carries its question in the target, one event per query on a datagram socket, and a connection to port 53 that sent nothing is a `net_dial`. Amended by N-28 (2026-10-15): a datagram sent to port 53 with an explicit address is `net_dns` too.
Date: 2026-10-11 (security review).
Context: N0 dropped every connection to port 53 on the reasoning that DNS lookups are the resolver's and no trajectory records them. The filter is on the port, not on the protocol: a TCP connection to port 53 anywhere is a channel for data, and it left no trace in the capture and no counter.
Decision: A connection to port 53 is emitted as `net_dns` with the `ip:port` target, ground truth only like `net_bind`: in the capture and the report's capability list, never aligned and never a finding, since an honest run makes one per lookup. The count is in `Coverage.DNS`. Port 0, the resolver's address selection, is still not emitted but is counted (`Coverage.AddressProbes`).
Consequences: Data moved over port 53 is visible to a reader of the report and in the forensic view of the command that did it. It is not a finding, because the probe cannot tell a lookup from an exfiltration, and the resolver's own connections are many. The claimable set loses `net_dns`, which no adapter ever produced.
Alternatives rejected: Distinguishing UDP from TCP (the connect tracepoint does not see the socket type; a socket hook is more code for a weak signal, since UDP carries data too); treating port 53 as a finding (every honest run resolves names).

### N-21: Connections still open at the end of the capture are emitted then
Status: Accepted, implemented (`flushOpenConnections` in `pkg/probe/net/observer.go`).
Date: 2026-10-11 (security review, local only).
Context: A connection whose ClientHello carried no name was emitted only on its `close()`, with the address as target. One held open until the process exited, or past the end of the capture, was never emitted and nothing counted it: an agent that connected by address, sent, and never closed left no trace.
Decision: When both record feeders have closed, the correlator emits every connection still open, in connect order, each stamped with its connect time, and counts them in `Coverage.OpenAtStop`.
Consequences: Every connection the probe saw reaches the capture. The stamp is the connect time, so the event sorts where the connection began; a connection with a name was already emitted at its hello and is not emitted twice.
Alternatives rejected: Emitting every connection at connect time (a connection with a name would then be emitted by address first and by name later, two events for one connection, and the baseline names addresses that change).
Note 2026-10-11: "every connection the probe saw" excludes one whose descriptor was closed without `close()` (by `dup2`, `close_range` or an exec under `O_CLOEXEC`) and on which the same process then connected again: the new connect replaces the entry before it is emitted, and nothing counts it ([../architecture/13_probe_net.md](../architecture/13_probe_net.md), Known limits).

### N-22: A connection that sent nothing is capability evidence, not a connection
Status: Accepted, implemented (`connection.wrote`, `emit` in `pkg/probe/net/observer.go`, `models.NetDial`).
Date: 2026-10-11 (security review; the IP literals in baseline rules).
Context: Every baseline held `net_connect` rules naming addresses, `160.79.104.10:443` and an IPv6 twin: the losing halves of the harness's dual-stack connects, which close with no ClientHello and so were emitted by address at their close. The addresses change with DNS, so the rules were tied to the day of the capture, and a rule for an address explained any later connection to it that sent data without a name.
Decision: A connection that closes, or is flushed at the end, with no name and no byte ever written on it is `net_dial`, ground truth only like `net_bind`: in the capture and the capability list, never aligned, never a rule. A connection that wrote and had no name stays `net_connect` by address, which a claim or a rule must explain.
Consequences: Baselines no longer name addresses for the harness's losing connects, so they do not rot with DNS, and a data-carrying connection by address is no longer explained by one. A dial carries at most the fact that it happened, a covert channel of one bit per connect, which the report shows. The `wrote` flag comes from the first write the kernel saw on the descriptor, whatever it carried.
Alternatives rejected: Templating addresses in rules (a wildcard explains whatever an attacker makes it match, V-19); resolving addresses back to names (DNS is not observed, O-20).
Note 2026-10-11: the writes the kernel sees are `write`, `sendto` and `sendmsg` by the process that made the connect. A connection without a name whose data went through `writev`, `sendfile`, `splice`, `sendmmsg` or io_uring, or was written by a child that inherited the descriptor, is a `net_dial`, and so is not a finding, even at level 0 ([../architecture/13_probe_net.md](../architecture/13_probe_net.md), Known limits; O-18).

### N-23: The send side of a connection is completed in the probe, and `net_dial` stays capability evidence
Status: Accepted, implemented (`trace_writev`, `trace_pwritev2`, `trace_sendmmsg`, `trace_sendfile`, `trace_splice`, `capture_hello_iov`, `mark_sent` in `pkg/probe/net/net.bpf.c`, `netSend` in `pkg/probe/net/observer.go`, keyed by socket per N-24; `TestObserver_SendsWithoutWriteAreConnections`, `TestObserver_HelloAcrossIovecsYieldsSNI`, `TestObserver_ForkedChildWriteMarksConnection`, `TestObserver_SCMRightsReceiverWriteMarksConnection`, `TestHandleNetRecord_RecordsFromAnotherProcessFollowTheSocket`). Ratified by the user on 2026-10-11 (was O-27 in open.md).
Date: 2026-10-11.
Context: N-22 makes a connection with no observed send `net_dial`, capability evidence that is never a finding. The probe sees a send only through `write`, `sendto` or `sendmsg` by the process that made the connect. Data sent through `writev`, `sendfile`, `splice`, `sendmmsg` or io_uring, or written by a child after `fork` (a shell that connects through `/dev/tcp` and pipes a file through a forked `cat`), leaves the connection a `net_dial`, so an unclaimed connection that carried data can pass unreported.
Decision: Keep N-22. Close the gap in the probe: observe the missing send paths and follow the socket across `fork` and descriptor passing, so that any connection that carried data is a `net_connect`.
Consequences: Baselines keep no address rules (N-22). Until the probe work lands, the gap is a known limit of the net lane, shared in part with io_uring (O-18).
Alternatives rejected: Reporting a dial only in a command's subtree, and reverting dials to `net_connect` by address: both bring address rules back into baselines for the cases they cover.
Note 2026-10-11 (docs review): scope of this entry. Sends through `writev`, `sendmmsg`, `sendfile` and `splice`, a multi-iovec `sendmsg`, and a connection written by another process that holds the descriptor (a child after `fork`, or a process that received it over `SCM_RIGHTS`) are in scope. Sends through io_uring are covered by O-18 (moving the hooks to the socket layer), which would also close this entry's gaps.

### N-24: A connection is identified by its socket and ends at its last descriptor
Status: Accepted, implemented (`fd_socket`, `file_last_ref`, `release_fd`, `trace_dup2`, `trace_dup3` in `pkg/probe/net/net.bpf.c`; `handleNetRecord` in `pkg/probe/net/observer.go`; `TestObserver_ConnectionClosedByDup2IsEmitted` and the N-23 tests).
Date: 2026-10-12.
Context: N-23 requires a send by any process holding a connection to mark it. The probe keyed a connection by the tgid and descriptor of the connect, which a child after `fork`, a receiver of `SCM_RIGHTS` and a duplicate descriptor do not share, and it ended the connection at the connecting process's `close()` of that descriptor, which can come before another holder sends (a sender commonly closes its copy right after passing it). A syscall tracepoint sees only the descriptor number. The socket-layer hooks of O-18 would receive the socket directly, but O-18 is undecided.
Decision: Every hook that names a descriptor of a connection resolves it with CO-RE reads through the calling task's fd table (`task->files->fdt->fd[fd]`) to the file, checks that its inode is a socket, and keys the connection by the socket inode number (`f_inode->i_ino`). Records carry the number in the header field `sock`, and userspace keys its connections by it. A connection ends when a tracked process drops a descriptor that holds the last reference to the socket's file, through `close`, `dup2` or `dup3`; the count is read from `f_ref` (kernel 6.13 and later) or `f_count`, chosen by a CO-RE field-existence check. The event's PID stays the process that connected.
Consequences: A send from any tracked holder marks the connection, in whatever order the holders close. A duplicate in the same process (bash moves its `/dev/tcp` descriptor with `fcntl(F_DUPFD)` before it closes it) no longer ends the connection early, and a `dup2` over a connected descriptor ends that connection at the `dup2` instead of at a later connect on the same number (N-21's note of 2026-10-11 described the earlier keying). A connection whose last reference goes without a hooked call (process exit, `close_range`, an exec under `O_CLOEXEC`, a holder outside the tracked tree) ends at the end of the capture with its connect time (N-21), where a close by the connecting process used to end it. A syscall running in another thread on the same socket holds a reference, so a close during it is not the last. Each send of a tracked process now costs a few kernel reads. `Coverage.Replaced` counts only a socket connected again.
Alternatives rejected: Keying by the `struct sock` address (the slab hands it to the next socket, so an entry left by a socket released without a hooked call would match an unrelated socket; the inode number is not reused that way); following descriptors in the (tgid, fd) map across `fork`, `dup` and `SCM_RIGHTS` (the receiver gets a number the sender never sees, and every dup path would need a hook); socket-layer hooks (O-18, undecided).

### N-25: io_uring socket operations by tracked processes are counted as event loss
Status: Accepted, implemented (`trace_iouring_submit`, `trace_iouring_setup` and the `iouring_*_count` maps in `pkg/probe/net/net.bpf.c`; `ProbeCoverage.IOURingNetOps`; `verification.Assess`; `TestObserver_IOURingSocketOpsAreCounted`, `TestObserver_IOURingFileOpsAreNotNetwork`). Amended by N-32 (2026-10-18): `trace_iouring_submit` is a raw tracepoint on `io_uring_submit_req`, and `io_uring_setup` is counted by the `sys_enter` dispatcher `trace_sys_enter`; `trace_iouring_setup` no longer exists.
Date: 2026-10-13.
Context: Every net hook is a `sys_enter_*` tracepoint, and an operation submitted through io_uring passes none of them, so a runtime that sends through io_uring yields no connection or a `net_dial` and a run can read FAITHFUL on a network omission. O-18 (socket-layer hooks) would see such operations but is undecided and costly. The cheap alternative, counting every `io_uring_setup` as loss, would make every run that starts Node.js INCONCLUSIVE. Measured on 2026-10-13, kernel 6.17, unprivileged (**Verified**): `strace -f -e trace=io_uring_setup,io_uring_enter,io_uring_register` shows no io_uring call from the Claude Code 2.1.296 process (Bun) in `claude --version`, `--help`, `auth status` (which connects over TCP), `doctor` and `mcp list`, and the binary has no io_uring symbol or string and imports `epoll_ctl` and `epoll_wait`. The io_uring calls in those runs came from Node.js children (`npm`, `npx` MCP servers). Node.js 20.19.4 with libuv 1.50.0 sets up two rings per process and, logged per submission by an `LD_PRELOAD` shim on libuv's `syscall` and `mmap64`, submits only `IORING_OP_EPOLL_CTL`, for a `fetch` over HTTPS with file copies, a raw `net.connect`, `npm config get prefix`, and a file read with `UV_USE_IO_URING=1`. Python 3.13 (`urllib` fetch, `shutil.copy`), curl 8.14, git 2.51 (`ls-remote` over HTTPS) and `cp` make no io_uring call.
Decision: Option 1 of O-18: detect and degrade. A program on the `io_uring:io_uring_submit_req` tracepoint counts, for tracked processes, every submitted operation (diagnostic) and every network operation in `iouring_net_count`, reported as `ProbeCoverage.IOURingNetOps`, which `Assess` treats as event loss, so the run is INCONCLUSIVE with a reason naming io_uring. A network operation is one whose opcode works only on sockets (`SENDMSG`, `RECVMSG`, `ACCEPT`, `CONNECT`, `SEND`, `RECV`, `SHUTDOWN`, `SOCKET`, `SEND_ZC`, `SENDMSG_ZC`, `BIND`, `LISTEN`, `RECV_ZC`), or a data operation (`READ`, `WRITE`, their vectored and fixed-buffer forms, `READ_MULTISHOT`, `SPLICE`, `TEE`) whose descriptor is a socket by the same fd-table lookup as N-24, or is a registered file or cannot be read, which the probe cannot tell from a socket. `EPOLL_CTL`, `POLL_ADD`, file operations and the rest are not. A `sys_enter_io_uring_setup` program counts the rings tracked processes set up (diagnostic). On a kernel without `io_uring_submit_req` but with the syscall, the observer adds every ring to `IOURingNetOps`, so the minimum kernel stays unchanged and such a kernel degrades every io_uring user. The operations themselves are still not recorded; O-18 stays open.
Consequences: A run in which a tracked process moves network data through io_uring can no longer be FAITHFUL. Runs of the measured runtimes are unaffected: Node.js's `EPOLL_CTL` submissions do not count. A file-only program that reads or writes registered files through io_uring is INCONCLUSIVE, the price of not resolving the ring's file table. The count says the net lane was blind for part of the run, not how many actions it missed. A capture written before this counter existed carries no `io_uring_net_ops` and reads as zero.
Alternatives rejected: Counting `io_uring_setup` alone (every Node.js child would make a run INCONCLUSIVE); counting every submitted operation (the same, through `EPOLL_CTL`); recording the operations as events (that is O-18's socket-layer rewrite, not a counter); resolving registered files through the ring's file table (kernel-version-specific layout for a case no measured runtime uses).

### N-26: A net probe that tracked no pid reports that it did not run
Status: Accepted, implemented (`Observer.tracking` and `CaptureCoverage` in `pkg/probe/net/observer.go`; `TestCaptureCoverage_NothingTrackedIsNotRan`, `TestObserver_HostWideRunIsNotRan`).

### N-27: A DNS query is recorded with its question in the `net_dns` target
Status: Accepted, implemented (`parseDNSQuery`, `dnsName`, `dnsTarget` in `pkg/probe/net/dns.go`; `dnsQuery` and `emit` in `pkg/probe/net/observer.go`; `sock_type`, `dns_per_datagram` and the `sotype` header field in `pkg/probe/net/net.bpf.c`; `TestParseDNSQuery`, `FuzzParseDNSQuery`, `TestHandleNetRecord_DNSQueriesCarryTheirQuestion`, and the privileged `TestObserver_DNSQuestionsAreRecorded`, `TestObserver_GetaddrinfoQuestionIsRecorded`, `TestObserver_DigAndHostQuestionsAreRecorded`). Amends N-20. Decides the DNS-name part of O-20. Amended by N-31 (the bytes copied per query).
Date: 2026-10-15.
Context: Since N-20 a connection to port 53 is `net_dns` with the resolver's `ip:port` as target, so a lookup shows which resolver was asked, not which name, and a DNS exfiltration channel shows only as a number of connects to the resolver. Measured on 2026-10-15 on the development machine (kernel 6.17, glibc 2.42, `hosts: files mdns4_minimal [NOTFOUND=return] dns`, nameserver 127.0.0.53) with `strace -f -e trace=connect,sendto,sendmsg,sendmmsg,write,writev` (**Verified**): glibc's `getaddrinfo` (`getent ahosts`, Python's `socket.getaddrinfo`, Node.js 20 `dns.lookup`) connects a datagram socket to the resolver and sends the A and AAAA queries in one `sendmmsg` with no address; glibc's `gethostbyname` (`getent hosts`) and c-ares (Node.js `dns.resolve4`) use `sendto` with no address on the connected socket; `dig`, `host` and `nslookup` (BIND 9) use `sendmsg` with no address, one connected socket per query; `dig +tcp` connects over TCP and sends the two-byte length prefix and the message as two iovecs of one `writev`; Go 1.26's resolver (`PreferGo`) and busybox `nslookup` use `write` on a connected socket, busybox sending A and AAAA on the same socket; `resolvectl` asks systemd-resolved over D-Bus. Go's RFC 6724 address selection (`srcAddrs` in `net/addrselect.go`, **Reported**) connects a datagram socket to port 53 of every candidate address and sends nothing, so each Go lookup also produced `net_dns` events naming the web server's addresses. No resolver measured here sends with an explicit address on an unconnected socket; musl's `res_msend` does (**Reported**, musl source; no musl program was measured).
Decision: The question travels in the target, as `<name>/<type>[/<class>]@<resolver ip:port>`: the name of the first question in presentation form (case kept; every byte other than a letter, digit, `-` or `_` written `\DDD`, so the target holds no stray `.`, `/`, `@` or control byte; the root is `.`), the type as its mnemonic or `TYPE<n>`, the class only when not `IN`. The probe reads every datagram sent on a datagram socket connected to port 53, and every datagram sent to port 53 with an address (N-28), and emits one `net_dns` event per query that parses, stamped at the send; on a stream socket it reads the first send only, with the TCP length prefix. Parsing is in userspace, on the 1024 bytes the kernel copies: only a standard query (QR 0, opcode QUERY) with a question parses, every read is bounded by the captured bytes, a compression pointer may point only backwards and past the header, at most 16 are followed, a label is at most 63 bytes and the name at most 255. Bytes that do not parse are counted in `Coverage.DNSUnparsed` and never trusted: the connection then ends as `net_dns` with the resolver's address alone, as before. A connection to port 53 that sent nothing is a `net_dial` (N-22), not `net_dns`.
Why the target, not a field: capability evidence reaches the reader through its target, in the capability list of the report, the per-command groups (`dns (N): ...`) and the forensic view, so the name is shown with no change to `cmd/verify`, to `GroundTruthEvent` or to the JSON formats. Baselines never hold `net_dns`: it is unclaimable, so `agent.Capture` never takes a rule from it, and it is not one of the types a command's subtree record checks (`SubtreeChecked`, V-38), so I-41's canonical forms never apply to it and a per-run name in the target compares with nothing. I-41 rejected a second target field on `GroundTruthEvent` on the same grounds (a second target every rewrite would have to keep in step, and a change to the formats). A capture written before this decision has bare `ip:port` targets, which stay valid and read as before; the `@` tells the two forms apart.
Consequences: The report names every looked-up name a tracked process sent, and a DNS exfiltration channel shows its queries, not a count. An honest run has more `net_dns` events (one per query rather than per socket where a resolver reuses a socket) and none in the verdict. A flood of datagrams to port 53 is one record each and can fill the ring buffer, which is counted as event loss (`RingbufDrops`) and makes the run INCONCLUSIVE rather than hiding it. Go programs no longer produce `net_dns` events naming web servers; their address-selection sockets are `net_dial` events. `Coverage.DNS` counts every `net_dns` event, `DNSNamed` those with a question; neither, nor `DNSUnparsed`, reaches `ProbeCoverage`, since a question that did not parse is a content gap on capability evidence, not event loss. Only the first message of `sendmmsg` is read, so glibc's AAAA query is not recorded, and a batch of queries shows its first. A lookup through `nss-resolve` or `nscd` leaves the tree over a Unix socket and its name is not seen. Every fixture predates this decision, so verification of them is unchanged.
Alternatives rejected: A `Query` field on `GroundTruthEvent` (above). Parsing in the BPF program (label loops and compression pointers under the verifier's bounds, for no gain over a defensive parser in userspace that a fuzz test exercises). Reading the first datagram of a socket only (one socket can carry a whole exfiltration, of which only the first name would show). Lowercasing names (DNS compares them case-insensitively, but case can carry data, and nothing here compares them).

### N-28: A datagram sent to an explicit address is a connection to that address
Status: Accepted, implemented (`read_peer`, `addressed_send`, the `dgrams` map and `NET_DGRAM` in `pkg/probe/net/net.bpf.c`; `handleDatagram` in `pkg/probe/net/observer.go`; `TestHandleNetRecord_AddressedDatagrams` and the privileged `TestObserver_AddressedDatagramsAreConnections`, `TestObserver_DNSQuestionsAreRecorded`). Decides the unconnected-UDP part of O-20. Amended by N-31 (the bytes copied per datagram).
Date: 2026-10-15.
Context: A datagram sent with `sendto` or `sendmsg` and an address, on a socket that was never connected, passes no `connect()`, so N0 never saw it: UDP data, QUIC (HTTP/3) and a resolver that sends unconnected (musl, N-27) went unseen, with no counter. O-20 proposed recording such datagrams as unclaimable capability evidence. A datagram socket that is connected and sends is already a `net_connect` by address (N-22), which a claim or a baseline rule must explain. A `sendto` with `MSG_FASTOPEN` and an address on a TCP socket connects it (TCP Fast Open) with no `connect()` either.
Decision: A send with an `AF_INET` or `AF_INET6` address (`sendto`, `sendmsg`, the first message of `sendmmsg`) on a `SOCK_DGRAM` or `SOCK_RAW` socket, connected or not, is recorded as the connection a `connect()` to that address followed by that send would be: to port 53, `net_dns` per datagram with its question (N-27); to any other port, `net_connect` by address, once per socket and destination, with the sender as `PID`, stamped at the first datagram. The kernel deduplicates in an LRU map and userspace drops the repeats an eviction causes. Port 0 is not address selection there, since bytes went. On a TCP socket not yet connected, `MSG_FASTOPEN` with an address is recorded as the connect it is, and the bytes it sends as its hello, so its SNI is read. `Coverage.Datagrams` counts the datagrams recorded (diagnostic).
Why `net_connect` and not capability evidence: the same bytes to the same address are a `net_connect` when the socket was connected first. Recording the unconnected form as unclaimable would let an agent turn an unclaimed connection that carried data into capability evidence by skipping `connect()`, the downgrade N-22 and N-23 closed for connections that sent data.
Consequences: An unclaimed datagram by the agent's own process is an Unrecorded finding, and one beneath a claimed command is that command's content. A harness that sends datagrams itself (QUIC, telemetry over UDP) would need address rules in its baseline, which age with DNS as N-22 describes; no harness or resolver measured so far sends one (N-27), but QUIC-capable clients were not measured (**Unverified**). A QUIC connection is reported by address: its name is in the encrypted Initial packet. The record says that data went to a destination, not how much. A capture written before this decision has no such events.
Alternatives rejected: An unclaimable type for datagrams (the downgrade above, and a new action type the verifier, the report and the models would have to learn). A kernel record per datagram (QUIC sends thousands; the ring buffer would fill and make honest runs INCONCLUSIVE). Counting datagrams without recording them (the count would not say where the data went). Socket-layer hooks (O-18, undecided).

### N-29: Responses are captured at `SSL_read` and recorded as `net_response` attestation
Status: Accepted, implemented (`probe_ssl_read_entry`, `probe_ssl_read_return` in `pkg/probe/net/tls.bpf.c`; `pkg/probe/net/response.go`; `tlsoffset.Scan`; `tlsparse.ResponseParser` and `sse.go`; `models.NetResponse`, `models.ResponseAttestation`, `ProbeCoverage.Responses` and `ResponseGaps`; `TestResponseParser_*`, `FuzzResponseParser`, `TestResponses_*`, and the privileged `TestObserver_SSEResponseViaSSLReadUretprobe`). Supersedes N-16, amends N-11. Decides O-19 and the capture half of O-14. How a `WebSearch` call uses a response is decided by V-45 ([verification.md](verification.md)). Amended 2026-10-18: `cmd/verify` counts, lists and groups responses under their own label, and `Assess` adds a note for `ResponseGaps` and for an inactive response capture, so neither changes an outcome ([20_verifier.md](../architecture/20_verifier.md), [40_tools.md](../architecture/40_tools.md)).
Date: 2026-10-17.
Context: N-16 hooked `SSL_write` only, so the model API response stream was unreadable: a server-side tool such as Claude Code's `WebSearch` runs inside it (I-16), and the join between a transcript's `requestId` and the response's `request-id` header needs it. O-14 weighed an `SSL_read` uretprobe against an N2 proxy (detectable, defeated by pinning, N-10); O-19 proposed the uretprobe and SSE reassembly. The offset experiment of 2026-09-13 found two functions of the `ssl_lib.cc` cluster firing in lockstep with a 512 KiB read length in Claude Code 2.1.270 (**Verified**, the read path), so `SSL_read` is in the same cluster `pkg/tlsoffset` already scans. OpenSSL 3.5's `s_client` reads through `SSL_read` (**Verified** with gdb on 2026-10-17).
Decision: Capture: a uprobe at `SSL_read`'s entry stores `ssl` and `buf` by pid and tid, a uretprobe at its return copies as many bytes as it returned, at most 16 KiB, onto the same ring as the writes, so a response is read in userspace after the request before it on the same thread. A faulted read and a ring drop of a read frame have their own counters. Offset: `tlsoffset.Scan` returns `SSL_read` candidates (the symbol, else the cluster), a cached offset first; the first is attached in `New`; after the `SSL_write` offset validated, each remaining candidate other than it gets a window in which a read from a tracked process that begins with an HTTP/1.x status line accepts it (N-D4); reads before that are discarded and counted; `Start` does not wait. Parsing: HTTP/1.1 responses per connection (N-30), bounded, the body hashed as it streams and never kept, a `text/event-stream` split into events and counted by event name, a gzip or deflate stream decoded at its end. Representation: a new action type `net_response`, ground truth only, stamped at the status line, whose `Target` is the request it answers and whose record (`ResponseAttestation`) holds the status, the `request-id` (else `x-request-id`), content type and encoding, body length and SHA-256, end time, completeness, truncation, pairing and the event counts. Response data the capture may be missing is summed in `ProbeCoverage.ResponseGaps`, the read side's state in `ProbeCoverage.Responses`.
Why a new type and not fields on `net_request`: a response arrives later than its request, a stream runs for minutes, and a response can arrive with no request seen (before validation, or after a request frame was lost). Fields on the request would hold the request back until its response ended, or lose the response. A separate event keeps request emission as it was. Why unclaimable: N-11 makes the response side attestation, and the request side already carries what a claim states; an unclaimable type is never aligned and never a finding, so no verifier change is needed and no verdict changes. The body hash identifies a response (two captures, or a later stage, can tell whether the same bytes came back); it amends N-11's "never hashed" only in that sense, and nothing compares it with a trajectory.
Consequences: A capture with content capture has one `net_response` per response read over TLS by the hooked executable, beside the requests. The verifier places it with the capability evidence (unclaimable, not part of the verdict), and `cmd/verify` prints it there; its per-command grouping, which names unknown capability types "unix sockets", and the capability count's wording do not yet know the type. `Assess` does not read `Responses` or `ResponseGaps`, so neither changes an outcome. Read frames add load to the TLS ring (now 4 MiB), so a burst of responses can cost a write frame, which counts as event loss. How a `WebSearch` claim would use a response is not decided (O-14). Every fixture predates this decision, so verification of them is unchanged. The live capture on Claude Code (whether its `SSL_read` validates on a current Bun build, whether its stream is compressed, and whether the transcript `requestId` equals the `request-id` header) is not done (**Unverified**). Amended 2026-10-27 (commit d12f5d3): on the `long` pilots of Claude Code 2.1.306 with content capture every model API response was read complete and parsed and its event stream counted ([../architecture/13_probe_net.md](../architecture/13_probe_net.md)); the `requestId` join is still unconfirmed (O-14).
Alternatives rejected: An N2 proxy (N-10, N-17). Fields on `net_request` (above). A claimable `net_response` (N-11). Keeping event text, such as the search query or result URLs, from the stream (N-D3; part of O-14). A second ring for reads (it would lose the order between a request and its response, which pairing needs). Decoding brotli and zstd (no such decoder in the standard library; the stream is still hashed).

### N-30: TLS content is reassembled per `SSL*`, not per thread
Status: Accepted, implemented (`ssl` in the `ssl_frame` header of `pkg/probe/net/tls.bpf.c`; `sslKey`, `tlsConn` in `pkg/probe/net/correlator.go`; `TestResponses_PairedPerConnectionOnOneThread`, `TestHandleSSLFrame_TruncatedWriteDropsTheStream`). Amends N-D1.
Date: 2026-10-17.
Context: Since N-D1 frames were reassembled per (tgid, tid). An event loop such as Bun's serves every connection from one thread, so the reads of a streaming response interleave with those of other connections, and a per-thread stream mixes them; pairing a response with its request needs the connection as well. The first argument of `SSL_write` and `SSL_read` is the connection's `SSL*`. A write larger than the 16 KiB copy left a hole in the stream that the request parser read across, so a body could be hashed from the wrong bytes.
Decision: Both probes record the `SSL*`, and userspace keys a connection's request stream, response parser and latest request by (tgid, `SSL*`). A response answers the latest request on its connection. At most 4096 connections keep state; the least recently seen is closed past that. Each frame records the bytes the call moved as well as those copied; a write frame with bytes missing discards its connection's request stream, counted in `FramesTruncated` and `FramesUnattributed`, instead of parsing across the hole.
Consequences: Interleaved connections on one thread no longer mix. A pointer the allocator reuses for a later connection continues the earlier one's state, which the request parser and the response parser's status-line resynchronization absorb. The `SSL*` is still not joined to a socket, so a request is still attributed by its `Host` header. Pipelined requests pair the first response with the later request.
Alternatives rejected: Per-thread streams (above). Joining `SSL*` to the socket by reading BoringSSL internals (per-build structure offsets, the drift N-15 describes).

### N-31: The ClientHello is captured whole, across sends and records
Status: Accepted, implemented (`HELLO_CAP_LEN`, `hello_follow`, `capture_more`, `capture_more_iov`, `NET_HELLO_MORE` and the header's `flags` in `pkg/probe/net/net.bpf.c`; `resolveHello` and the `netHelloMore` case in `pkg/probe/net/observer.go`; `tlsparse.ParseClientHello` across records and `tlsparse.ClientHelloComplete`; `TestParseClientHello_SNIPastTheFirstKiB`, `FuzzParseClientHello`, `TestHandleNetRecord_HelloAcrossSends`, and the privileged `TestObserver_LargeAndSplitHellosYieldSNI`). Decides O-20. Amends N-27 and N-28 (the bytes copied per record).
Date: 2026-10-18.
Context: The hello capture was 1024 bytes of the first send of a connection. A ClientHello with a post-quantum key share is larger. Measured on 2026-10-18 on the development machine, each client connecting to a local listener with SNI `api.anthropic.com` (**Verified**): OpenSSL 3.5.3 (`openssl s_client`, curl 8.14.1, Python 3.13 `ssl`, and Node.js 20.19.4, which links the same OpenSSL) sends 1559 to 1603 bytes in one write, with an X25519MLKEM768 key share of 1216 bytes, and its SNI extension ends at byte 173 to 217; Go 1.26 `crypto/tls` sends 1479 bytes with the SNI extension ending at byte 134; Chrome 151 (BoringSSL) sends 1733 to 1829 bytes and permutes its extensions per connection, so in 10 of 20 connections the SNI extension ended past byte 1024 (at 1516 to 1824) and the connection was reported by address. Claude Code's Bun runtime uses BoringSSL; whether Bun enables extension permutation or a post-quantum group was not measured, since the agent does not run here without its model (**Unverified**). A client that writes its hello in pieces, or fragments it over several TLS records (RFC 8446 allows it, and DPI-evasion tools do it on purpose), lost the name at any size.
Decision: Two parts. One record carries up to 4096 bytes (`HELLO_CAP_LEN`; the per-CPU scratch grows to 8 KiB for the iovec copy's slack, the ring to 1 MiB), so a hello up to 4 KiB sent in one call is captured whole. When the first send of a stream connection begins a TLS handshake record carrying a ClientHello (or is 2 to 8 bytes that begin a handshake record) and does not hold the whole message, the kernel follows it: `conns` keeps how many bytes remain (to the end of the record when the message fits its record; up to one full record, 16389 bytes in all, when the message continues past its record or the header is incomplete), and each later send on the connection, by any holder, is captured as `NET_HELLO_MORE`, up to 4096 bytes and 8 records, with a flag on each record while more follows. A send the capture cannot hold whole (over 4096 bytes, or past the eighth iovec) ends the following, since the send after it would not continue the captured bytes. Userspace keeps the bytes per connection and parses the hello when the flag is clear or the handshake records hold the complete message; `tlsparse.ParseClientHello` joins the handshake records at the start of the bytes into the first handshake message. A hello still incomplete when its connection ends is parsed from what arrived, and a name found then stamps the connection at the hello.
Why not only a larger capture: it covers the measured cases but not a hello written in pieces or fragmented over records, and following costs one field in `conns` and records only for the connections that need it. Why the kernel decides how far to follow: userspace sees the records after the sends, so only the kernel can know at each send whether to copy it.
Consequences: A hello up to 4 KiB in one send, or up to 16 KiB over at most 9 sends, yields its name. A followed hello is emitted at its last part (or the connection's end), stamped at its first. Records are larger, so a burst of new connections, of DNS queries over 1 KiB or of datagrams to new destinations fills the ring sooner, which the larger ring offsets; a full ring is counted as before. DNS queries and addressed datagrams carry up to 4096 bytes (N-27, N-28), which no parse depends on. `Coverage.HellosFollowed` counts the hellos followed (a diagnostic, not in `ProbeCoverage`). A record from before this decision has flags 0 and parses as before. Every fixture predates this decision, so verification of them is unchanged. Encrypted Client Hello still hides the name: a limit no capture size changes.
Alternatives rejected: A larger fixed capture alone (above). Parsing SNI in the BPF program (extension walks under the verifier's bounds, and the following would still be needed for split hellos). Following the next sends of every connection whatever its first bytes (a record per send of every plaintext protocol). Following without a bound (a client that fragments into 1-byte records would have the kernel copy every send; the bound turns that into a connection reported by address).

### N-32: Hooks are raw tracepoints, and Stop drains the rings instead of closing them
Status: Accepted, implemented (`trace_sys_enter`, `sys_enter_progs` and the raw tracepoint programs in `pkg/probe/net/net.bpf.c` and `pkg/probe/net/tls.bpf.c`; `netRawTracepoints`, `sysEnterPrograms`, `kernelHasIOURing`, `Stop` and `drainRead` in `pkg/probe/net/observer.go`; the privileged `TestObserver_StopDrainsRingsPromptly`). Amended 2026-10-20: the proc probe made the same change in P-32, so its "five perf-event tracepoints" in Consequences no longer holds.
Date: 2026-10-18.
Context: The overhead benchmark at commit da3e4f0 (10 repetitions on the 12-CPU development laptop, **Verified**) showed `watch` with only the net probe taking 1.4 s from the workload's exit to its own, whatever the workload, against 0.32 s with the fs probe alone (which includes `watch`'s fixed 300 ms sleep) and 0.63 s with the proc probe alone. The net probe attached 18 perf-event tracepoints, the proc probe 5: about 60 ms per tracepoint in both. Releasing a perf-event tracepoint ends in `perf_trace_destroy`, which holds `event_mutex` and, when the event's last perf user goes, calls `tracepoint_synchronize_unregister`, an RCU tasks-trace and an SRCU grace period (**Reported**, Linux source, `kernel/trace/trace_event_perf.c`), so the detaches run one after another and each waits. Releasing a raw tracepoint link unregisters its probe and frees the old probe array through `call_srcu` or `call_rcu_tasks_trace`, and defers the link's own free the same way (**Reported**, `kernel/tracepoint.c`, `kernel/bpf/syscall.c`), so it does not wait. Separately, `Stop` closed both ring readers first: records committed but not yet read were dropped without a count, while the hooks stayed attached.
Decision: Every hook of `net.bpf.c`, and the fork and exit hooks of `tls.bpf.c`, is a raw tracepoint. The fourteen syscall hooks become one program on `sys_enter` that switches on the syscall number first (the tracepoint fires for every syscall on the host), then checks `tracked_pids`, skips a 32-bit syscall (`TS_COMPAT`, as the per-syscall tracepoints do on x86_64), counts `io_uring_setup` itself, and tail-calls the hook's program through a program array that `New` fills before it attaches anything; each program reads its arguments from the saved user registers by x86_64's syscall convention. A tail call that fails counts as a ring drop. `task_newtask`, `sched_process_exit` and `io_uring_submit_req` are raw tracepoints on the same events; the last reads the opcode from the request through CO-RE and counts an operation whose opcode it cannot read as network. Whether the kernel has io_uring, which tells "no submit event" from "no io_uring", is read from tracefs (`events/io_uring`). `Stop` detaches the net hooks, flushes the net ring so that its feeder reads with a deadline of now and returns at the first empty read, flushes the TLS ring to end a validation in progress, waits for `Start`, detaches the TLS write side and the TLS fork and exit hooks, and drains the TLS ring the same way. Then it stops `validateRead` (a status line read during the drain still validates the read side), snapshots the counters and closes the maps.
Consequences: Stopping the net probe no longer waits a grace period per hook; how long it takes is to be measured by rerunning the benchmark as root (**Unverified**). Records committed before the detach are read, not dropped. A hook program still running on another CPU when its link is released can commit a record after the drain has ended, which is then lost uncounted; the window is the run time of one program. The `sys_enter` program runs for every syscall of every process on the host, adding a program call and a switch to each (`write` and `close` already ran a program on every call under the per-syscall tracepoints); the benchmark's workload ratio measures the cost (**Unverified**). With content capture the `SSL_write` and `SSL_read` uprobes still detach through perf events, each with its grace period. The syscall numbers are x86_64's, which the probe already required (the `msghdr` and `iovec` layouts, the uprobes' calling convention). ### N-34: A request line is a capital-letter method, an RFC 9112 target and HTTP/1.0 or HTTP/1.1, or the request is malformed
Status: Accepted, implemented (`parseRequestLine`, `isMethod`, `isTarget` in `pkg/tlsparse/http1.go`; `TestParseHTTP1_OnlyARequestLineIsARequest`, `TestParseHTTP1_ABodyTailAheadOfTheNextRequestIsNotARequest`, `TestHandleSSLFrame_ABodyTailIsNeverARequestMethod`). The cause Context leaves open (O-34) was confirmed and removed by N-37: a failed `SSL_write` retried with the same bytes, copied at its entry.
Date: 2026-10-27 (the first `long` pilot of Claude Code 2.1.306).

The fixtures' ground truths are recorded, so `cmd/verify` on every fixture is unchanged.
Alternatives rejected: Resynchronizing on the last method-like word before the target (a guess at where a request starts, which a body holding a request line could steer). Accepting any RFC 9110 token as the method (a JSON tail without punctuation is a token).

### N-35: The ELF scan reads the executable's sections in windows, never whole
Status: Accepted, implemented (`scanChunk`, `section`, `stringStart`, `scanText`, `scanSection` in `pkg/tlsoffset/scan.go`; `TestScanSectionAgreesWithTheWholeSection`, `TestStringStartAgreesWithTheWholeSection`).
Date: 2026-10-27 (the first `long` pilot of Claude Code 2.1.306).
Context: On the pilot `watch` peaked at 253 MB of resident memory in the task run and at 251 to 252 MB in each control of about five seconds, so the peak does not grow with the session (**Verified**, `watch_maxrss_kb` from `scripts/measure-watch.py`). `tlsoffset.Scan` alone, run on the Claude Code 2.1.306 executable outside `watch`, peaked at 188 MB (VmHWM): to find the `ssl_lib.cc` string it read every allocated section before the one holding it whole (its `.rodata` is 24 MB), and to find the references it read `.text` whole (86 MB), with the Go heap's slack on top (**Verified** with a small program calling `Scan`). Alternatives rejected: Skipping the scan on a cache hit (a cached offset that fails validation needs the candidates, and validation runs later, in `Start`). Mapping the file (file-backed pages count in the resident set as they are touched). Releasing memory after the scan (the measured quantity is the peak).


### N-36: A uretprobe on SSL_write counts, per call, the length asked against the value returned

### N-37: SSL_write content is copied at the call's return, as many bytes as it wrote
Status: Accepted, implemented (`probe_ssl_write`, `probe_ssl_write_return`, `count_write`, `ssl_write_args`, `ssl_write_counting` in `pkg/probe/net/tls.bpf.c`; `attachWrite` in `response.go`; `prepareTLS`, `attachAndValidateTLS` and `Stop` in `observer.go`; the privileged `TestObserver_SSLWriteCountsPartialWrites`).
