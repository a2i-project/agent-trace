# Filesystem probe

Checked against commit 3123fc3 on 2026-10-26.

## Objective

The filesystem probe (`pkg/probe/fs`) records file opens, writes, closes, creations, deletions and renames on the filesystem that holds the workspace, or on every real filesystem mounted on the host, with the PID that caused each one and a content hash for files that were written and closed. The common contract, clocks and coverage format are in [10_probes_common.md](10_probes_common.md).

`Config` fields: `Path` (required; selects the filesystem, and the directory hashed at `Start`), `AllFilesystems` (mark every real filesystem on the host, P-17), `PathFilter` (string prefix on the resolved path), `PIDFilter` (exact pid, test use), `EventBufSize` (default 4096). `New` makes `Path` and `PathFilter` absolute, since events carry absolute paths. `cmd/watch` sets `Path` to `--workspace` and `AllFilesystems`, with no `PathFilter`: the agent's file claims may name any path, so the probe filters nothing and `watch` applies the scope rule once the process tree is known ([10_probes_common.md](10_probes_common.md#how-cmdwatch-builds-and-starts-probes)).

## Technologies

fanotify through `golang.org/x/sys/unix`, in notification class (`FAN_CLASS_NOTIF`) with `reportFlags`, `FAN_REPORT_FID | FAN_REPORT_DFID_NAME` (`0xe00`, the constants of `x/sys/unix`), so the kernel reports file handles and entry names instead of open file descriptors (P-25). Until P-25 the probe requested `0x2400`, `FAN_REPORT_DIR_FID | FAN_REPORT_FD_ERROR`, meant as `FAN_REPORT_DFID_NAME`: no entry name, so a create, delete or rename named only its directory and was ambiguous, and the `FD_ERROR` bit exists only from kernel 6.13; every checked-in capture was recorded that way. Measured on kernel 6.17.0 on 2026-10-14 with an unprivileged inode mark on directories in tmpfs and in ext4, which gave the same records (**Verified**, a scratch program that dumps the info records and resolves each handle by `name_to_handle_at` of the paths that exist when the record is read; `TestKernelNamesEveryDirectoryEntryRecord` repeats the core of it in the suite, without root): every create, delete, moved-from and moved-to record carries one DFID_NAME record (the directory's handle and the entry's name) and no FID record; every open, modify and close-write record carries a DFID_NAME record and a FID record (the file's own handle); no record carried a directory handle without a name. The name is the entry's name when the event happened: a temporary's close read after its rename still names the temporary, while its FID record resolves to the new name. A rename gives a moved-from record naming the source and a moved-to record naming the destination, with nothing linking them. Only records of one process on one directory and one name merge: a temporary created and renamed away before the read gives one `FAN_CREATE | FAN_MOVED_FROM` record on its name, ahead of its `FAN_OPEN | FAN_MODIFY | FAN_CLOSE_WRITE` record, and the moved-to record on the target after both; a file renamed away and back gives one `FAN_MOVED_FROM | FAN_MOVED_TO` record per name; two replaces of one target read in one late batch give one moved-to record. The probe's filesystem-wide mark needs root, so the same shapes under it rest on the privileged tests (`TestObserver_AReplaceThroughATemporaryIsNamed`, which logs the sequence it saw, and the delete and rename tests), which run in CI. The mark is `FAN_MARK_ADD | FAN_MARK_FILESYSTEM` on `Config.Path`, which covers every mount of the filesystem containing that path. `New` reads `/proc/self/mountinfo` once (`readMountTable`) and keeps the file open. With `AllFilesystems`, `markAll` skips pseudo filesystems, read-only images and fuse mounts (`pseudoFSTypes`), and marks each remaining filesystem once, by its `statfs` id, keeping one mount fd per id; it tries the mounts of a whole filesystem (root `/` in the table) before any bind of a subdirectory, each in table order (`markOrder`, P-33). A filesystem it cannot mark or open is recorded and skipped, and `Scope` returns both lists. `MountTable` returns, after `Stop`, every line of the table grouped by device, with each mount's id, parent id, root and mount point, and `Names` on the mount of each kept fd, found by `statx`'s mount id (`mountIDOf`); and whether the table changed while the probe ran, from one `POLLPRI` poll of the kept file at `Stop` (`mountTableChanged`): the kernel raises `POLLPRI | POLLERR` on a mountinfo file once any mount of the namespace was added, removed, moved or remounted since it was opened (**Verified** on kernel 6.17.0 on 2026-10-26 in an unprivileged user namespace, a scratch program). `cmd/watch` writes both into the capture's `fs_scope` (P-33). The mask is `FAN_OPEN | FAN_MODIFY | FAN_CLOSE_WRITE | FAN_CREATE | FAN_DELETE | FAN_MOVED_FROM | FAN_MOVED_TO`. Every fanotify info record carries the filesystem id of its handle (`recordFSID`), and handles are resolved with `open_by_handle_at` on the mount fd of that filesystem, then `readlink` of `/proc/self/fd/N`; a handle from an unmarked filesystem resolves to no path, and so does a directory that has been removed (`isRemovedDir`: a directory with no links), whose handle can still open while something holds it and whose `readlink` then carries a ` (deleted)` mark inside the path. A file reachable by more than one path (a bind mount, or a filesystem mounted twice) gives the same records whichever path a process used: the filesystem id, the directory's handle and the entry's name are those of the file, and nothing says which mount the access went through. Measured on kernel 6.17.0 on 2026-10-18 in an unprivileged user namespace, with a tmpfs, a bind mount of one of its subdirectories and one `FAN_MARK_FILESYSTEM` mark (**Verified**, a scratch program): writes through the bind and through the source each gave their records, with the same filesystem id and the same directory handle. The probe therefore names every file of a filesystem through the one mount fd it keeps for it, the first mount of that filesystem in `markOrder` with `AllFilesystems`, the directory `Config.Path` without it, and `readlink` names the file through that mount whatever path the process used (P-30); `TestObserver_ABindMountAliasIsNamedThroughTheProbesMount` checks it as root, with the workspace given as the alias. An object outside that mount, which a handle reaches when the mount is a bind of a subdirectory, has no name through it, and `readlink` gives `/` for it: a directory and a file opened through a bind of a tmpfs subdirectory and renamed out of it read back as `/` (**Verified** on kernel 6.17.0 on 2026-10-26 in an unprivileged user namespace, a scratch program; P-30 had stated, unverified, a path relative to the filesystem's root). `newKernelResolver` therefore resolves a handle whose `readlink` is `/` to no path unless the object is the process's root directory by device and inode (`isProcessRoot`, P-33); `TestObserver_AFileOutsideTheProbesBindIsNotNamed` checks it as root. A second fanotify group, the rename watch (`openRenameWatch`, P-28), uses `FAN_REPORT_FID` and the mask `FAN_MOVE_SELF | FAN_ONDIR` on the same filesystems with `FAN_MARK_FILESYSTEM`; it reports every move with the moved object's handle and the `FAN_ONDIR` bit for a directory, and its records never become events. It is a group of its own because `FAN_ONDIR` applies to every event of a mark: in the main mark it would add the opens, creations and removals of directories to the capture. Requires `CAP_SYS_ADMIN` in the initial user namespace.

## Workflow

### Reading and resolving

1. `Start` starts `readLoop`, then walks `PathFilter`, or `Path` when there is no filter, and hashes every regular file into `shadowHashes` (by path) and `shadowHashesByInode` (by device and inode), keeping a hash the read loop settled meanwhile. The read loop runs during the walk because each file the walk opens queues a record while the mark is active, and a directory of more files than the kernel queue holds would otherwise overflow it before the run began. Files elsewhere are not hashed, so their opens carry no input hash unless the probe settles a close of them or saw them created (P-22). `Start` also records the time it ran, for the creation rule, and caches every directory the walk passes by the handle `name_to_handle_at` gives it, which is the handle fanotify reports for it (`fillPath`), under the path resolving that handle gives, the name every record of the directory carries, so that a walk through a bind mount does not name a removed directory by another alias than its live records (P-30); the walk's own path is kept only for a handle that does not resolve, and serves only once the directory is gone.
2. `readLoop` polls the fanotify fd and a stop pipe until the quiet window of the earliest pending close ends (`pollTimeout`), so it wakes to judge pending closes even when nothing arrives, and without a timeout when no close is pending: it wakes for a record, a settle deadline or the stop signal, not on a fixed period (P-29; until then it woke every 5 ms). Each wakeup drains every available record (`drainNonBlocking`) and stamps the batch with one `time.Now()` plus one nanosecond per record, so the records keep their kernel order under the verifier's stable sort by timestamp, and a close emitted later, after its settle window, keeps the place of the record that produced it (P-18).
3. `parseEvents` walks the metadata records. `resolveEventPath` prefers a DFID_NAME record (parent directory handle plus name), then a FID record (the object's own handle), then a DFID record (directory only), and resolves a later one only when the earlier ones gave no path (P-29). Only the last case, or no path at all, sets `PathIsAmbiguous`. With the flags above every record carries a DFID_NAME record, so every event names its entry as it was named when the event happened, a content event included; the FID record is the fallback when the directory no longer resolves, and its handle is kept for later inode lookups. Every directory that resolves is recorded in the directory cache (`dirCache`, P-28), a map from the directory's handle (filesystem id, type and bytes) to the path it resolved to, bounded at 8192 entries (`dirCacheSize`) with the least recently used evicted. A DFID_NAME record whose directory the probe resolved before is named from that entry without resolving the handle again (`hit`, P-29), when the rename watch guards its filesystem; the watch is read after the batch is read and before it is parsed, so every directory rename that completed before any event of the batch has dropped its filesystem's entries, and the path is the one resolving would give. The one difference: a directory renamed after the batch was read is named by its path at the event, where resolving would have joined its new path to the entry's old name. An entry the start walk made is not used this way, since the walk's path can be another alias of the directory. A DFID_NAME record whose directory no longer resolves, because the directory was removed before the record was read, takes the directory's path from the cache and joins the entry's name to it; that path is exact and the event is not ambiguous. Before each batch and before each lookup the cache reads the rename watch without blocking, and a directory move on a filesystem drops every entry of that filesystem; an overflow of the watch, a record without a handle or a failed read drops all of them, and a failed read stops further lookups. A rename completes before the directory's removal and its record is queued in the rename watch before the rename returns, so a lookup made after the removal sees every rename that preceded it: a cached path is the directory's path when it was cached, with no directory on its filesystem renamed since. A lookup on a filesystem the rename watch did not mark misses. A DFID_NAME record whose directory neither resolves nor is cached yields no path, never the bare name (`TestParseEvents_DfidNameWithUnresolvedDirectory`). A capture recorded before P-25 has no names, and its directory-entry events resolved through the DFID record, ambiguous.
4. `processRawEvent` sets `overflow` on `FAN_Q_OVERFLOW`, applies `PIDFilter`, counts a record whose path no handle resolved in `UnresolvedPaths` (one per action type, unless the recorder caused it), applies `PathFilter`, strips the probe's own hash-read `FAN_OPEN` (tracked in `pendingHashOpens` by the path `readlink` gives for the file, less the ` (deleted)` mark of a removed file, since the record names the entry by its directory and name), and bumps the path's `pathGeneration` and `lastWriteAt` for any create, modify, close-write or open, and for a record that carries a file handle the file's `handleGeneration`, keyed by `handleKey` (filesystem id, handle type and bytes), which follows the file across renames (P-26).
5. `maskToActionTypes` expands one mask into events in a fixed causal order: `FAN_OPEN` to `file_open`, `FAN_CREATE` or `FAN_MODIFY` to one `file_write`, `FAN_CLOSE_WRITE` to `file_close`, then `FAN_DELETE` to `file_delete` and `FAN_MOVED_FROM` or `FAN_MOVED_TO` to `file_rename`. The kernel merges events on one object (one directory and name) into a single mask that has no order; emitting open, write, close in that order makes a merged notification and the same operations delivered separately produce the same sequence (commit 81b3c4d). The verifier aligns by position, so a fixed order matters. A rename is therefore two `file_rename` events, the source's from its moved-from record and the destination's from its moved-to record, in the kernel's order (P-25), except a source merged into a creation's record, which step 7 holds for its place; a record with both bits on one name is one event.
6. Before emission, `repeats` drops a `file_write` that follows a `file_write`, or a `file_rename` that follows a `file_rename`, on the same path by the same pid with no other event on the path between (`lastEmitted`). The kernel merges notifications on one object into one mask when nothing reads between them and delivers them apart otherwise, so a truncating open plus its write, or two renames onto one name, reached the verifier as one event or two depending on timing; now it is one either way (P-18). The two halves of one rename name two paths and are both emitted; a file renamed away and back is one event per name, merged or not (`TestProcessRawEvent_NamedRenames`). Any other event on the path, or another process's event, resets the path, so two writes separated by a close are two events.
7. A removal merged into a creation's record is held for its place (P-27). The kernel queues a record at its first event and merges later events of the same process on the same name into it while it is unread, so a file created, written and renamed or deleted before the read gives `FAN_CREATE | FAN_MOVED_FROM` (or `FAN_CREATE | FAN_DELETE`) on its name, then the file's content record, then the moved-to record on the destination: the removal happened after the content record's events, at the moved-to's place. `holdRemoval` picks out those two masks, and the record emits its `file_write` in place while its `file_rename` or `file_delete` waits in `held`. `placeHeld` emits a held moved-from just before the next moved-to record of the same process, unless a moved-from that was emitted in place is still waiting for that moved-to (`fromsInFlight`), and a held delete before any record except a content record on its name whose file has left that name (`stillNamed`: the record's handle resolves elsewhere or not at all; a file still there was created again after the delete). A released removal takes the timestamp of the record it precedes, so it sorts before that record's events and after the content record's deferred close. What is still held when a drain empties the queue, at `Stop` and at the final flush, is emitted one nanosecond after the last record (`releaseHeld`).
8. When `Stop` is signalled, `readLoop` first reads the records the kernel still holds (`drainAtStop`, P-24): it processes them like any other batch for at most `stopDrainBudget` (2 s), then reads what is left for at most 250 ms more (`stopCountBudget`) without processing it and counts it in `UndrainedRecords` (`countRecords`). The count leaves out the observer's own records and those `PIDFilter` excludes, and sets `overflow` on an overflow record. Then it resolves the pending closes (step 4 of Hashes below).
9. Every event carries `PID` from the fanotify metadata (0 when the kernel caused it). There is no tracked-set filter: `PIDFilter` matches one exact pid and does not follow children. A fanotify event is read some time after the access, a short-lived child has often left any tracked set by then, and a filter consulting the set would drop that child's events with nothing counting the loss. Attribution is the verifier's job (`pkg/verification.Forest.Attribute`).

### Hashes

A `file_open` gets an `InputHash` only when the probe measured the file's content (`inputHash`, P-22). `identify` opens the file through its handle (by path for a record without one) and reads its device, inode and birth time with one `statx`; what a handle named is remembered by its `handleKey`, so a file opened again, the shared libraries of every command among them, costs no system call (P-29; bounded at 16384 handles, then started over). The hash is the settled hash for the file's device and inode first (it survives a rename, and after an atomic replace it is the new file's while the path still remembers the replaced one, P-20), else the last settled hash for the path, else, for the first open of a file whose birth time (`statx`) is at or after `Start`, the SHA-256 of empty content, since that open created it. Any other open carries no input hash: a pre-existing file outside the walked directory, a later open of a born-here file the probe never settled, and any file on a filesystem that reports no birth time.

A `file_close` goes through a settle protocol so its `OutputHash` is the content the close described and not a state a later write left behind:

1. `registerClose` makes the close the pending one for its path, records the path's write generation (`pendingClose.gen`, taken after the close's own event bumped it) and the file's handle generation, and opens an `O_PATH` fd from its handle. If a close was already pending for that path, the older one is emitted at once with no `OutputHash`, because a newer close proves it was not final.
2. `resolveSettled` runs after every wakeup. It hashes a pending close only if it is still the current entry for its path, the path has had no write-class event for `settleQuietWindow` (20 ms), and both generations are still the ones recorded at registration. A write-class event after the close, an open included, under the close's name or any other name of the file, means the content the close described may be gone, so the close is published with no `OutputHash` and no read is made (P-16, P-26).
3. `hashSettledFD` snapshots both generations, then asks whether the process that closed the file still holds it open for writing (`openForWriteBy`: a descriptor in `/proc/<pid>/fd` naming the file whose `fdinfo` flags are not read-only). The kernel merges that process's next open and truncation into the close's record while it is unread, so no later record shows a rewrite that has begun; a process still holding the file is the trace of one that has not finished, and the close is published with no `OutputHash` and no read. So is a close whose process the probe cannot ask (pid 0, a table it may not read); a process that has exited holds nothing (P-26). Otherwise it reads the content through the `O_PATH` fd, drains the fanotify queue without blocking, and compares the generations again. A write that completed during the read has its notification already queued, so a changed generation means the read is not trusted and no `OutputHash` is attached (time-of-check to time-of-use protection); so does a drain that returned on the stop pipe with records still queued. A trusted digest updates both shadow maps.
4. On `Stop`, `flushPendingCloses` resolves every remaining close without the quiet check, since no further write can be observed.

`FileClose` events therefore leave the probe later than the events around them; `cmd/watch` sorts all events by timestamp before writing.

### Cost

Per record the probe resolves the directory's handle unless it resolved that directory before, and the file's own handle only when the directory gave no path (step 3 of Reading and resolving); per open it identifies a file once per handle; it calls `getpid` once, at `New`; and the read loop sleeps until a record, a settle deadline or the stop signal (P-29). `BenchmarkObserver_ShellLoop` measures this without root: it runs the shell workload of `scripts/bench-overhead.sh`, without its TCP connection, under the whole observer on an inode-marked fanotify group, with the workload's commands and libraries copied into a marked directory so their loads are seen, and it opens handles by path, which costs a path lookup and a `name_to_handle_at` where the probe pays one `open_by_handle_at`. An unprivileged group reads pid 0 for another process's event, so the rig asks the writer check about the shell. It reports the benchmark process's CPU per workload iteration. `BenchmarkProcessRecords` replays synthetic records of the same shape through `parseEvents` and `processRawEvent` and counts handle resolutions and opens per record. Hashing is not where the time goes in that workload: nearly every close is read by another process within the settle window and is published without a hash (P-26).

## Guarantees and loss accounting

Paths are resolved by the kernel from file handles, not read from user memory. The probe sees every writer on the marked filesystem, whichever process tree it belongs to, and records the causing PID. A published `OutputHash` is computed only after the path has been quiet for the settle window, the closing process has stopped writing the file, and the read survived the generation checks; it is the content of the file at a close, the close's own or a later close by the same process merged into its record, and when the probe cannot vouch for it, the hash is absent rather than stale (P-16, P-26). `TestObserver_MergedTruncatingOpenDropsTheHash` feeds the settle code the merged record of a close and a later truncating open with the file in that state, which published the empty file's hash before P-26; `TestKernelMergesATruncatingOpenIntoTheUnreadClose` checks that the kernel merges that way, without root; `TestObserver_StalledRewriteNeverPublishesAnIntermediateHash` and `TestTier4_E2E_RacedRewriteDropsStaleHash` (200 iterations) drive the whole probe as root in CI.

The emitted sequence does not depend on whether the kernel merged notifications or on when a close settled: a repeated write or rename on one path by one process is one event (`TestProcessRawEvent_RepeatedWritesAndRenamesCollapse`), and a record's timestamp is its position in its batch (`TestDrainNonBlocking_StampsRecordsByBatchPosition`, P-18). A removal the kernel merged into a creation's record, ahead of the file's open, write and close, is emitted at the place of the rename's moved-to, or after the content record of a deleted file (P-27): `TestKernelMergedRemovalsComeOutInOrder` reads real records of operations read late, without root, and checks that the probe emits them in the order they ran. What merging removes is still gone; it is under Known limits. A real capture of a two-write shell agent, `cmd/verify/testdata/p5`, checks it end to end: each file's close sits before the next file's open, the honest trajectory verifies FAITHFUL, and one that leaves out the second write has exactly that file's three events unrecorded (`TestP5CloseOrderDemo`).

The probe never drops on its own channel: `processRawEvent` and the settle code send with a blocking send. A slow consumer stalls the read loop, the kernel queue fills, and a full kernel queue produces `FAN_Q_OVERFLOW`, which `QueueOverflow` reports, so back-pressure makes a run INCONCLUSIVE rather than silently short. The kernel side was measured on kernel 6.17.0 on 2026-10-14 with an unprivileged inode mark and no reader (**Verified**, a scratch program): 20000 file creations left 16385 records, the default limit of 16384 (`/proc/sys/fs/fanotify/max_queued_events`) plus one overflow record at the end. `TestObserver_SlowConsumerMakesTheCaptureIncomplete` drives the observer itself with a consumer that reads nothing during such a burst and logs the kernel version and what was lost; it needs root and runs in CI. A backlog still queued at `Stop`, the overflow record included, is read or counted by the stop drain (P-24). The time the read loop spends blocked is not measured. `CaptureCoverage` reports `Ran: true`, `QueueOverflow` and `UndrainedRecords` (event loss), `HashlessCloses`, the closes published without a hash (a content gap: the events are there, their content is not vouched for), and `UnresolvedPaths` (a note, V-35), the records that neither a handle nor the directory cache named. `DirCache` reports, after `Stop`, whether the rename watch marked anything (`Watching`), how many records the cache named from an entry the probe resolved (`Hits`, P-29, a removed directory's included) and from an entry of the start walk after the handle did not resolve (`Resolved`), how many entries it evicted and how many a rename or a loss of the watch dropped; these are not in the coverage record. Every unresolved delete in the first Claude Code and agy captures with names (2026-10-17) was in a directory an earlier record had resolved (**Verified** by reading the capture logs against the directories still on disk; the captures are private), the shape `TestKernelDeleteInARemovedDirectoryIsNamedFromTheCache` reads from a real kernel without root; `TestObserver_DeleteInADirectoryRemovedAfterItWasSeenIsNamed` and `TestObserver_RenamedThenRemovedDirectoryIsNotNamedByItsOldPath` drive the whole probe as root in CI, and `TestDirCache_TheStartWalkCachesTheResolvedName` checks, without root, that the walk caches a directory under its resolved name. The mount table's parser, the marking order and the grouping are checked without root (`TestParseMountTable`, `TestMarkOrder_WholeFilesystemMountsFirst`, `TestBuildMountTable_GroupsByFilesystem`), and so are the table this process reads, whose mount of `/` carries the mount id `statx` gives for `/`, and the poll (`TestReadMountTable_FindsTheRootMount`). How `Assess` reads each is in [10_probes_common.md](10_probes_common.md#probecoverage), and how the verifier treats a claim on a hashless close in [20_verifier.md](20_verifier.md#content-comparison-and-the-three-valued-nil). All other `ProbeCoverage` counters are zero for this probe.

## Known limits

- The `OutputHash` is computed in userspace after the close, so a write that lands between the close and the read, outside the generation check's window, can still make the hash describe later content. The probe errs towards publishing no hash: any open of the file after the close drops it, including a plain read, so a file read within the settle window of being written is published without a hash. When the kernel merged a later rewrite by the same process into the close's record and that rewrite has finished, the hash is the later close's content, attached to the earlier close (P-26).
- The writer check reads the closing process's descriptor table (P-26). A writing descriptor passed to another process, or held in a thread with a descriptor table of its own, is not seen. A process that keeps the file open for writing through another descriptor while it closes one gets no hash on those closes, and each settled close costs a `stat` per descriptor of its process.
- Only the directory walked at `Start` is hashed in advance (P-17). An open of any other file the probe has not settled carries no input hash, so a claimed `input_hash` on it is unverified and the run INCONCLUSIVE (P-22, V-29), never confirmed. The creating open of a born-here file is recognised by its birth time; on a filesystem without one it carries no input hash either, and a file deleted before its open event is read cannot be identified and carries none.
- Writes through a shared `mmap` do not raise `FAN_MODIFY`.
- `Stop` waits for the read loop, which blocks while the events channel is full, so a caller must keep reading `Events` until it is closed; one that stops reading first makes `Stop` hang.
- The stop drain reads for at most 2 s. A process that keeps writing after `Stop` (an agent that outlives a `--root-pid` recording) can keep the queue from emptying, and its records are then counted in `UndrainedRecords`, which makes the run INCONCLUSIVE although they may postdate the recording. The count is a lower bound (it stops after 250 ms) and does not apply `PathFilter`, which needs the path resolved, so it can count a record the filter would have dropped.
- `FAN_ACCESS` and `FAN_CLOSE_NOWRITE` are not in the mask, so reads are invisible beyond the open and the probe never emits `file_read`.
- Attribute and permission changes are not watched.
- Without `AllFilesystems`, only the filesystem containing `Config.Path` is marked, so activity on tmpfs `/tmp` or any other mount is invisible. With it, fuse mounts, read-only images and any filesystem that refused the mark are still invisible; the capture's `fs_scope` lists them.
- `PathFilter` is a plain string prefix, so `/work` also admits `/workspace2`. `cmd/watch` no longer uses it; its own workspace test is directory-bounded.
- `FAN_REPORT_NAME` needs kernel 5.9 or later (**Reported**, `fanotify_init(2)`); an older kernel refuses the flag set at `fanotify_init`.
- A rename is two `file_rename` events, the source and the destination, with nothing linking them: the probe does not say which source went to which destination, and the verifier pairs each with a claim of its own. Two renames onto one name by one process with nothing on that name between are one event of the destination, whether or not the kernel merged them (P-18).
- No `FAN_ONDIR` is in the main mask, so creating, removing and renaming a directory give no event; the files moved or removed with it give none either. The rename watch sees directory moves but only to invalidate the directory cache (P-28).
- An event names its entry as it was named when the event happened, not where the file is when the record is read; a file renamed between its open and the read of that record is named by its old name, while the inode-keyed hash lookup still finds its content (P-20).
- A delete inside a tree being removed can arrive after its parent directory is gone, and then no handle resolves. The directory cache names it when an earlier record, or the start walk, resolved that directory and no directory on its filesystem was renamed since (P-28). Otherwise the event has an empty target: a directory created and removed with its files before any of their records was read (an `rm -rf` of a tree made outside the walked directory before the capture and never touched during it), one evicted from the cache, one on a filesystem the rename watch could not mark, and any directory removed after a directory rename on its filesystem, by any process, invalidated the cache. `cmd/watch` counts those in `fs_scope.unresolved` and leaves them out of the capture; the probe counts them in `UnresolvedPaths`, which `Assess` reads as a note, not as event loss (V-35). The count covers every process, not only the agent's tree.
- A file reached through a bind mount, or any second mount of its filesystem, is named through the mount the probe resolves that filesystem's handles with, not through the path the process used (P-30). A claim naming the file through another alias does not match its event by path; the capture records the mount table so that matching can trace the alias (P-33, O-31). `cmd/watch`'s scope rule, which keeps other processes' events under the workspace path, misses those named through another alias.
- When the probe's mount for a filesystem is a bind of a subdirectory (the namespace has no mount of the whole filesystem, or, without `AllFilesystems`, `Config.Path`'s mount is such a bind), a file outside that subdirectory, reachable through a mount the probe did not keep or from another mount namespace, has no name: its records are unresolved and counted, or named from the directory cache (P-33).
- The mount table is the probe's namespace when `New` ran. An agent in another mount namespace (a sandbox) names files by a table the capture does not hold, and a change there is not detected. `mount_table_changed` says only that some mount of the probe's namespace changed, by any process, not which; mount ids are not stable across such a change. A capture without a readable mountinfo has no table.
- The directory cache trusts that a directory's handle names that directory only: a filesystem that reuses a handle for a new directory (one without generation numbers; ext4, xfs, btrfs and tmpfs have them) could name a removed new directory by the old one's path. The cache does not watch mount changes; the probe only records whether the table changed (P-33). The cache's counters are reported by `DirCache` only, not in the coverage record.
- Two writes through one open descriptor with no other event on the path between them are one `file_write`: the collapse that makes the count stable cannot tell a second write from the unmerged half of the first.
- Timestamps are taken at userspace read time, plus the record's position in its batch, and are not comparable in order with proc or net timestamps.
- The startup walk opens every file under the walked directory while the mark is active; the probe reports those opens with the recorder's own PID, and `cmd/watch` drops them with every other file event of its own pid. The read loop runs during the walk, so when the agent already runs (`--root-pid`) an open it makes before the walk has hashed the file carries no input hash. The walk's read is not settled: a file the agent is writing while the walk reads it can keep a partial hash as its input hash until a close of it settles with one.
- The kernel merges a directory-entry record into an earlier unread record for the same directory, name and process even when records for other files lie between them, which put a rename's source before the open, write and close of the file it renamed until P-27 held it for its place. Measured on kernel 6.17.0 on 2026-10-15 with an unprivileged inode mark (**Verified**, `TestKernelMergedRemovalsComeOutInOrder`). What merging removes stays removed, and the emitted sequence then still depends on when the records were read: a moved-to merged into an earlier unread one of the same name disappears as an event of its own (two replaces of one target read late give one destination), and its held source is emitted at the end of the drain, after records that may postdate it; a creation merged into an earlier record of its name (a name renamed away and created again) gives no `file_write`; a record with both rename bits on one name is one event. A held moved-from is placed by the next moved-to of its process, so a rename whose source was merged away with no creation (a name renamed onto and then away again) can take another rename's place. A capture made before P-27 has the old order, which the Claude Code adapter accepts (I-56).
- `pathGeneration`, `lastWriteAt` and the shadow hash maps grow for the observer's whole life; the handles `identify` remembers are bounded.
- A file deleted after `identify` remembered its handle is still identified, by the inode the handle named, so its open looks up that inode's settled hash; before P-29 the handle no longer resolved and only the path's hash was looked up.
- The read loop wakes for every batch of records, often one or two records long when commands run in sequence, and much of the probe's remaining CPU is the wakeup and the Go scheduler's handoff of each event to the consumer. Reading later, to gather more records per wakeup, would cost less but let the kernel merge more records while they are unread, which the merging limits above depend on; that trade is not decided (P-29).
- PID reuse among short-lived processes is resolved by time in the verifier, which is a heuristic.
