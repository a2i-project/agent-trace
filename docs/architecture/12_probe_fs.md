# Filesystem probe

Checked against commit 984d9ef on 2026-10-14.

## Objective

The filesystem probe (`pkg/probe/fs`) records file opens, writes, closes, creations, deletions and renames on the filesystem that holds the workspace, or on every real filesystem mounted on the host, with the PID that caused each one and a content hash for files that were written and closed. The common contract, clocks and coverage format are in [10_probes_common.md](10_probes_common.md).

## Structure

| File | Contents |
|---|---|
| `fanotify.go` | `initFanotify`, `markFilesystem`, `markAll`, `parseMountInfo`, `openMountFD`, `newKernelResolver`, and the pure parser `parseEvents`, `resolveEventPath`, `parseDfidName`, `extractFID`, `recordFSID` |
| `observer.go` | `Config`, `Observer`, `New`, `markOne`, `Scope`, `Start`, `Stop`, `readLoop`, `drainAtStop`, `countRecords`, `drainNonBlocking`, `processRawEvent`, `registerClose`, `resolveSettled`, `hashSettledFD`, `lookupShadowHash`, `maskToActionTypes` |
| `pkg/content/hash.go` | `SHA256File`, `SHA256FD`, `SHA256Bytes`; digests are written as `sha256:<hex>` |

`Config` fields: `Path` (required; selects the filesystem, and the directory hashed at `Start`), `AllFilesystems` (mark every real filesystem on the host, P-17), `PathFilter` (string prefix on the resolved path), `PIDFilter` (exact pid, test use), `EventBufSize` (default 4096). `New` makes `Path` and `PathFilter` absolute, since events carry absolute paths. `cmd/watch` sets `Path` to `--workspace` and `AllFilesystems`, with no `PathFilter`: the agent's file claims may name any path, so the probe filters nothing and `watch` applies the scope rule once the process tree is known ([10_probes_common.md](10_probes_common.md#how-cmdwatch-builds-and-starts-probes)).

## Technologies

fanotify through `golang.org/x/sys/unix`, in notification class (`FAN_CLASS_NOTIF`) with `reportFlags`, `FAN_REPORT_FID | FAN_REPORT_DFID_NAME` (`0xe00`, the constants of `x/sys/unix`), so the kernel reports file handles and entry names instead of open file descriptors (P-25). Until P-25 the probe requested `0x2400`, `FAN_REPORT_DIR_FID | FAN_REPORT_FD_ERROR`, meant as `FAN_REPORT_DFID_NAME`: no entry name, so a create, delete or rename named only its directory and was ambiguous, and the `FD_ERROR` bit exists only from kernel 6.13; every checked-in capture was recorded that way. Measured on kernel 6.17.0 on 2026-10-14 with an unprivileged inode mark on directories in tmpfs and in ext4, which gave the same records (**Verified**, a scratch program that dumps the info records and resolves each handle by `name_to_handle_at` of the paths that exist when the record is read; `TestKernelNamesEveryDirectoryEntryRecord` repeats the core of it in the suite, without root): every create, delete, moved-from and moved-to record carries one DFID_NAME record (the directory's handle and the entry's name) and no FID record; every open, modify and close-write record carries a DFID_NAME record and a FID record (the file's own handle); no record carried a directory handle without a name. The name is the entry's name when the event happened: a temporary's close read after its rename still names the temporary, while its FID record resolves to the new name. A rename gives a moved-from record naming the source and a moved-to record naming the destination, with nothing linking them. Only records of one process on one directory and one name merge: a temporary created and renamed away before the read gives one `FAN_CREATE | FAN_MOVED_FROM` record on its name, ahead of its `FAN_OPEN | FAN_MODIFY | FAN_CLOSE_WRITE` record, and the moved-to record on the target after both; a file renamed away and back gives one `FAN_MOVED_FROM | FAN_MOVED_TO` record per name; two replaces of one target read in one late batch give one moved-to record. The probe's filesystem-wide mark needs root, so the same shapes under it rest on the privileged tests (`TestObserver_AReplaceThroughATemporaryIsNamed`, which logs the sequence it saw, and the delete and rename tests), which run in CI. The mark is `FAN_MARK_ADD | FAN_MARK_FILESYSTEM` on `Config.Path`, which covers every mount of the filesystem containing that path. With `AllFilesystems`, `markAll` reads `/proc/self/mountinfo`, skips pseudo filesystems, read-only images and fuse mounts (`pseudoFSTypes`), and marks each remaining filesystem once, by its `statfs` id, keeping one mount fd per id; a filesystem it cannot mark or open is recorded and skipped, and `Scope` returns both lists. The mask is `FAN_OPEN | FAN_MODIFY | FAN_CLOSE_WRITE | FAN_CREATE | FAN_DELETE | FAN_MOVED_FROM | FAN_MOVED_TO`. Every fanotify info record carries the filesystem id of its handle (`recordFSID`), and handles are resolved with `open_by_handle_at` on the mount fd of that filesystem, then `readlink` of `/proc/self/fd/N`; a handle from an unmarked filesystem resolves to no path. Requires `CAP_SYS_ADMIN` in the initial user namespace.

## Workflow

### Reading and resolving

1. `Start` starts `readLoop`, then walks `PathFilter`, or `Path` when there is no filter, and hashes every regular file into `shadowHashes` (by path) and `shadowHashesByInode` (by device and inode), keeping a hash the read loop settled meanwhile. The read loop runs during the walk because each file the walk opens queues a record while the mark is active, and a directory of more files than the kernel queue holds would otherwise overflow it before the run began. Files elsewhere are not hashed, so their opens carry no input hash unless the probe settles a close of them or saw them created (P-22). `Start` also records the time it ran, for the creation rule.
2. `readLoop` polls the fanotify fd and a stop pipe with a 5 ms timeout (`settlePollMs`), so it wakes to judge pending closes even when nothing arrives. Each wakeup drains every available record (`drainNonBlocking`) and stamps the batch with one `time.Now()` plus one nanosecond per record, so the records keep their kernel order under the verifier's stable sort by timestamp, and a close emitted later, after its settle window, keeps the place of the record that produced it (P-18).
3. `parseEvents` walks the metadata records. `resolveEventPath` prefers a DFID_NAME record (parent directory handle plus name), then a FID record (the object's own handle), then a DFID record (directory only). Only the last case, or no path at all, sets `PathIsAmbiguous`. With the flags above every record carries a DFID_NAME record, so every event names its entry as it was named when the event happened, a content event included; the FID record is the fallback when the directory no longer resolves, and its handle is kept for later inode lookups. A DFID_NAME record whose directory does not resolve yields no path, never the bare name (`TestParseEvents_DfidNameWithUnresolvedDirectory`). A capture recorded before P-25 has no names, and its directory-entry events resolved through the DFID record, ambiguous.
4. `processRawEvent` sets `overflow` on `FAN_Q_OVERFLOW`, applies `PIDFilter`, counts a record whose path no handle resolved in `UnresolvedPaths` (one per action type, unless the recorder caused it), applies `PathFilter`, strips the probe's own hash-read `FAN_OPEN` (tracked in `pendingHashOpens` by the path `readlink` gives for the file, less the ` (deleted)` mark of a removed file, since the record names the entry by its directory and name), and bumps the path's `pathGeneration` and `lastWriteAt` for any create, modify, close-write or open.
5. `maskToActionTypes` expands one mask into events in a fixed causal order: `FAN_OPEN` to `file_open`, `FAN_CREATE` or `FAN_MODIFY` to one `file_write`, `FAN_CLOSE_WRITE` to `file_close`, then `FAN_DELETE` to `file_delete` and `FAN_MOVED_FROM` or `FAN_MOVED_TO` to `file_rename`. The kernel merges events on one object (one directory and name) into a single mask that has no order; emitting open, write, close in that order makes a merged notification and the same operations delivered separately produce the same sequence (commit 81b3c4d). The verifier aligns by position, so a fixed order matters. A rename is therefore two `file_rename` events, the source's from its moved-from record and the destination's from its moved-to record, in the kernel's order (P-25); a record with both bits on one name is one event.
6. Before emission, `repeats` drops a `file_write` that follows a `file_write`, or a `file_rename` that follows a `file_rename`, on the same path by the same pid with no other event on the path between (`lastEmitted`). The kernel merges notifications on one object into one mask when nothing reads between them and delivers them apart otherwise, so a truncating open plus its write, or two renames onto one name, reached the verifier as one event or two depending on timing; now it is one either way (P-18). The two halves of one rename name two paths and are both emitted; a file renamed away and back is one event per name, merged or not (`TestProcessRawEvent_NamedRenames`). Any other event on the path, or another process's event, resets the path, so two writes separated by a close are two events.
7. When `Stop` is signalled, `readLoop` first reads the records the kernel still holds (`drainAtStop`, P-24): it processes them like any other batch for at most `stopDrainBudget` (2 s), then reads what is left for at most 250 ms more (`stopCountBudget`) without processing it and counts it in `UndrainedRecords` (`countRecords`). The count leaves out the observer's own records and those `PIDFilter` excludes, and sets `overflow` on an overflow record. Then it resolves the pending closes (step 4 of Hashes below).
8. Every event carries `PID` from the fanotify metadata (0 when the kernel caused it). There is no tracked-set filter: `PIDFilter` matches one exact pid and does not follow children. A fanotify event is read some time after the access, a short-lived child has often left any tracked set by then, and a filter consulting the set would drop that child's events with nothing counting the loss. Attribution is the verifier's job (`pkg/verification.Forest.Attribute`).

### Hashes

A `file_open` gets an `InputHash` only when the probe measured the file's content (`inputHash`, P-22): the settled hash for the file's device and inode first (it survives a rename, and after an atomic replace it is the new file's while the path still remembers the replaced one, P-20), else the last settled hash for the path, else, for the first open of a file whose birth time (`statx`) is at or after `Start`, the SHA-256 of empty content, since that open created it. Any other open carries no input hash: a pre-existing file outside the walked directory, a later open of a born-here file the probe never settled, and any file on a filesystem that reports no birth time.

A `file_close` goes through a settle protocol so its `OutputHash` is the content the close described and not a state a later write left behind:

1. `registerClose` makes the close the pending one for its path, records the path's write generation (`pendingClose.gen`, taken after the close's own event bumped it) and opens an `O_PATH` fd from its handle. If a close was already pending for that path, the older one is emitted at once with no `OutputHash`, because a newer close proves it was not final.
2. `resolveSettled` runs after every wakeup. It hashes a pending close only if it is still the current entry for its path, the path has had no write-class event for `settleQuietWindow` (20 ms), and the path's generation is still the one recorded at registration. A write-class event after the close, an open included, means the content the close described may be gone, so the close is published with no `OutputHash` and no read is made (P-16).
3. `hashSettledFD` snapshots the path's generation, reads the content through the `O_PATH` fd, drains the fanotify queue without blocking, and compares the generation again. A write that completed during the read has its notification already queued, so a changed generation means the read is not trusted and no `OutputHash` is attached (time-of-check to time-of-use protection). A trusted digest updates both shadow maps.
4. On `Stop`, `flushPendingCloses` resolves every remaining close without the quiet check, since no further write can be observed.

`FileClose` events therefore leave the probe later than the events around them; `cmd/watch` sorts all events by timestamp before writing.

## Guarantees and loss accounting

Paths are resolved by the kernel from file handles, not read from user memory. The probe sees every writer on the marked filesystem, whichever process tree it belongs to, and records the causing PID. A published `OutputHash` is computed only after the path has been quiet for the settle window and survived the generation check; when the probe cannot vouch for it, the hash is absent rather than stale.

The emitted sequence does not depend on whether the kernel merged notifications or on when a close settled: a repeated write or rename on one path by one process is one event (`TestProcessRawEvent_RepeatedWritesAndRenamesCollapse`), and a record's timestamp is its position in its batch (`TestDrainNonBlocking_StampsRecordsByBatchPosition`, P-18). One kind of merge escapes this; it is under Known limits. A real capture of a two-write shell agent, `cmd/verify/testdata/p5`, checks it end to end: each file's close sits before the next file's open, the honest trajectory verifies FAITHFUL, and one that leaves out the second write has exactly that file's three events unrecorded (`TestP5CloseOrderDemo`).

The probe never drops on its own channel: `processRawEvent` and the settle code send with a blocking send. A slow consumer stalls the read loop, the kernel queue fills, and a full kernel queue produces `FAN_Q_OVERFLOW`, which `QueueOverflow` reports, so back-pressure makes a run INCONCLUSIVE rather than silently short. The kernel side was measured on kernel 6.17.0 on 2026-10-14 with an unprivileged inode mark and no reader (**Verified**, a scratch program): 20000 file creations left 16385 records, the default limit of 16384 (`/proc/sys/fs/fanotify/max_queued_events`) plus one overflow record at the end. `TestObserver_SlowConsumerMakesTheCaptureIncomplete` drives the observer itself with a consumer that reads nothing during such a burst and logs the kernel version and what was lost; it needs root and runs in CI. A backlog still queued at `Stop`, the overflow record included, is read or counted by the stop drain (P-24). The time the read loop spends blocked is not measured. `CaptureCoverage` reports `Ran: true`, `QueueOverflow` and `UndrainedRecords` (event loss), `HashlessCloses`, the closes published without a hash (a content gap: the events are there, their content is not vouched for), and `UnresolvedPaths` (a note, V-35). How `Assess` reads each is in [10_probes_common.md](10_probes_common.md#probecoverage), and how the verifier treats a claim on a hashless close in [20_verifier.md](20_verifier.md#content-comparison-and-the-three-valued-nil). All other `ProbeCoverage` counters are zero for this probe.

## Known limits

- The `OutputHash` is computed in userspace after the close, so a write that lands between the close and the read, outside the generation check's window, can still make the hash describe later content. The probe errs towards publishing no hash: any open of the path after the close drops it, including a plain read, so a file read within the settle window of being written is published without a hash.
- Only the directory walked at `Start` is hashed in advance (P-17). An open of any other file the probe has not settled carries no input hash, so a claimed `input_hash` on it is unverified and the run INCONCLUSIVE (P-22, V-29), never confirmed. The creating open of a born-here file is recognised by its birth time; on a filesystem without one it carries no input hash either, and a file deleted before its open event is read cannot be identified and carries none.
- Writes through a shared `mmap` do not raise `FAN_MODIFY`.
- `Stop` waits for the read loop, which blocks while the events channel is full, so a caller must keep reading `Events` until it is closed; one that stops reading first makes `Stop` hang.
- The stop drain reads for at most 2 s. A process that keeps writing after `Stop` (an agent that outlives a `--root-pid` recording) can keep the queue from emptying, and its records are then counted in `UndrainedRecords`, which makes the run INCONCLUSIVE although they may postdate the recording. The count is a lower bound (it stops after 250 ms) and does not apply `PathFilter`, which needs the path resolved, so it can count a record the filter would have dropped.
- `FAN_ACCESS` and `FAN_CLOSE_NOWRITE` are not in the mask, so reads are invisible beyond the open and the probe never emits `file_read`.
- Attribute and permission changes are not watched.
- Without `AllFilesystems`, only the filesystem containing `Config.Path` is marked, so activity on tmpfs `/tmp` or any other mount is invisible. With it, fuse mounts, read-only images and any filesystem that refused the mark are still invisible; the capture's `fs_scope` lists them.
- `PathFilter` is a plain string prefix, so `/work` also admits `/workspace2`. `cmd/watch` no longer uses it; its own workspace test is directory-bounded.
- `FAN_REPORT_NAME` needs kernel 5.9 or later (**Reported**, `fanotify_init(2)`); an older kernel refuses the flag set at `fanotify_init`.
- A rename is two `file_rename` events, the source and the destination, with nothing linking them: the probe does not say which source went to which destination, and the verifier pairs each with a claim of its own. Two renames onto one name by one process with nothing on that name between are one event of the destination, whether or not the kernel merged them (P-18).
- No `FAN_ONDIR` is in the mask, so creating, removing and renaming a directory give no record; the files moved or removed with it give none either.
- An event names its entry as it was named when the event happened, not where the file is when the record is read; a file renamed between its open and the read of that record is named by its old name, while the inode-keyed hash lookup still finds its content (P-20).
- A delete inside a tree being removed can arrive after its parent directory is gone, and then no handle resolves: the event has an empty target. Names do not help, since the directory's handle is what the name is joined to (P-25). `cmd/watch` counts those in `fs_scope.unresolved` and leaves them out of the capture; the probe counts them in `UnresolvedPaths`, which `Assess` reads as a note, not as event loss (V-35). The count covers every process, not only the agent's tree.
- Two writes through one open descriptor with no other event on the path between them are one `file_write`: the collapse that makes the count stable cannot tell a second write from the unmerged half of the first.
- Timestamps are taken at userspace read time, plus the record's position in its batch, and are not comparable in order with proc or net timestamps.
- The startup walk opens every file under the walked directory while the mark is active; the probe reports those opens with the recorder's own PID, and `cmd/watch` drops them with every other file event of its own pid. The read loop runs during the walk, so when the agent already runs (`--root-pid`) an open it makes before the walk has hashed the file carries no input hash.
- The kernel merges a directory-entry record into an earlier unread record for the same directory, name and process even when records for other files lie between them. Measured on kernel 6.17.0 on 2026-10-14 with an unprivileged inode mark (**Verified**, a scratch program): with the flags before P-25, writing `file1` and renaming it to `file2` in one directory, read afterwards, gave the directory's `FAN_CREATE | FAN_MOVED_FROM | FAN_MOVED_TO` ahead of the file's `FAN_OPEN | FAN_MODIFY | FAN_CLOSE_WRITE`; with names it gives `FAN_CREATE | FAN_MOVED_FROM` on `file1`, then the content record on `file1`, then `FAN_MOVED_TO` on `file2`. When the read loop falls behind, the probe therefore still emits the rename's source before the open, write and close of the file it renamed, all naming `file1`, and the destination after them. The sequence then depends on merging, against P-18; the Claude Code adapter takes both orders for a replace through a temporary (I-56), and any other honest run in that order can read as NOT FAITHFUL. A destination merged into an earlier unread one of the same name disappears as an event of its own.
- `pathGeneration`, `lastWriteAt` and the shadow hash maps grow for the observer's whole life.
- PID reuse among short-lived processes is resolved by time in the verifier, which is a heuristic.
