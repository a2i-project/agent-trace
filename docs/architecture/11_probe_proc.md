# Process probe

Checked against commit d223e7d on 2026-10-28.

## Objective

The process probe (`pkg/probe/proc`) records which programs the agent's process tree ran, how they exited, and which process created which. It produces `process_exec`, `process_exit` and `process_fork` events carrying `PID` and `PPID`, so the verifier can rebuild the process forest from events alone and attribute every other probe's events through it. An exec event also carries the working directory of the attempt and, when the exec took effect, the kernel's record of what it ran (P-36). The common contract, clocks and coverage format are in [10_probes_common.md](10_probes_common.md).

## Structure

| File | Contents |
|---|---|
| `proc.bpf.c` | seven programs, all raw tracepoints (P-32): `handle_fork` (`task_newtask`), `trace_sys_enter` (`sys_enter`, the syscall dispatcher, which handles `exit_group` itself), `handle_execve` and `handle_execveat` (tail-called by the dispatcher, both through `record_exec`), `handle_exec_cwd` (tail-called by both, adds the working directory, P-36), `handle_exec_ok` (`sched_process_exec`), `handle_exit` (`sched_process_exit`); `walk_path`, the path walk `handle_exec_cwd` and `handle_exec_ok` share, one `walk_step` per `bpf_loop` iteration |
| `observer.go` | `Config`, `Observer`, `New`, `procRawTracepoints`, `sysEnterPrograms`, `Start`, `Stop`, `drainRead`, `SetRootPID`, `CaptureCoverage`, `readLoop`, `execImage`, `joiner`, `commandLine` |
| `postexec.go` | `walkedPath` (a walked path to a string), `filenameChanged`, `holder` (exec events wait for their outcome, P-36) |
| `diagnostics.go` | `ringMeter` (the ring's high-water mark) and `trackedCounter` (the tracked set's occupancy), for the coverage record's diagnostics (P-34) |
| `bpf_bpfel.go`, `bpf_bpfeb.go`, `.o` | generated by `bpf2go`, committed |

Kernel maps:

| Map | Type, size | Purpose |
|---|---|---|
| `tracked_pids` | hash, 16384 | the tracked tgids; the value is 1 and carries nothing |
| `config_map` | array, 1 | 1 = ancestry-filtered mode, 0 = host-wide |
| `execs` | hash, 4096 | a header per tgid, written when an exec takes effect and kept until exit; the exit code lands here and the exit record is this header (P-19, P-31) |
| `heap` | array, one entry per possible CPU, sized at load | scratch `exec_scratch` (header, 256-byte filename, 256 KiB args area for a 128 KiB command line, and 4352 bytes beyond it for the working directory), indexed by the running CPU, which is private to `record_exec` and `handle_exec_cwd` because `sys_enter` runs its tail-call chain with preemption disabled; a per-CPU array value is capped at 32 KiB by the kernel |
| `ok_heap` | per-CPU array, 1 | scratch `exec_ok_scratch` of `handle_exec_ok` (header, the kernel's filename, the interpreter, the program's path), about 5 KiB |
| `sys_enter_progs` | program array, 3 | the tail-call slots: `handle_execve`, `handle_execveat` (from the dispatcher), `handle_exec_cwd` (from both) |
| `events` | ring buffer, 8 MiB | records to userspace; an exec record can be 128 KiB |
| `drop_count`, `untracked_count`, `state_lost_count` | per-CPU arrays | loss counters |
| `tracked_stat` | array, 1 | `{live, peak}`: the entries the kernel inserted into `tracked_pids` minus those it deleted, and the highest occupancy read back after an insert (P-34) |
| `tracked_seeded` | array, 1 | the pids userspace inserted into `tracked_pids` (the root), written only by userspace |

Record kinds (`event_hdr.kind`): `KIND_EXEC` 0 (an exec attempt), `KIND_EXIT` 1, `KIND_FORK` 2, `KIND_EXEC_OK` 3 (an attempt took effect). An exec record carries the filename, the arguments and then the working directory; an exec-success record the kernel's filename (`bprm->filename`), the interpreter (`bprm->interp`, its length in `args_size`, 0 when it is the filename) and the path of the file the new image runs; the others are the header only. A path at a record's end (`path_size` bytes) is the names from the file up to the process's root, leaf first, each with its NUL. The header's `tid` names the thread that made the attempt, in an exec and an exec-success record. The header's `args_truncated` says the filename or the arguments did not fit, or the probe could not read them to their end (in a success record: the kernel's filename or the interpreter), `path_truncated` that the path's walk did not reach the root, and `via_fd` that an exec record's filename is `(fexecve)`.

`Config` fields: `PIDFilter` (ancestry root set at `New`), `CommandFilter` (command line prefix), `DeferRootPID` (start filtered with an empty tracked set), `EventBufSize` (default 4096), and the test-only capacity overrides `RingbufBytes`, `TrackedPIDsMax` and `ExecsMax`.

## Technologies

eBPF raw tracepoints loaded with cilium/ebpf, one tail-call program array, one ring buffer, the `bpf_loop` helper (a base helper, available to raw tracepoints since Linux 5.17) for the path walk, CO-RE (`BPF_CORE_READ`, `bpf_core_field_offset`) to read `task_struct->real_parent->tgid`, the syscall arguments from the saved user registers (`pt_regs`), the child's pid from the new task, and the dentries and mounts a path walk follows (`fs_struct`, `dentry`, `vfsmount`, `mount`, `linux_binprm`, `file`). `bpf_d_path` is not used: the kernel allows it only to tracing and LSM programs attached to a list of functions, not to a raw tracepoint (**Reported**, `kernel/trace/bpf_trace.c`). See [10_probes_common.md](10_probes_common.md) for code generation and the constant-size rule.

## Workflow

### Modes

`New` loads the object, applies capacity overrides, and sets `config_map` to 1 when `PIDFilter > 0` or `DeferRootPID` is set. With `PIDFilter`, it also seeds the root into `tracked_pids`. `SetRootPID(pid)` does the same later, records the pid in `cfg.PIDFilter` and clears `CommandFilter`. With `config_map` at 0 the probe is host-wide: every exec on the host is recorded and `handle_fork` does nothing.

### Kernel side

Every hook is a raw tracepoint (P-32). The syscall hooks sit behind `trace_sys_enter` on `sys_enter`, which fires for every syscall on the host: it switches on the syscall number first (x86_64's: `execve` 59, `exit_group` 231, `execveat` 322) and returns for any other, then skips a 32-bit syscall (`TS_COMPAT` in `thread_info.status`), as the per-syscall tracepoints did. It handles `exit_group` itself; for an exec it returns for an untracked tgid in filtered mode and tail-calls `handle_execve` or `handle_execveat` through `sys_enter_progs`, which `New` fills before it attaches anything. A tail call that fails (an empty slot) counts in `drop_count`. The exec programs read their arguments from the saved user registers by x86_64's syscall convention (`rdi`, `rsi`, `rdx`). `record_exec` is too large to inline into the dispatcher twice, hence the tail calls. The perf-event syscall tracepoints were dropped because on Linux 7.0 `sys_enter_execve` ran its program for only some execs, with no count of the others (P-32 has the measurement and what the kernel source shows).

1. `handle_fork` (filtered mode only) ignores `CLONE_THREAD` clones, reading the clone flags and the new task from the tracepoint's arguments (`task_newtask(task, clone_flags)`; the child's pid is `task->pid` through CO-RE). If the parent tgid is tracked, it emits a `KIND_FORK` record with `pid` = child and `ppid` = parent, then inserts the child into `tracked_pids` with `BPF_NOEXIST`. A new entry adds one to `tracked_stat.live` (an atomic add) and raises `peak` to `live` plus `tracked_seeded` read back after the add; an entry already present for the pid is replaced as before and not counted again.
2. `handle_execve` and `handle_execveat` run at syscall entry, so they record every attempt, including execs that then fail. An `execveat` with an empty pathname and `AT_EMPTY_PATH` execs the descriptor itself (glibc's `fexecve`): there is no path, and the filename is recorded as `(fexecve)` (P-21); an empty pathname without the flag, which fails, and a pathname whose first byte cannot be read are recorded the same way. With a pathname the kernel looks it up whatever the flags, so it is recorded as given, also with `AT_EMPTY_PATH` (`TestObserver_ExecveatWithAPathNamesIt`); one relative to a directory descriptor stays unresolved. Both share `record_exec`, which reads any other filename into a 256-byte buffer with `bpf_probe_read_user_str`, sets `ppid` from `real_parent->tgid` via CO-RE, `tid` from the current thread, and stamps `bpf_ktime_get_ns()`. In filtered mode the dispatcher has already returned for an untracked tgid, and the exec programs are reached only through its tail call. It copies up to 64 argv strings into the args area, stopping at 128 KiB, and sets `args_truncated` when a string did not fit, the strings ran past 128 KiB, an argument followed when they filled it exactly, there were more than 64 arguments, or the filename was longer than 255 bytes. A string read that fills its buffer returns the same length whether the string fit with its NUL or was cut, so the program then reads the buffer's last byte from user memory: a NUL there means the string fit. The decision fails safe: the flag stays clear only when every read succeeded and the record provably holds the whole filename and argv up to its terminating NULL pointer. A failed read of the filename, of an argv pointer, of an argv string, of the byte that proves a fit, or of the pointer that would follow a full area or the 64th argument sets it, because these reads cannot fault a page in and fail on a valid argv whose page is not present. A failure used to end the argv loop as if argv had ended, so a command line one byte over the area was recorded unflagged on CI; a failed read is the only path that leaves the flag clear at that size (**Unverified**: the record's length was not logged, and the repeated tests now log every flagged record's length). The tests run each boundary case five times and require that no unflagged record differs from the command line (`TestObserver_CommandLineOfExactly128KiBIsWhole`, `TestObserver_ProgramPathOf255BytesIsWhole`). It then tail-calls `handle_exec_cwd` and does not touch `execs`, since the attempt may fail; were the tail call to fail, which cannot happen once `New` filled the slot, it outputs the record without a working directory.
3. `handle_exec_cwd` runs in the same tail-call chain on the same CPU, so the scratch slot holds the record `record_exec` built. It appends the working directory after the arguments: `walk_path` from the task's `fs->pwd` up to its `fs->root` (P-36). The walk is `bpf_loop` over a callback, `walk_step`, that makes one step with its state in a stack struct, so the BPF verifier checks the step once rather than every path through 32 copies of it; an open-coded loop exceeded the verifier's limit of a million instructions on Linux 7.0. `TestSpec_NoOpenCodedLoops` checks, without root, that no program's control flow has a cycle and that both walking programs call `bpf_loop`. The walk reads one name per step into the record, leaf first, with `bpf_probe_read_kernel_str` into a 256-byte window (`NAME_MAX` plus the NUL, so no name is cut); a step that meets the root of a mount continues from the mount point in the parent mount without a name, and the walk ends at the process's root, or at the top of the mount namespace when the process's root is not on the way (a working directory outside a `chroot`). It stops, with `path_truncated` set, after 32 steps (names and mount crossings), when the names reach 4096 bytes, at a dentry that is its own parent without being a mount root (a disconnected one), or when a read fails. The walk is the one `prepend_path` makes, without its locks; `bpf_d_path` is not available to a raw tracepoint. It outputs the record.
4. `handle_exec_ok` runs on `sched_process_exec`, which fires only for an exec that succeeded, after the kernel replaced the image (P-31). In filtered mode it returns for an untracked tgid. It builds a header with the tgid, `ppid` from `real_parent->tgid`, a fresh timestamp, and `tid` set to the tracepoint's `old_pid` (its second argument): a non-leader thread that execs takes the leader's pid, so `old_pid` is the thread that made the attempt. It stores the header in `execs` keyed by tgid, replacing an earlier image's. It then builds the `KIND_EXEC_OK` record in `ok_heap` (P-36): the kernel's copy of the filename (`bprm->filename`, `/dev/fd/N` for an exec through a descriptor), the interpreter when a binary handler replaced `bprm->interp` (a script's `#!` line), both read with `bpf_probe_read_kernel_str` into 256 bytes and flagged in `args_truncated` when cut, and the path of `bprm->file`, the file the new image runs and `mm->exe_file` (the program, or a script's interpreter), walked from the file's dentry up to `fs->root` by `walk_path`. It outputs that record; without the scratch slot it outputs the header alone. A process whose exec attempts all failed has no `execs` entry.
5. The dispatcher, on `exit_group`, stores the low 8 bits of the `exit_group` argument as the exit code in the tgid's `execs` header and sets `has_exit_code`. That is the status the parent's `wait` reads and a shell or a harness reports: `_exit(263)` is 7 and `_exit(-1)` is 255 (`TestObserver_ExitCodeIsTheWaitStatus`).
6. `handle_exit` acts only when the exiting thread is the last of its process: it reads `signal->live` through CO-RE, which `do_exit` decrements before this tracepoint (**Reported**, `kernel/exit.c` at v6.17), and returns unless it is zero. A leader that exits first (`pthread_exit`, a raw `exit`) or that another thread's exec replaces therefore does not end the process: it stays tracked, its later children are in the tree, and its exit record carries the last thread's exit and code (`TestObserver_ProcessOutlivesItsLeaderThread`). In filtered mode it first removes the tgid from `tracked_pids`, so a process that never exec'd leaves the set too (`TestObserver_ProcessThatNeverExecsLeavesTheTrackedSet`); a delete that succeeds subtracts one from `tracked_stat.live`. If the tgid has an `execs` entry, it deletes the entry and, if that delete succeeded, outputs the header with the kind `KIND_EXIT` and a fresh timestamp; two threads that exit at once can both read zero, and only one of them deletes. The command line is not in the kernel's copy: keeping it per process would preallocate a gigabyte, so userspace joins the exit to the exec it read.

### Userspace side

`readLoop` reads the ring buffer and decodes the header with `binary.NativeEndian`.

1. A record whose pid equals `cfg.PIDFilter` is dropped: the root is the controller, not an agent action. This covers the root's own exec, which can reach the ring buffer before `SetRootPID` takes effect.
2. A fork record first releases the held attempts of an earlier process with the child's pid, which has exited, then becomes `process_fork` with `Target` = the child pid as a decimal string, `PID` and `PPID`. It is skipped when `CommandFilter` is set.
3. An exec record becomes `process_exec`. `commandLine` builds the target from the filename recorded at syscall entry (the literal `(fexecve)` for an exec through a descriptor) followed by `argv[1:]`; `argv[0]` is dropped because the caller controls it. Only when the filename is empty does it fall back to `argv[0]`. The working directory becomes `Cwd` (`walkedPath`: the names reversed and joined under `/`; a walk flagged cut keeps the names it read without a leading slash and sets `CwdTruncated`; a record with no path and no flag has no working directory). The `joiner` remembers the target and the truncation flag as the latest attempt of the thread `tid`, before any filter. A record with an empty command line is dropped (and forgets the thread's attempt), and `CommandFilter` drops non-matching prefixes. The event is not sent yet: the `holder` keeps it until its outcome is known (P-36), and first releases the same thread's previous attempt, whether or not the new one passes the filters.
4. An exec-success record emits no event of its own. The `joiner` makes the latest attempt of its `tid` the image of its tgid, replacing an earlier one; a success whose attempt it never read (a ring drop, counted) clears the image instead. A failed attempt has no success record and changes nothing (`TestJoiner_ExitNamesTheLastImageThatTookEffect`). The `holder` releases the held attempts of other threads of the process, which the exec ended, then the attempt of `tid` with `Image` set from the record (`execImage`): `Filename`, `Interpreter`, `Program` (walked as above), `Truncated` when any of them is cut, and `FilenameChanged` when `Filename` is not the filename read at entry, except for an exec through a descriptor and for `/dev/fd/N/<path>`, the kernel's name of an `execveat` path relative to a directory descriptor (`filenameChanged`).
5. An exit record first releases the held attempts of its tgid, which failed, then becomes `process_exit` with the target and flag of its tgid's image, the last exec that took effect, which are then forgotten (P-31). A process that tried a missing binary and then exec'd another exits under the other (`TestObserver_FailedExecDoesNotNameTheExit`); one that exec'd twice exits under its second program (`TestObserver_ProcessThatExecsTwiceExitsAsItsLastImage`); a non-leader thread's exec names the exit (`TestObserver_ExecByANonLeaderThreadNamesTheExit`). An exit with no known image (the exec or its success record lost to a ring drop, counted by `drop_count`) is not emitted.
6. The event carries `PID`, `PPID`, `TargetTruncated` and, for an exit with `has_exit_code`, `ExitCode`; an exec event also `Cwd`, `CwdTruncated` and, when its exec took effect, `Image`.
7. Events are sent without blocking; a full channel increments `Dropped`. An exec event goes out when its success record arrives or when a record shows its attempt over (above); an attempt still held when `readLoop` ends is released then, before `Stop` closes the channel (`TestHolder_ReleasesEachExecWithItsOutcome`). The order of events on the channel therefore differs from the order of their timestamps for an exec whose release waited; `cmd/watch` sorts the ground truth by time.

`readLoop` samples the ring at every record it reads (`ringMeter.observe`, P-34): the read reports the bytes the ring still holds after the record, so the occupancy before it is that plus the record's 8-byte header and its length rounded up to 8. The highest value is the ring's `PeakBytes`, and the records read its `Records`. `SetRootPID`, and `New` with `PIDFilter`, insert the root with `BPF_NOEXIST` and count it in `tracked_seeded` (`trackedCounter.seed`); a root already present is updated in place and not counted again.

`Stop` detaches the hooks first, then flushes the ring buffer reader: `readLoop` then reads with a deadline of now, gets every record already committed, and returns at the first empty read (`drainRead`, as N-32 does for the net probe). `Stop` waits for it, snapshots the three kernel counters and the tracked-set count, closes the reader and the maps, and closes the events channel. Detaching a raw tracepoint does not wait for a grace period, unlike the perf-event tracepoints the probe used before, which took about 60 ms each (N-32).

## Guarantees and loss accounting

The target's first token is the path the kernel was asked to execute (or `(fexecve)` when it was given a descriptor), not `argv[0]`, so a process cannot rename itself in the ground truth (`TestObserver_ResistsArgv0Spoofing`). Every tracked process appears through a fork record even if it never execs, which is what lets a subshell's file activity be attributed (`TestObserver_ForkRecordsPlaceProcessesThatNeverExec`). Threads are never inserted into `tracked_pids` (`TestObserver_ThreadsAreNotTracked`). An exec event names the working directory a relative path in its target resolves against (`TestObserver_RelativeExecReportsItsCwd`; through mounts, `TestObserver_CwdAcrossMounts`; a directory deeper than the walk is flagged and keeps its deepest names, `TestObserver_DeepCwdIsFlagged`). An exec that took effect carries the kernel's own record of it: an exec through a descriptor names the program it ran (`TestObserver_FexecveNamesItsProgram`), a script its interpreter (`TestObserver_ScriptNamesItsInterpreter`), and a failed attempt carries none (`TestObserver_FailedExecHasNoImage`). Neither is read by any verdict (V-51).

| Counter | Incremented when | Coverage field |
|---|---|---|
| `drop_count` | `bpf_ringbuf_output` fails for an exec, exec-success, exit or fork record, or the dispatcher's tail call to an exec program fails | `RingbufDrops` |
| `untracked_count` | inserting a child into `tracked_pids` fails | `UntrackedChildren` |
| `state_lost_count` | storing a successful exec in `execs` fails, so its exit record will be missing | `StateMapFull` |
| `Dropped` (userspace) | the events channel is full | `ChannelDrops` |

All four are event loss ([10_probes_common.md](10_probes_common.md#probecoverage)). `CaptureCoverage` also writes the diagnostics (P-34, [10_probes_common.md](10_probes_common.md#diagnostics)), which no verdict reads: the `events` ring's size, `PeakBytes`, `Records` and `Drops` (equal to `RingbufDrops`), and the `proc` tracked set's capacity, `Peak` (the kernel's peak, or the occupancy read back after a seed, whichever is higher) and `AtStop` (`live` plus the seeded pids). A process counts in the tracked set from its fork record to the exit of its last thread, whether or not it exec'd, so `Peak` is the most processes of the tree alive at once, the root included. The events cannot reproduce it: a process that never exec'd, or whose attempts all failed, has a fork event and no exit event (Known limits), so a count of the tree's processes alive at once from fork and exit events keeps every such process alive to the end of the capture and exceeds `Peak` by up to their number; a shell's subshells and command substitutions are such processes. `TestObserver_RingHighWaterMark` writes ten runs of a known command before the reader starts and requires a mark of at least their bytes; `TestObserver_FullRingHighWaterMark` overflows a 16 KiB ring the same way and requires the mark within one exec record of the size; `TestObserver_TrackedSetPeak` keeps 24 children alive under the root, compares the count with the map's own entries, and requires a peak of 25 and one entry at the stop; `TestObserver_CountsUntrackedChildren` requires a peak equal to the capacity when the map fills. Tests force each kernel counter through a capacity override (`TestObserver_CountsRingbufDrops`, `TestObserver_CountsUntrackedChildren`, `TestObserver_CountsStateMapFull`) and check that the tracked-set and state-map counters stay zero when the map fits. `TestObserver_EveryExecAttemptIsRecorded` runs 200 `/bin/true` children and 50 failed attempts under a tracked shell and requires one exec record per attempt, one exit per successful exec and no loss counted, stopping the probe as soon as the shell has exited; `TestHooks_EveryProgramIsARawTracepointAndIsWired` checks, without root, that every program is a raw tracepoint that `New` attaches or that a `sys_enter_progs` slot holds.

## Known limits

- A process that never execs produces no `process_exit`, because exit records are copies of an `execs` entry; nor does one whose exec attempts all failed, such as the child of a spawn helper (Go, Python, libuv) that exits with a code of its own after a failed exec (P-31).
- The exit names the last exec that took effect, so a process that exec'd twice (a shell that execs its last simple command) exits under its second program. The verifier compares an exit claim with the exit of the process its aligned exec started, under that exec's command line (V-44), so this is no finding on an honest exit claim; the record itself keeps the program that exited.
- A lost exec-success record leaves the exit joined to the image before it, or to none; the loss is counted in `drop_count`.
- A process killed by a signal never calls `exit_group`, so its exit has no `ExitCode`; nor does one whose last thread ends with a plain `exit` rather than `exit_group`.
- Filename and argv are read from user memory at syscall entry, so another thread can change them before the kernel copies them. For an exec that took effect, `Image.FilenameChanged` reports a changed filename, and `Image.Program` names the file the kernel ran whatever the filename said; a changed argv is not detected: the probe does not read the new image's argv, and no test changes argv between the two reads, which a test cannot time.
- An exec through a descriptor names no program in its target: the target is `(fexecve)` followed by the arguments, so a claim that names the program reads as a substitution unless the adapter rewrites one side (P-21, `TestObserver_ExecThroughADescriptorIsRecorded`). Its `Image.Program` names the program when the exec took effect (P-36), for the reader only. An `execveat` pathname relative to a directory descriptor is recorded unresolved in the target, and reads like a pathname relative to the working directory; its `Image.Filename` is `/dev/fd/N/<path>`, which names the descriptor, not the directory, and its `Image.Program` names the file.
- argv is kept up to 64 arguments and 128 KiB in all, and the filename up to 255 bytes; beyond that the record is cut and `TargetTruncated` says so, and the verifier pairs the cut target by prefix as unverified (V-26). A record the probe could not read to its end is flagged the same way, so an honest command line can read as cut, which costs only the prefix pairing. Linux allows one argument of 128 KiB, and the shell's own arguments share the 128 KiB area, so a harness's single-string command fits unless it nears that size (`TestObserver_LongCommandLineIsRecordedWhole`, `TestObserver_OverlongCommandLineIsFlagged`).
- The probe captures no environment or stdin, so a script fed through a pipe or heredoc is invisible.
- The working directory and the program's path are walked without the kernel's rename lock, so a rename of a directory on the path during the walk can produce a path that never existed. A removed working directory is named by the path it had; the kernel's `getcwd` would add ` (deleted)`. A working directory outside the process's root (after a `chroot` that left it outside) is named from the top of the mount namespace, where `getcwd` says it is unreachable. A walk of more than 32 steps (names and mount crossings) or 4096 bytes is flagged and keeps the deepest names. A file reached through a bind mount is named through that mount, as the process sees it.
- A relative path in an argument is relative to `Cwd` only if the program did not change directory before using it; `Cwd` is the directory at the exec.
- An exec event is sent when its outcome is known: at its success record, or, for a failed attempt, at the next attempt of the same thread, the success of another thread's exec in the process, the process's exit record, the fork of a new process with its pid, or `Stop`. A failed attempt of a process that then exits without another exec or an exit record (the child of a spawn helper whose exec failed) is sent at `Stop`. The capture is unchanged, since `cmd/watch` sorts by time, but a live reader of the channel sees such events late.
- A lost success record (a ring drop, counted) leaves its attempt's event without an `Image`, the same as a failed attempt; a capture that counted ring drops cannot tell the two apart from the event. A script's `Image.Interpreter` is the interpreter as its first line wrote it; `Program` is the file that ran, resolved. A binary handler other than a script's (`binfmt_misc`) is reported the same way.
- Each successful exec's record grows from 48 bytes to about 600 plus the program's path, and each exec record by its working directory's length; neither cost is measured (**Unverified**).
- In host-wide mode no fork records are emitted, so the forest cannot place processes that never exec.
- With `cmd/watch --root-pid`, the root pid is inserted into a process already running, so a fork before `SetRootPID` is untracked and uncounted. An agent `cmd/watch` launches is registered before it execs (P-23, [10_probes_common.md](10_probes_common.md#how-cmdwatch-builds-and-starts-probes)).
- `PPID` is the parent at exec time; a later reparenting is not reflected in the exit record.
- A 32-bit (ia32) syscall is skipped, as the per-syscall tracepoints skipped it on x86_64: a 32-bit process's exec attempts have no record, so its exec's success record finds no attempt and its exit is not emitted, and its `exit_group` code is not recorded. A 64-bit process that execs a 32-bit program is recorded, since the exec is a 64-bit syscall. The syscall numbers and argument registers are x86_64's.
- The dispatcher runs for every syscall of every process on the host, adding a program call and a switch to each; its cost is not measured (**Unverified**).
- A hook still running on another CPU when `Stop` detaches it can commit a record after the drain has ended; that record is lost uncounted. The window is the run time of one program.
- The ring's `PeakBytes` is sampled by the reader, so it can fall short of the true peak by one record and its header: the reader consumes one record between two samples. A ring the reader never reads (the probe stopped before `Start`) has no sample.
- The tracked set's `Peak` is read back after the atomic add with a plain load and raised with a plain store, since `bpf2go` compiles for BPF v1, which has no fetch-and-add and no compare-and-swap. An insert or delete on another CPU between the add and the load, or two raises racing, can leave the peak short, by at most the number of such races; every value kept was the occupancy at some instant. A pid seeded while a tracked process forks can be missing from the occupancy that insert reads back.
- A raw tracepoint program that the kernel does not run because the same program is already running on that CPU (a nested call, in practice only from an NMI) increments the program's own `recursion_misses`, which the probe does not read.
