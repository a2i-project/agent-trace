# Agent adapters

Checked against commit 90f08c5 on 2026-10-24.

## Objective

An adapter isolates everything one agent harness does differently from the core verifier: how its session file is read into claims, how observed events are rewritten into the form claims use, what the harness does on its own, and which content fields its format can state. `pkg/matching` and `pkg/verification` contain no agent knowledge; adding an agent means adding a package under `pkg/agent` that implements `agent.Adapter` and registers itself. The design reasons are in [decisions/integration.md](../decisions/integration.md) (D6 to D13) and [decisions/verification.md](../decisions/verification.md) (V2, V7).

### The Adapter interface

```go
type Adapter interface {
	Name() string
	Detect(path string) bool
	Parse(path string) (models.Trajectory, Report, error)
	Normalize(models.GroundTruthEvent) (models.GroundTruthEvent, bool)
	IsHarnessNoise(models.GroundTruthEvent) bool
	Expresses(entry models.TrajectoryEntry, field string) bool
	Process() ProcessModel
}
```

`HarnessOwner` is an optional interface, `IsHarnessOwned(path string) bool`, for an adapter that can say where the harness keeps its own files; the verifier reports an unexplained level-0 file event there as unexplained harness activity rather than as the agent's unreported action ([20_verifier.md](20_verifier.md#verdict-vocabulary), V-24, I-30). It declares where, not what: nothing is explained by it. `HarnessHoster` is an optional interface, `HarnessHosts() []string`, for an adapter that can name its harness's own service hosts, exact host names as the net probe reports a connection's target (its TLS SNI), that the harness connects to only in some runs; the verifier reports an unexplained level-0 `net_connect` to exactly one of them as unexplained harness network activity rather than as an omission (V-34). A host is declared only from a capture that shows the harness's own process connecting to it in some runs and not others (I-52, I-53); a host in every run is the baseline's. Like `HarnessOwner` it explains nothing, and a connection there by a command the agent ran stays a finding. `SensitiveDeclarer` is an optional interface, `SensitiveFiles() []string`, for an adapter that can name its harness's security-sensitive files: the short list of settings, permission and configuration files whose change would change what the harness lets the agent do, each under `~/` (the home of the user the agent runs as) or `{workspace}/` (I-59). `cmd/watch` snapshots them at the start and the stop of a capture with `pkg/agent/sensitive` ([40_tools.md](40_tools.md#watch), [10_probes_common.md](10_probes_common.md#ground_truthjson), V-40); `agent.SensitiveFiles(a)` returns the list, or nil for an adapter that declares none. `SensitiveKeyDeclarer` is an optional interface, `SensitiveKeys(file string) []string`, for an adapter one of whose declared files mixes the harness's state (caches, counters, timestamps) with its settings: for that file it returns the key paths that decide what the harness lets the agent do, as patterns of dot-separated elements in which `*` matches any one element (a per-project entry keyed by its directory), and nil for a file whose every key path is checked (V-41, I-60). An unexplained change under one of them is a finding, any other unexplained change of the file is listed report-only ([20_verifier.md](20_verifier.md#verdict-vocabulary)); `agent.SensitiveKeys(a, file)` returns the list, nil for an adapter that does not implement it. `Canonicalizer` is an optional interface, `Canonical(models.GroundTruthEvent) models.GroundTruthEvent`, for an adapter whose observed targets carry ids that differ every run: it returns the event with those ids replaced by fixed tokens, and is applied only where events of different runs are compared, when `Capture` builds rules and when `Prepare` matches a run's events against them. Pairing and every other comparison within a run use the exact target (I-41). `StreamNormalizer` is an optional second interface, `NormalizeStream(models.GroundTruth) models.GroundTruth`, for an adapter whose observed events are comparable only when several are looked at together (I-22). `Name` keys the registry and the baseline file. `Parse` returns entries in claim order, each with its interval (`Timestamp`, `End`), its `ThreadID` where subagents were flattened, its `BlockID` where the format issued several calls at once, and its `Tool`. `Normalize` returns false to drop an event. `IsHarnessNoise` is what the adapter knows statically; the measured baseline is supplied separately. `Expresses` answers for one of the `verification.Diff*` field names.

### ProcessModel

| Field | Meaning |
|---|---|
| `ShellPerCommand` | Each shell claim execs its own process, so a claim aligns with a command's exec. False means a persistent shell, where both checks lose their subject. |
| `SubagentsInProcess` | Subagent actions are indistinguishable from main-thread ones in G, which forces flattening (D9). |
| `Containerized` | Observed paths and pids live in another namespace. No adapter handles it. |
| `IntervalKind` | `IntervalNone` (a point), `IntervalDecision` (start is when the model decided, includes approval latency), `IntervalExecution` (start is when execution began). |
| `Concurrency` | `Sequential`, `Parallel` (entries sharing a `BlockID` have no order among themselves), `ConcurrencyUnmeasured`. |
| `ExitsClaimed` | The format records process exits. False makes `Prepare` set `Options.IgnoreExits`. |

Only `ExitsClaimed` changes verifier behaviour today. The other fields are declarations; `Concurrency` in particular is not consumed, because the verifier does not implement the partial order ([20_verifier.md](20_verifier.md), Known limits).

### Report

`Report` makes what was not measured visible: `ToolCalls` (invocations in the session), `Entries` (claims produced), `AgentVersion` (the harness version the session states, if any), `UnmappedByTool` (tool calls that produced no entry, by name), `UnknownTools` (tools neither mapped nor declared non-effectful, which may have acted unseen), `ParseErrors`, and `Degradations` (each precision loss in words). `cmd/verify` prints all of them before the verdict.

## Technologies

Go. The Claude Code adapter reads JSONL with `bufio.Scanner` (lines up to 64 MiB) and `encoding/json`. The Gemini adapter copies the conversation database and its write-ahead log, when there is one, into a private temporary directory and opens the copy read-only through `modernc.org/sqlite` (pure Go, no cgo), so reading a session writes nothing next to it (I-51), and decodes the undocumented protobuf step payload with a hand-written wire-format walker (`wire.go`), since no `.proto` is available. Content hashes use `pkg/content.SHA256Bytes` (`sha256:<hex>`).

## Workflow

### Registry and detection

Each adapter package calls `agent.Register` from `init`. `Register` panics on an empty or duplicate name. A command makes an adapter available by importing its package (`cmd/verify` and `cmd/baseline` blank-import `claudecode` and `gemini`).

`agent.Detect(path)` asks every registered adapter, in sorted name order, whether it recognises the path. Exactly one match returns that adapter. No match returns an error wrapping `ErrNoMatch`, so a caller can fall back to the generic adapter. Several matches return an error naming them; the caller must choose with `--agent`. The generic adapter never detects.

### From session to verifier input

`agent.Prepare(a, claims, groundTruthFile, measured, opts)` builds a `verification.Input`: it runs the observed events through `agent.NormalizeGround` (every event through `a.Normalize`, dropping those it rejects, then the stream through `NormalizeStream` when the adapter implements it; `Capture` uses the same function, so a rule is measured on the shape the verifier compares against), combines `a.IsHarnessNoise` and the measured baseline into one predicate (an event is harness activity if either says so; the measured baseline sees the event as `Canonical` returns it, the events the verifier aligns keep their exact targets, I-41), sets `opts.Expresses = a.Expresses`, `opts.IgnoreExits = !a.Process().ExitsClaimed` and, when the adapter is a `HarnessOwner`, `opts.HarnessOwned`, and copies `RootPID`, `Coverage`, `FSScope` and `Workspace` from the file. Caller options such as `IntervalSlack` are kept. `agent.PrepareWithBaseline(a, claims, groundTruthFile, baseline, opts)` does the same with a `*Baseline`, passing its `Predicate` as the measured baseline and its subtree records as `Input.BaselineSubtree` (`agent.BaselineSubtree`: the command and the event beneath it are compared in their `Canonical` form, and a command `IsHarnessNoise` declares explains its whole subtree), so a baselined command explains only what its controls did beneath it (V-38). `Prepare` given only the predicate leaves the records out and keeps the V7 reading; `cmd/verify` sets `BaselineSubtree` after `Prepare`. Both set `Input.Sensitive` with `agent.SensitiveInput(a, groundTruthFile, baseline)` (V-40): nil when the capture holds no snapshot or the adapter declares no file, else one entry per declared file with what the snapshot recorded of it and the adapter's `SensitiveKeys` for it, and, from a baseline with a sensitive record, `Baseline.SensitiveExplained` and which files its controls measured; `Prepare` passes no baseline, so the changes are reported as not checked, and `cmd/verify` sets it again with its baseline.

### Generic

`Generic` reads a trajectory already in the normalized JSON form (`models.ParseTrajectory`, which rejects unclaimable action types). It normalizes nothing, declares no noise, treats every field as expressible, and declares `ShellPerCommand`, `IntervalNone`, `Sequential` and `ExitsClaimed: true`. Its report carries one degradation saying so. It is the adapter for `cmd/simagent` output and for an agent whose format has been converted elsewhere.

**Precision lost against the native adapters.** **Verified** on eleven of the twelve paired fixtures of both native adapters, all but `paired-2.1.306-tools`, which the test does not list yet (`generic_paired_test.go` in `pkg/agent`): each session is read by its own adapter, written as the generic format and read back by `Generic`, then verified against the same task run, once with a baseline `Generic` captured from the fixture's controls and once without, both at an agreement of one control in N. The conversion applies only what the format can state: the entries as the native `Parse` returned them, without the harness-implied claims (`attack.WithoutImplied`). `ImpliedBy` has no JSON form, so a converted trajectory never names it, and `ParseTrajectory` refuses one that does (V-33); a converter that kept such an entry would make the harness's read a claim of the agent's. Nothing on the observed side is converted. A run of `cmd/verify --agent generic` with a baseline from `cmd/baseline --agent generic` on `paired-2.1.286` gives the same counts as the test.

Every one of the 22 verdicts is NOT FAITHFUL, against FAITHFUL or INCONCLUSIVE natively. No claim is unwitnessed, and every mismatch differs on the target: a command against its wrapper's argv, a write against a temporary or the harness's own file. None is a disagreement on the content of the claimed target, so the outcomes show lost precision, not a defect of `Generic`. ### Gemini (`gemini`)

The harness is `agy` (Antigravity's CLI), a single Go binary. A print-mode run (`agy -p`) keeps its conversation in `~/.gemini/antigravity-cli/conversations/<id>.db` and prints the id with `--output-format json`; it also writes transcripts under `~/.gemini/antigravity-cli/brain/<id>/`, which the adapter does not read. A subagent's steps are in a database of its own, `<subagent id>.db` in the same directory, named in the result of the `invoke_subagent` step (I-55).

Detect: a file starting with the SQLite header whose `steps` table has a `step_payload` column.

Detect and Parse read a private copy of the database and of its write-ahead log `<path>-wal`, when one exists, so steps the harness has not yet checkpointed into the database file are read, and nothing is created next to the session, whose directory may be read-only (I-51). Parse reads `steps` ordered by `idx` and decodes each payload. Tool calls are the submessages at protobuf path 5.4: field 1 the call id, 2 the tool name, 3 the arguments as a JSON string. The claim start is the started timestamp (5.6), falling back to created (5.1) with a degradation; `End` is completed (5.8) when present. Entries are sorted stably by start. A step with more than one call gives its entries `BlockID` = `step-<idx>`; calls the model issued together were seen as separate steps, one call each, which therefore carry no block id. Parse fails loudly, naming the field path, when a payload does not decode, a call lacks its name or arguments, the arguments are not JSON, a step has no timestamp, or the database has no steps: a version that moves a field number must produce an error, never an empty trajectory. The four conversation databases of those runs (three main conversations and a subagent's) and the 46 older ones on the development machine parse without an error. A payload holds more than the adapter reads: field 140 repeats the step with its result, a `run_command` result's text states the exit code (`The command exited with code N.`), and field 5.32 preceded the exec of each of seven measured commands by 12 to 23 ms (I-47); of these only an `invoke_subagent` step's result is read, as follows.

Parse then follows the subagents (I-55). A step holding an `invoke_subagent` call, whatever its status, names the conversations of the subagents it created at 140.2.6.2.143.10.1, one 143.10 per subagent: 140.2.6 is a `google.protobuf.Any` wrapping a Step, and 143 is that Step's subagent result. The result's text for the model (140.2.1) names the same ids and is not read. An id of any other form than a lowercase UUID is not looked up, since it comes from the trajectory and could name a path. Each id is looked up as `<id>.db` beside the conversation, where agy keeps it, and then in `<conversation without .db>/subagents/`, where the capture script copies it (`<label>.conversation/subagents/<id>.db`); nested subagents are looked up in the same two directories. The subagent's database is read like the main one (a private copy, I-51), and its claims get `ThreadID` = the subagent's conversation id (D9) and, for a step with several calls, `BlockID` = `<id>/step-<idx>`, so two threads' blocks never share an id (V-32). Subagents are read breadth first, each id once (so a cycle ends), down to four levels below the main conversation (`maxSubagentDepth`). The claims of all threads are sorted together, stably by start, the main thread's first on a tie, as the Claude Code adapter orders its subagents' calls. A subagent's tool calls join the report's counts. A subagent whose database is not found, an `invoke_subagent` step that names no usable id, and a subagent nested deeper than the bound are degradations, not errors; a subagent database that does not parse is a parse error naming the subagent and contributes nothing else.

What the harness does, measured with `strace -f` on agy 1.3.4 (I-47, I-48). The agy process is the agent: no launcher, and its language server runs inside it. Each `run_command` is a new child of it that execs `bash -c <CommandLine>` in the call's `Cwd` on a new pseudo-terminal, bash found on `PATH` (`/usr/bin/bash`, or `/bin/bash` under `setpriv --reset-env`); before it the harness rewrites its shim `~/.gemini/antigravity-cli/bin/agentapi` and opens `/dev/ptmx`. ### Baseline construction

A baseline is the harness's own activity, measured by control runs in which the agent is given a task that claims nothing, so everything it does is the harness (D11, V7).

`agent.Capture(a, version, runs, now, opts)` requires at least one run and a root pid in each. For each run it normalizes events with the adapter (`NormalizeGround`, the same two steps as `Prepare`), builds the forest and partition, and takes the distinct `(action_type, target)` pairs of the aligned sequence (`Partition.Observed`), each event in the form the adapter's `Canonical` gives it, since a rule is compared with other runs (I-41). Descendants of a command are not rules. Instead, for every command rule, `Subtrees` records what the command did beneath it (V-38): the distinct `(action_type, target)` pairs of the checked types (`verification.SubtreeChecked`: programs run, files written, closed after writing, renamed or deleted, connections and requests) beneath any instance of the command in a run, canonical and with the workspace templated like a rule, kept in `Subtree.Events` when as many runs did them as a rule needs, and in `Subtree.Unstable` otherwise; reads and exits are not recorded. A pair seen in at least `opts.MinAgreement` of the runs (default 1, every run) becomes a `Rule`; a pair seen in fewer goes to `Unstable`, which is recorded for the reader and subtracts nothing. A target named in `opts.Exclude` becomes neither, whatever its action type, and the baseline records it in `Excluded`; it names the control task's own command (I-28). The run's own workspace (recorded by `watch` in the ground truth file) is replaced by `{workspace}` in each target, and its mangled form (every slash a dash, which is how Claude Code names its per-project transcript directory) by `{workspace-}` (I-24, I-29). Both lists are sorted. The `Baseline` records `Schema`, `Agent`, `AgentVersion`, `Captured` (UTC), `Runs`, `MinAgreement` and `Excluded`; `SaveBaseline` writes it as JSON with the keys `schema` (1), `agent`, `agent_version`, `captured`, `runs`, `min_agreement`, `rules`, `unstable`, `excluded` and `subtrees`, each rule an `action_type` and a `target`, each subtree a `command` (the rule's target), its `events` and its `unstable` rules. `subtrees` is always written, an empty list when there is no command rule; a file without the key, written before V-38, loads with no records (`RecordsSubtrees` false), and its commands explain their whole subtree.

`Capture` also records what the controls changed in the adapter's declared sensitive files (`Baseline.Sensitive`, V-40), when the adapter declares some and every control holds a snapshot; otherwise it records none, and the key `sensitive` is left out of the file. `files` lists the declared files every control measured at both ends (present or missing, not unread). For those files, each control's changes are taken as `(file, key, kind)` with the run's workspace replaced by `{workspace}` in every element of the key (Claude Code keys its per-project entries of `~/.claude.json` by the directory) and the mangled form by `{workspace-}`; a change made by as many controls as a rule needs is kept in `changes`, one made by fewer in `unstable`, which explains nothing. Entry counts and values are not recorded. `Baseline.SensitiveExplained(workspace)` answers whether a run's change, its key templated with the run's workspace, is exactly one of `changes`; nil when there is no record.

`Baseline.Predicate(workspace)` recognises an event when a rule has exactly its action type and target (`Prepare` passes it the canonical event), with the placeholders expanded to the workspace of the run being verified and its mangled form (a rule that names the placeholder matches nothing when no workspace is known). There is no pattern matching, since a wildcard would explain whatever an attacker made it match. `Baseline.Subtree(workspace)` answers, for a command's exec and an event beneath it, whether the record of the command with exactly that target holds the event exactly, placeholders expanded the same way; a command with no record explains nothing beneath it, and a baseline without records gives nil. `LoadBaseline` rejects an unknown schema and a baseline that names no agent. Which control runs `cmd/baseline` refuses, and which baselines `cmd/verify` refuses, is in [40_tools.md](40_tools.md#baseline).

### Configured agent versions

Each adapter's shapes, id families, harness hosts and version gates were measured on particular versions of its agent, and a version that changes them can stop fitting without an error. `config/agents.json` records, per adapter, the versions whose checked-in fixtures verify (I-57): for each, the `version` as `--version` prints it and the session states it, `verified`, the date of its newest checked-in capture, and `fixtures`, the fixture directories recorded with it, relative to the repository root. Each adapter also names its `binary`, which `status` runs. Today the file lists Claude Code 2.1.286 (the five `paired-2.1.286*` fixtures, verified 2026-10-12), 2.1.296 (the four `paired-2.1.296-*` fixtures, verified 2026-10-17) and 2.1.306 (`paired-2.1.306-tools`, verified 2026-10-24, I-63), and agy 1.3.4 (`agy-1.3.4-strace`, `paired-agy-1.3.4-basic` and `paired-agy-1.3.4-search`, verified 2026-10-13). Claude Code 2.1.284 is in I-46's gate, from the strings of its binary, but has no capture, so it is not configured.

`pkg/config` reads the file. A tool finds it from `--config`, else `$AGENT_TRACE_CONFIG`, else beside its executable (`make build` puts the binaries in the repository root), else in the nearest directory at or above the working directory that holds both `config/agents.json` and a `go.mod`. `Load` refuses another schema, an adapter without a binary, a version that is not dotted numbers, a duplicate, a date that is not `YYYY-MM-DD` and a version without a fixture. The tests tie the file to the code without coupling them at run time: every adapter in the file is registered and every registered adapter but `generic` has an entry; every listed fixture exists and was recorded by its version (each Claude Code transcript, subagents included, states it on every record, and the adapter reports it; an agy conversation states none, so a Gemini fixture is checked by its name, which the capture gave it from `agy --version`, and by the adapter reading it); every fixture directory under `pkg/agent/*/testdata` whose name carries a version is listed under that version; and every configured Claude Code version is in I-46's `harnessReadVersions`, `capturedVersion` is configured, and a gated version the file lacks is explained in the test (2.1.284).

`cmd/status` compares the agents installed on the machine with the file, `cmd/verify` the session's version, and the capture script refuses an unlisted installed version before it asks for sudo ([40_tools.md](40_tools.md)).

To add a version: capture it with `scripts/capture-claude-code.sh --allow-unconfigured-version` (its own `verify` runs read INCONCLUSIVE, naming the version, until it is listed); reduce the capture to a fixture named with the version (`scripts/make-capture-fixture.py`) and add its test; resolve what the capture shows to differ, as decisions; decide each version gate in the adapter (for Claude Code, whether I-46's parser is unchanged, read from the new binary); then add the entry with the capture's date and the fixture. The tests fail until the fixture and the gates agree with the entry.

## Guarantees and loss accounting

- No tool call is dropped silently: in both real adapters every call either produces entries or is counted in `UnmappedByTool`, and an unknown tool is also listed in `UnknownTools` (`TestParseCountsWhatItDoesNotMap`, `TestParseCountsAndNamesWhatItDoesNotClaim`).
- A format limit is never read as an opt-out: `Expresses` turns a nil that the format cannot state into no finding, and `ExitsClaimed: false` removes exits from both sides rather than reporting every exit as an omission.
- Detection never guesses between adapters (`TestDetectRefusesToGuessBetweenAdapters`).
- A search is recognised only from the command lines a capture showed, and the fold of a failed ripgrep with its fallback only in the measured shape; any other program, option shape or interleaving keeps its text (`TestSearchOfRecognisesOnlyTheMeasuredForms`, `TestFoldSearchesIsNarrow`, I-54).
- A Gemini subagent the conversation names is read or named in the report: a missing database, a result with no usable id and a subagent beyond the depth bound are degradations, and a subagent database that does not parse is a parse error; an id that is not a conversation id is never used as a path, and a cycle ends (`TestAMissingSubagentIsADegradation`, `TestAnInvokeWithNoUsableIDIsReported`, `TestASubagentThatDoesNotParseIsAParseError`, `TestNestedSubagentsAreBoundedAndCyclesEnd`, I-55).
- The Gemini adapter fails with the field path rather than returning a partial trajectory when the payload layout changes. It reads steps that only the write-ahead log holds, writes nothing next to the database, and reads a database in a read-only directory (`TestParseReadsTheLogAndLeavesTheDirectoryAlone`, `TestParseReadsADatabaseInAReadOnlyDirectory`, I-51).
- A harness-implied open is derived only from the call itself, never from a marker in the transcript, never for a command the reader does not follow, and never merged with the agent's own open of the file (`TestReadCommandFilesFollowsTheHarnessParser`, `TestABashReadCommandImpliesTheHarnessRead`, `TestTheAdapterIgnoresAMarkerInItsInputAndNeverMergesTheAgentsOpen`); the harness's read after `cat` in a parallel block is explained and the run FAITHFUL, and without the claim the read is Unrecorded (`TestTheHarnessReadAfterCatIsExplainedEndToEnd`, I-46).
- A claim pairs only with an event on the exact path it names, while the baseline compares runs on the canonical path: a Read of one background task's output file is not witnessed by another task's, and a control's task output still explains the run's own (`TestAClaimOnATaskOutputPairsWithThatFileOnly`, I-41).
- Each adapter declares as harness hosts only the hosts its harness's own process connected to in some measured runs and not in others, never an address and never a host every run has (`TestHarnessHostsAreTheMeasuredOccasionalHosts` in both adapters, I-52, I-53), and `Prepare` passes them to the verifier (`TestPreparePassesHarnessHostsToTheVerifier`).
- A baseline only subtracts exact `(action_type, target)` pairs that enough control runs produced, from loss-free runs, for the adapter it was captured with, and never the control task's own command (`TestCaptureExcludesTheControlTasksOwnCommand`, `TestPairedControlCommandIsNotABaselineRule`).
- A baselined command explains only the programs, writes and connections beneath it that the controls' same command produced: on the paired 2.1.286 capture a curl, a connection and a workspace write forked beneath the harness's `/bin/bash -c env` are each unexplained and the run NOT FAITHFUL (`TestPairedBaselineCommandDoesNotExplainAnInjectedSubtree`), while every checked-in Claude Code capture, at every agreement, has the same outcome and findings with the records as without (`TestSubtreeRecordsAddNoFindingToAnHonestFixture`, V-38). The records are built per command rule at the rules' threshold (`TestCaptureRecordsWhatEachCommandDidBeneathIt`).
- No call is claimed twice: a record of a type other than `assistant` or `user` that repeats calls and results claims nothing and replaces no result, and a call or result stated twice is a parse error with the first kept (`TestOnlyAssistantAndUserRecordsStateCalls`, `TestARepeatedCallIsAParseErrorNotASecondClaim`, I-62).
- An Edit's content claim reaches the verdict: on the `edits` capture, an Edit whose file ended with other content than its result reports is a Mismatched finding on its output hash and the run NOT FAITHFUL (`TestPairedEditWithSubstitutedContentIsNotFaithful`, I-31).
- Every version `config/agents.json` lists has a fixture recorded by it, every versioned fixture is listed under its version, and every configured Claude Code version is in I-46's gate (`TestEveryListedFixtureHasItsVersion`, `TestEveryVersionedFixtureIsListed`, `TestVersionGatesAgreeWithTheConfig`, I-57).

## Known limits

- The fold takes a second rename of a replace's directory only in captures recorded before P-18; on a current capture its condition, narrower than P-18's, never holds (I-33). On an old capture it hides what P-18 hides: two real renames of one directory by one process with nothing between read as one. A split rename in the read-after-rename shape has not been seen in an old capture and is not folded, so it would show as an unrecorded rename of the directory.
- A Write's kind read from its result text (I-35) rests on the wording of 2.1.296, found in its binary and seen in the `tools` capture; the binary of 2.1.306 holds the same two sentences. Another wording gives no kind, so such a Write is assumed to overwrite, as before. Since commit 656d025, `scripts/make-capture-fixture.py` keeps a `tool_result` text that starts with the create or update sentence, and `is_error`, so a reduced fixture keeps a subagent's Write kind; a fixture reduced before that holds `(elided)` there, and its subagent Writes have no kind.
- The Claude Code claim shapes rest on the ten paired captures above; the background Bash call (`run_in_background`), the subagent that writes a file and `NotebookEdit` on the `tools` fixture and one more raw capture. The in-place rewrite of a Write and an Edit rests on one raw capture (`shapes`, I-45); a NotebookEdit in place and the paths taken when a rename fails are unchecked. Unchecked: other versions, `MultiEdit` (not offered by 2.1.296 and reported as an unknown tool, I-42). A parallel block whose members started out of the order they were emitted was seen once, in the `shapes` capture (two Bash calls of one message exec'd in reverse order), and V-32 pairs it; concurrent subagents are unchecked (O-29). The Gemini adapter's shapes rest on one paired capture (I-50).
- A baseline rule names a family, not a file: one rule for a canonical path explains every member of the family in a run, such as every task's output file (I-38). Explaining never pairs, so a claim still needs the exact file (I-41). Three family patterns are unanchored (`/tasks/<id>.output`, `/fswatch-probe-<id>`, `.lock.tmp.<8 hex>`), so a workspace path of that shape is canonicalised for baseline matching too, and a rule explains it if a control produced the same canonical path. On the two `tools` fixtures every control's background Bash opens its own output file, so the rule explains the run's own too, and a trajectory that omits the Read of that file reads as honest. The attack evaluation scores that omission as undetectable by design (E-5), and reports both fixtures without gating on them, because fabrications and substitutions there are detected but, in an ambiguous alignment, sometimes located on another claim or joined by findings no mutation explains ([50_attack_generators.md](50_attack_generators.md)).
- The fold of the cwd file's read (I-43) reads the agent's process opening a file in `/tmp` and deleting it, both in one batch with nothing else of the process on `/tmp` between, as the harness's read of its cwd file, and a rule for the harness's own deletes explains the delete. Claude Code's file tools do not delete, so at level 0 only the harness produces that shape. The fold does not check for the root pid, which `NormalizeStream` does not receive; a descendant's file events are a command's content and no position changes. The batch bound of one microsecond rests on the probe's stamping (P-18) and on the measured gaps: at most 33 ns within a batch and at least 17 microseconds between batches on the paired captures. A claim on the literal path `/tmp/claude-N-cwd` pairs with the rewritten open.
- The third shape of the version lock's rewrite (I-44) is folded for the lock only, so a write of the lock by the agent's process in that shape reads as the harness's rewrite; the agent's files in the same shape are left alone and show as raw events. In the temporary shape, a write naming the target that the rename separates from the close (seen on two 2.1.286 runs of `paired-2.1.286-p17`, the task's and a control's lock rewrite) is not taken into the replace (I-34) and stays as a bare write of the lock; the rule for the folded write of the lock, which every run gives, explains it.
- The named shapes (P-25, I-56) rest on synthetic tests that mirror every fold test of the older shapes (`named_test.go` in both adapters) and on the kernel records measured with an unprivileged inode mark on kernel 6.17 ([12_probe_fs.md](12_probe_fs.md#technologies)), and on one capture of a harness with names, the fixture `paired-2.1.296-tools-named` (I-58): every replace of the task run folds. In one of its controls the subagent metadata's replace stayed raw, because the harness's write of the task's output file lay between the temporary's create and its open, where the fold requires the create to be the process's event just before the open; that temporary keeps its per-run id `agent-<id>.meta.json.tmp.<8 hex>`, so no other run explains it, and at full agreement the run's folded write of the metadata, which that control lacks, is unexplained harness activity. A replace whose destination the kernel merged into an earlier unread rename of the same target with an event on the target between (two replaces of one file read in one late batch, with a read of it between) has no destination the fold can account for and stays as raw events, which shows as unexplained or unrecorded on an honest run. The measurement behind P-25 found no ambiguous record once names are requested, so the I-39 and I-43 rewrites and the directory-covers-file fallback (V-18) are expected to apply to older captures only.
- The read that precedes a replace reaches the probe in one of two ways (I-39): as named opens of the file before the replace, or merged into a read-after-rename batch as an ambiguous open of the directory ahead of the directory's create and rename. The fold reads the second as an open of the target by the order of events in the batch; an ambiguous open of the directory by the agent's process that merely preceded an unrelated replace in that directory would be read the same way. The emitted open carries no input hash, so an Edit whose only read merged into the batch has its `input_hash` unverified (V-29). A `NotebookEdit` claims an open with no `input_hash`: the result's `original_file` matched the notebook's content before the edit on the first `tools` capture, but is not claimed. `updated_file` is the text before the harness converts it to the file's line endings and encoding (**Reported**, from the code of 2.1.296); its hash equalled the observed close's on the capture's LF, UTF-8 notebook, and a notebook with other line endings or encoding would read as a mismatch on an honest edit. A failed `NotebookEdit` claims nothing, so a read it made before failing shows as an unrecorded open.

At full agreement it is left out of the baseline. The capture script therefore takes more controls at a lower agreement threshold, and what still escapes is reported as unexplained harness activity when it is a file event in the harness's own directories (V-24), and as unexplained harness network activity when it is a connection to a host the adapter declares (V-34). A connection to another host and a command that the controls never showed are still findings: on `paired-2.1.306-tools` the package-manager probe ran in the task run and in four of the five controls, so at full agreement, the default of `cmd/baseline` (I-24) and of the attack evaluation, the honest run is NOT FAITHFUL on the probe's Unrecorded exec and its unexplained subtree (I-63). Occasional harness commands are open decision O-30 in [decisions/open.md](../decisions/open.md). The declared hosts are those the captures showed: a harness that refreshes or checks another endpoint only sometimes reads as NOT FAITHFUL until a capture shows it and a declaration names it. A tool that runs inside the harness's process, such as Claude Code's `WebFetch`, connects at level 0, so an unreported fetch from a declared host reads INCONCLUSIVE rather than NOT FAITHFUL (V-34).

An unclaimed such read of a file the harness opens at rest in the controls is therefore explained by the baseline and not detected, and a claimed one there is corroborated whether the agent or the harness opened the file (V-36). For Claude Code these paths include `~/.claude.json`, `~/.claude/remote-settings.json`, the session files and the transcripts; for agy they include its conversation databases, its logs and `bin/agentapi` under `~/.gemini/antigravity-cli`. - The declared sensitive files (I-59) rest on which files the harnesses' own processes opened and wrote in the checked captures and on the names in their binaries; a file a harness reads only when present, or under another configuration directory (`CLAUDE_CONFIG_DIR`), is not declared. Which key paths the harness changes at rest is measured for Claude Code 2.1.296 on one capture (I-60) and 2.1.306 on one (I-63), not for agy, whose files are checked whole on the evidence that they are settings only.
- The allowlist of `~/.claude.json` (I-60) is built from the strings of the 2.1.296 binary, whose `GLOBAL_CONFIG_KEYS`, `PROJECT_CONFIG_KEYS` and project defaults the binary of 2.1.306 holds unchanged (I-63); no other part of the 2.1.306 binary was compared: a key a later version reads to decide a permission, a trust or an MCP server is report-only until it is added, and a key the allowlist leaves out on purpose (the account record, onboarding and notice flags, migration flags) is never a finding.

- The Claude Code adapter's command recovery and id canonicalisation depend on the current wrapper and snapshot shapes (the shell, the preamble clauses, `&& eval`, the `pwd -P` suffix, `PATH_END_`), which are harness-version-specific. A version that changes the wrapper makes every Bash claim a mismatch until the allowlist is extended; that is the intended failure (D6, I-26).
- An Edit's content claims rest on the harness applying a plain string replacement of the strings its result reports, measured by the gate of I-31 (`TestProjectEditsClaimTheirContentAndAreCorroborated`) on the `edits` capture of 2.1.296: five Edits of different shapes, every one corroborated on both hashes. Another version that applies a different replacement shows as mismatches on every Edit, which is loud.
- An Edit's `input_hash` can be checked only on a file whose content the fs probe measured: the workspace at start, a file it saw written and settled, or a file created during the capture (P-22). An honest Edit of a pre-existing file outside the workspace is therefore INCONCLUSIVE with its `input_hash` unverified (V-29, `TestAnEditOfAFileTheProbeNeverHashedIsUnverified`), never confirmed and never a mismatch.
- A Read's content claim (I-40) is the text the harness returned, which equals the file's bytes only for a UTF-8 file without a byte order mark, CRLF line endings or a final CR, and, for a background task's output file, without the plugin hints the harness strips (**Reported**, from the code of 2.1.296). An honest Read of any other file reads as a mismatch; none was seen in a capture. A Read of a file the probe never measured is INCONCLUSIVE with its `input_hash` unverified (V-29). Since commit 6eaac57 `scripts/make-capture-fixture.py` keeps a Read's whole-file result, and its content only for a file in the run's workspace or its task directory that holds nothing private; the fixtures reduced before then claim no Read content, and `paired-2.1.296-tools`, `paired-2.1.296-tools-named` (three Reads each) and `paired-2.1.296-shapes` (two) exercise I-40. A subagent's Read never claims content, since its transcript has no structured result.
- The in-place fold (I-45) reads any direct write by the agent's process in that shape (an open, writes, the close, nothing else of the process between, no directory event around) as one write with the content's hash. An unclaimed one is still an Unrecorded write; a direct write in another shape, such as one without an open just before it, stays raw and shows as an unrecorded write and close. The fold tells the agent's process from a command by the absence of process events, since `NormalizeStream` does not receive the root pid: a descendant whose fork and exec the probe lost would be folded too, which changes no position, since its events are a command's content.
- Only `assistant` records state calls and only `user` records their results (I-62), as every checked capture shows. A version that moved a call into a record of another type would lose its claims, and its effects would show as Unrecorded events, not silently. Records of other types are not counted in the report.

A path the probe reports in another form than the `cwd` joined with the command's path (a symlink on the way) does not pair. A later version is not covered until its binary is read; its harness reads stay Unrecorded.
