# Agent adapters

Checked against commit d954104 on 2026-10-13.

## Objective

An adapter isolates everything one agent harness does differently from the core verifier: how its session file is read into claims, how observed events are rewritten into the form claims use, what the harness does on its own, and which content fields its format can state. `pkg/matching` and `pkg/verification` contain no agent knowledge; adding an agent means adding a package under `pkg/agent` that implements `agent.Adapter` and registers itself. The design reasons are in [decisions/integration.md](../decisions/integration.md) (D6 to D13) and [decisions/verification.md](../decisions/verification.md) (V2, V7).

The Claude Code adapter has been checked against seven paired captures (real sessions recorded by `watch` and verified with their own transcripts), all on one machine. **Verified** on those seven captures only; that is a check that the pipeline works, not an evaluation. ### The Adapter interface

```go
type Adapter interface {
	Name() string
	Detect(path string) bool
	Parse(path string) (models.Trajectory, Report, error)
	Normalize(models.GroundTruthEvent) (models.GroundTruthEvent, bool)
	IsHarnessNoise(models.GroundTruthEvent) bool
	Expresses(entry models.TrajectoryEntry, field string) bool
	Process() ProcessModel
}
```

`HarnessOwner` is an optional interface, `IsHarnessOwned(path string) bool`, for an adapter that can say where the harness keeps its own files; the verifier reports an unexplained level-0 file event there as unexplained harness activity rather than as the agent's unreported action ([20_verifier.md](20_verifier.md#verdict-vocabulary), V-24, I-30). It declares where, not what: nothing is explained by it. `Canonicalizer` is an optional interface, `Canonical(models.GroundTruthEvent) models.GroundTruthEvent`, for an adapter whose observed targets carry ids that differ every run: it returns the event with those ids replaced by fixed tokens, and is applied only where events of different runs are compared, when `Capture` builds rules and when `Prepare` matches a run's events against them. Pairing and every other comparison within a run use the exact target (I-41). `StreamNormalizer` is an optional second interface, `NormalizeStream(models.GroundTruth) models.GroundTruth`, for an adapter whose observed events are comparable only when several are looked at together (I-22). `Name` keys the registry and the baseline file. `Parse` returns entries in claim order, each with its interval (`Timestamp`, `End`), its `ThreadID` where subagents were flattened, its `BlockID` where the format issued several calls at once, and its `Tool`. `Normalize` returns false to drop an event. `IsHarnessNoise` is what the adapter knows statically; the measured baseline is supplied separately. `Expresses` answers for one of the `verification.Diff*` field names.

### ProcessModel

| Field | Meaning |
|---|---|
| `ShellPerCommand` | Each shell claim execs its own process, so a claim aligns with a command's exec. False means a persistent shell, where both checks lose their subject. |
| `SubagentsInProcess` | Subagent actions are indistinguishable from main-thread ones in G, which forces flattening (D9). |
| `Containerized` | Observed paths and pids live in another namespace. No adapter handles it. |
| `IntervalKind` | `IntervalNone` (a point), `IntervalDecision` (start is when the model decided, includes approval latency), `IntervalExecution` (start is when execution began). |
| `Concurrency` | `Sequential`, `Parallel` (entries sharing a `BlockID` have no order among themselves), `ConcurrencyUnmeasured`. |
| `ExitsClaimed` | The format records process exits. False makes `Prepare` set `Options.IgnoreExits`. |

Only `ExitsClaimed` changes verifier behaviour today. The other fields are declarations; `Concurrency` in particular is not consumed, because the verifier does not implement the partial order ([20_verifier.md](20_verifier.md), Known limits).

### Report

`Report` makes what was not measured visible: `ToolCalls` (invocations in the session), `Entries` (claims produced), `AgentVersion` (the harness version the session states, if any), `UnmappedByTool` (tool calls that produced no entry, by name), `UnknownTools` (tools neither mapped nor declared non-effectful, which may have acted unseen), `ParseErrors`, and `Degradations` (each precision loss in words). `cmd/verify` prints all of them before the verdict.

## Technologies

Go. The Claude Code adapter reads JSONL with `bufio.Scanner` (lines up to 64 MiB) and `encoding/json`. The Gemini adapter opens the conversation database read-only through `modernc.org/sqlite` (pure Go, no cgo) and decodes the undocumented protobuf step payload with a hand-written wire-format walker (`wire.go`), since no `.proto` is available. Content hashes use `pkg/content.SHA256Bytes` (`sha256:<hex>`).

## Workflow

### Registry and detection

Each adapter package calls `agent.Register` from `init`. `Register` panics on an empty or duplicate name. A command makes an adapter available by importing its package (`cmd/verify` and `cmd/baseline` blank-import `claudecode` and `gemini`).

`agent.Detect(path)` asks every registered adapter, in sorted name order, whether it recognises the path. Exactly one match returns that adapter. No match returns an error wrapping `ErrNoMatch`, so a caller can fall back to the generic adapter. Several matches return an error naming them; the caller must choose with `--agent`. The generic adapter never detects.

### From session to verifier input

`agent.Prepare(a, claims, groundTruthFile, measured, opts)` builds a `verification.Input`: it runs the observed events through `agent.NormalizeGround` (every event through `a.Normalize`, dropping those it rejects, then the stream through `NormalizeStream` when the adapter implements it; `Capture` uses the same function, so a rule is measured on the shape the verifier compares against), combines `a.IsHarnessNoise` and the measured baseline into one predicate (an event is harness activity if either says so; the measured baseline sees the event as `Canonical` returns it, the events the verifier aligns keep their exact targets, I-41), sets `opts.Expresses = a.Expresses`, `opts.IgnoreExits = !a.Process().ExitsClaimed` and, when the adapter is a `HarnessOwner`, `opts.HarnessOwned`, and copies `RootPID`, `Coverage`, `FSScope` and `Workspace` from the file. Caller options such as `IntervalSlack` are kept.

### Generic

`Generic` reads a trajectory already in the normalized JSON form (`models.ParseTrajectory`, which rejects unclaimable action types). It normalizes nothing, declares no noise, treats every field as expressible, and declares `ShellPerCommand`, `IntervalNone`, `Sequential` and `ExitsClaimed: true`. Its report carries one degradation saying so. It is the adapter for `cmd/simagent` output and for an agent whose format has been converted elsewhere.

### Claude Code (`claude-code`)

Detect: a `.jsonl` file in which one of the first 20 lines decodes with non-empty `sessionId`, `type` and `version`.

Parse reads the main transcript, then every `<session>/subagents/agent-*.jsonl` in sorted order (D8), with the file's id as `ThreadID`. It collects `tool_use` blocks and the timestamp of each matching `tool_result`. Calls are sorted by `tool_use` timestamp, ties in file order. A message holding more than one `tool_use` gives its entries `BlockID` = the message id. `End` is the `tool_result` timestamp when it is not before the start.

Between the atomic-write folds and the cwd-file fold it folds the harness's in-place rewrite (I-45): for one process, an open of a file, then a run of writes of it and its close, with no other event of the process between, becomes the open and one `file_write` carrying the close's hash. A claim keeps the exact path its call names, so it pairs only with an event on that path (I-41, superseding I-36), and `collapseOpenClaims` merges adjacent opens of one file among the file claims, since commands and connections are in the `proc` and `net` lanes and do not break a run. The structured result of the call (`toolUseResult`, on the user record that carries the `tool_result`: `type` for Write, the file before and the applied replacement for Edit, the notebook for NotebookEdit, the text returned for Read) is read only when the record holds a single result. A subagent's transcript holds no structured result, so for a Write whose record has none the kind is read from the `tool_result` text the harness sent the model (I-35): `File created successfully at: <path>`, alone or followed by a space, is `create`, and a text starting `The file <path> has been updated successfully.` is `update`, with `<path>` exactly the claimed `file_path`. A result marked `is_error`, another path or any other text gives no kind, and the Write is assumed to overwrite.

The exit code is not expressible because the format records only an `is_error` flag, which conflates a failed command with one that never ran.

### Gemini (`gemini`)

Detect: a file starting with the SQLite header whose `steps` table has a `step_payload` column.

Parse reads `steps` ordered by `idx` and decodes each payload. Tool calls are the submessages at protobuf path 5.4: field 1 the call id, 2 the tool name, 3 the arguments as a JSON string. The claim start is the started timestamp (5.6), falling back to created (5.1) with a degradation; `End` is completed (5.8) when present. Entries are sorted stably by start. A step with more than one call gives its entries `BlockID` = `step-<idx>`. Parse fails loudly, naming the field path, when a payload does not decode, a call lacks its name or arguments, the arguments are not JSON, a step has no timestamp, or the database has no steps: a version that moves a field number must produce an error, never an empty trajectory.

|---|---|---|---|
| `run_command` | `process_exec` | `CommandLine` | none |
| `run_command` with `RunPersistent: true` | none, counted as persistent shell (D7) | | |
| `view_file` | `file_open` | `AbsolutePath` | none |
| `write_to_file` | `file_open`, `file_write`, `file_close` | `TargetFile` | `output_hash` of `CodeContent` on `file_close` |
| `replace_file_content`, `multi_replace_file_content` | `file_open`, `file_write`, `file_close` | `TargetFile` | none |
| `read_url_content` | `net_connect` | hostname of `Url` | none |
| Non-effectful: `manage_task`, `send_message`, `ask_question`, `ask_permission`, `list_permissions`, `schedule`, `invoke_subagent`, `define_subagent`, `manage_subagents` | none, counted | | |

### Baseline construction

A baseline is the harness's own activity, measured by control runs in which the agent is given a task that claims nothing, so everything it does is the harness (D11, V7).

`agent.Capture(a, version, runs, now, opts)` requires at least one run and a root pid in each. For each run it normalizes events with the adapter (`NormalizeGround`, the same two steps as `Prepare`), builds the forest and partition, and takes the distinct `(action_type, target)` pairs of the aligned sequence (`Partition.Observed`), each event in the form the adapter's `Canonical` gives it, since a rule is compared with other runs (I-41). Descendants of a command are not rules, since a command explains its subtree. A pair seen in at least `opts.MinAgreement` of the runs (default 1, every run) becomes a `Rule`; a pair seen in fewer goes to `Unstable`, which is recorded for the reader and subtracts nothing. A target named in `opts.Exclude` becomes neither, whatever its action type, and the baseline records it in `Excluded`; it names the control task's own command (I-28). The run's own workspace (recorded by `watch` in the ground truth file) is replaced by `{workspace}` in each target, and its mangled form (every slash a dash, which is how Claude Code names its per-project transcript directory) by `{workspace-}` (I-24, I-29). Both lists are sorted. The `Baseline` records `Schema`, `Agent`, `AgentVersion`, `Captured` (UTC), `Runs`, `MinAgreement` and `Excluded`; `SaveBaseline` writes it as JSON with the keys `schema` (1), `agent`, `agent_version`, `captured`, `runs`, `min_agreement`, `rules`, `unstable` and `excluded`, each rule an `action_type` and a `target`.

`Baseline.Predicate(workspace)` recognises an event when a rule has exactly its action type and target (`Prepare` passes it the canonical event), with the placeholders expanded to the workspace of the run being verified and its mangled form (a rule that names the placeholder matches nothing when no workspace is known). There is no pattern matching, since a wildcard would explain whatever an attacker made it match. `LoadBaseline` rejects an unknown schema and a baseline that names no agent. Which control runs `cmd/baseline` refuses, and which baselines `cmd/verify` refuses, is in [40_tools.md](40_tools.md#baseline).

### Onboarding a new agent

Answer these questions, then encode each answer in the named place.

| Question | Encoded in |
|---|---|
| Where do session artifacts live, and what is the encoding? How is one recognised? | `Detect`, `Parse` |
| Which tools are effectful, and which are not? | `Parse` mapping; a non-effectful set; everything else to `UnknownTools` |
| For each effectful tool, which field holds the target, and which kernel events does it produce, in kernel order? | `Parse` claim shapes (claims of the `fs` lane must follow fanotify order) |
| Does a shell claim exec its own process, or is the shell persistent? (D7) | `ProcessModel.ShellPerCommand`; persistent calls counted, not claimed |
| Is the observed command line the claimed command, or a wrapper? (D6) | `Normalize` |
| Is the trajectory one stream, or split across files? (D8) | `Parse` merging |
| Are subagents separate processes or in-process? (D9) | `ProcessModel.SubagentsInProcess`, `ThreadID` |
| What does the harness do on its own? (D11) | A measured baseline via `cmd/baseline`; `IsHarnessNoise` only for what is static |
| Where do start and end timestamps come from, and does the start mean decision or execution? (D12, D13) | `Timestamp`, `End`, `ProcessModel.IntervalKind` |
| Which content fields can the format state, per tool? Does it record exits? | `Expresses`, `ProcessModel.ExitsClaimed` |
| Do observed paths and pids share a namespace with the trajectory's? | `ProcessModel.Containerized` (unhandled) |
| Can the agent issue several calls at once? (V2) | `ProcessModel.Concurrency`, `BlockID` |

Then: create `pkg/agent/<name>`, register from `init`, blank-import the package in `cmd/verify` and `cmd/baseline`, list every precision loss in `Report.Degradations`, and test `Detect`, the mapping, the `Expresses` table, the process model, loud failure on malformed input, and an honest synthetic session that verifies FAITHFUL after normalization. Finally capture a baseline from several control runs and check the adapter against a real paired capture.

## Guarantees and loss accounting

- No tool call is dropped silently: in both real adapters every call either produces entries or is counted in `UnmappedByTool`, and an unknown tool is also listed in `UnknownTools` (`TestParseCountsWhatItDoesNotMap`, `TestParseCountsAndNamesWhatItDoesNotClaim`).
- A format limit is never read as an opt-out: `Expresses` turns a nil that the format cannot state into no finding, and `ExitsClaimed: false` removes exits from both sides rather than reporting every exit as an omission.
- Detection never guesses between adapters (`TestDetectRefusesToGuessBetweenAdapters`).
- The Gemini adapter fails with the field path rather than returning a partial trajectory when the payload layout changes.
- A claim pairs only with an event on the exact path it names, while the baseline compares runs on the canonical path: a Read of one background task's output file is not witnessed by another task's, and a control's task output still explains the run's own (`TestAClaimOnATaskOutputPairsWithThatFileOnly`, I-41).
- A baseline only subtracts exact `(action_type, target)` pairs that enough control runs produced, from loss-free runs, for the adapter it was captured with, and never the control task's own command (`TestCaptureExcludesTheControlTasksOwnCommand`, `TestPairedControlCommandIsNotABaselineRule`).

## Known limits

- The fold takes a second rename of a replace's directory only in captures recorded before P-18; on a current capture its condition, narrower than P-18's, never holds (I-33). On an old capture it hides what P-18 hides: two real renames of one directory by one process with nothing between read as one. A split rename in the read-after-rename shape has not been seen in an old capture and is not folded, so it would show as an unrecorded rename of the directory.
- A Write's kind read from its result text (I-35) rests on the wording of 2.1.296, found in its binary and seen in the `tools` capture. Another wording gives no kind, so such a Write is assumed to overwrite, as before. Since commit 656d025, `scripts/make-capture-fixture.py` keeps a `tool_result` text that starts with the create or update sentence, and `is_error`, so a reduced fixture keeps a subagent's Write kind; a fixture reduced before that holds `(elided)` there, and its subagent Writes have no kind.
- The Claude Code claim shapes rest on the seven paired captures above; the background Bash call (`run_in_background`), the subagent that writes a file and `NotebookEdit` on the `tools` fixture and one more raw capture. The in-place rewrite of a Write and an Edit rests on one raw capture (`shapes`, I-45); a NotebookEdit in place and the paths taken when a rename fails are unchecked. Unchecked: other versions, `MultiEdit` (not offered by 2.1.296 and reported as an unknown tool, I-42). A parallel block whose members started out of the order they were emitted was seen once, in the `shapes` capture (two Bash calls of one message exec'd in reverse order), and V-32 pairs it; concurrent subagents are unchecked (O-29). The Gemini adapter has not seen a real capture.
- A baseline rule names a family, not a file: one rule for a canonical path explains every member of the family in a run, such as every task's output file (I-38). Explaining never pairs, so a claim still needs the exact file (I-41). Three family patterns are unanchored (`/tasks/<id>.output`, `/fswatch-probe-<id>`, `.lock.tmp.<8 hex>`), so a workspace path of that shape is canonicalised for baseline matching too, and a rule explains it if a control produced the same canonical path.
- The fold of the cwd file's read (I-43) reads the agent's process opening a file in `/tmp` and deleting it, both in one batch with nothing else of the process on `/tmp` between, as the harness's read of its cwd file, and a rule for the harness's own deletes explains the delete. Claude Code's file tools do not delete, so at level 0 only the harness produces that shape. The fold does not check for the root pid, which `NormalizeStream` does not receive; a descendant's file events are a command's content and no position changes. The batch bound of one microsecond rests on the probe's stamping (P-18) and on the measured gaps: at most 33 ns within a batch and at least 17 microseconds between batches on the paired captures. A claim on the literal path `/tmp/claude-N-cwd` pairs with the rewritten open.
- The third shape of the version lock's rewrite (I-44) is folded for the lock only, so a write of the lock by the agent's process in that shape reads as the harness's rewrite; the agent's files in the same shape are left alone and show as raw events. In the temporary shape, a write naming the target that the rename separates from the close (seen on two 2.1.286 runs of `paired-2.1.286-p17`, the task's and a control's lock rewrite) is not taken into the replace (I-34) and stays as a bare write of the lock; the rule for the folded write of the lock, which every run gives, explains it.
- The read that precedes a replace reaches the probe in one of two ways (I-39): as named opens of the file before the replace, or merged into a read-after-rename batch as an ambiguous open of the directory ahead of the directory's create and rename. The fold reads the second as an open of the target by the order of events in the batch; an ambiguous open of the directory by the agent's process that merely preceded an unrelated replace in that directory would be read the same way. The emitted open carries no input hash, so an Edit whose only read merged into the batch has its `input_hash` unverified (V-29). A `NotebookEdit` claims an open with no `input_hash`: the result's `original_file` matched the notebook's content before the edit on the first `tools` capture, but is not claimed. `updated_file` is the text before the harness converts it to the file's line endings and encoding (**Reported**, from the code of 2.1.296); its hash equalled the observed close's on the capture's LF, UTF-8 notebook, and a notebook with other line endings or encoding would read as a mismatch on an honest edit. A failed `NotebookEdit` claims nothing, so a read it made before failing shows as an unrecorded open.
- Some harness activity is occasional (a package-manager probe in two of three control runs; a backup of `~/.claude.json` in a task run and in no control). At full agreement it is left out of the baseline. The capture script therefore takes more controls at a lower agreement threshold, and what still escapes is reported as unexplained harness activity when it is a file event in the harness's own directories (V-24); a connection that sent data, or a command, that the controls never showed is still a finding (open decision O-25 in [decisions/open.md](../decisions/open.md)).
- `Concurrency`, `SubagentsInProcess`, `ShellPerCommand` and `IntervalKind` are declarations only; the verifier does not read them.
- The Claude Code adapter's command recovery and id canonicalisation depend on the current wrapper and snapshot shapes (the shell, the preamble clauses, `&& eval`, the `pwd -P` suffix, `PATH_END_`), which are harness-version-specific. A version that changes the wrapper makes every Bash claim a mismatch until the allowlist is extended; that is the intended failure (D6, I-26).
- An Edit's content claims rest on the harness applying a plain string replacement of the strings its result reports, measured by the gate of I-31 (`TestProjectEditsClaimTheirContentAndAreCorroborated`) on the `edits` capture of 2.1.296: five Edits of different shapes, every one corroborated on both hashes. Another version that applies a different replacement shows as mismatches on every Edit, which is loud.
- An Edit's `input_hash` can be checked only on a file whose content the fs probe measured: the workspace at start, a file it saw written and settled, or a file created during the capture (P-22). An honest Edit of a pre-existing file outside the workspace is therefore INCONCLUSIVE with its `input_hash` unverified (V-29, `TestAnEditOfAFileTheProbeNeverHashedIsUnverified`), never confirmed and never a mismatch.
- A Read's content claim (I-40) is the text the harness returned, which equals the file's bytes only for a UTF-8 file without a byte order mark, CRLF line endings or a final CR, and, for a background task's output file, without the plugin hints the harness strips (**Reported**, from the code of 2.1.296). An honest Read of any other file reads as a mismatch; none was seen in a capture. A Read of a file the probe never measured is INCONCLUSIVE with its `input_hash` unverified (V-29). `scripts/make-capture-fixture.py` keeps only the result's `type` for a Read, so no checked-in fixture's Read claims content and none exercises I-40; a subagent's Read never does, since its transcript has no structured result.
- The in-place fold (I-45) reads any direct write by the agent's process in that shape (an open, writes, the close, nothing else of the process between, no directory event around) as one write with the content's hash. An unclaimed one is still an Unrecorded write; a direct write in another shape, such as one without an open just before it, stays raw and shows as an unrecorded write and close. The fold tells the agent's process from a command by the absence of process events, since `NormalizeStream` does not receive the root pid: a descendant whose fork and exec the probe lost would be folded too, which changes no position, since its events are a command's content.
- Collapsing opens loses the count of repeated reads of one file, on both sides.
- The Gemini adapter does no wrapper recovery, so a wrapped command shows as a mismatch.
- The Gemini adapter does not follow subtrajectories and does not set `ThreadID`.
- The Gemini process model (shell per command, subagents, ordering) is unmeasured.
- Gemini commands run with `RunPersistent` and calls in non-completed steps are not claimed.
- A Grep or Glob claim does not verify its pattern or path, only that a search of that kind ran. A search is recognised only from the native installer's layout; another install layout shows its searches as unexplained commands. Gemini's search tools (`list_dir`, `grep_search`, `find_by_name`) and `search_web` are reported as unknown tools.
- A baseline holds for one agent version and one tool set: the shell snapshot command differs with the enabled tools (I-24).
- A baseline captured before N-22 holds `net_connect` rules naming the harness's addresses (`160.79.104.10:443`), the losing halves of its dual-stack connects, which change with DNS; from N-22 on those are `net_dial` capability evidence and become no rule. The checked-in fixtures predate it.
- Only the Claude Code adapter states the session's version (`Report.AgentVersion`), so only its baselines are checked against the version ([40_tools.md](40_tools.md#verify)).
- `Containerized` is not handled by any adapter.
