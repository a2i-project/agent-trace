# Command-line tools

Checked against commit aaea306 on 2026-11-01.

## Objective

Seven commands turn the probes, adapters and verifier into a workflow: `watch` records ground truth while an agent runs, `baseline` measures a harness's own activity from control runs, `verify` compares a trajectory with a capture and prints a verdict, `status` says whether the agents installed on the machine are at versions the adapters were verified against and whether the kernel meets the probes' stated minimums (I-57), `attack` mutates a trajectory for evaluation (see [50_attack_generators.md](50_attack_generators.md)), `simagent` is a simulated agent that exercises the whole chain in tests, and `analyze` computes the evaluation's numbers and verdicts from a campaign directory (see below). The probes are described in [10_probes_common.md](10_probes_common.md), the verifier in [20_verifier.md](20_verifier.md) and the adapters in [30_agent_adapters.md](30_agent_adapters.md).

### watch

Launches or attaches to an agent, runs the selected probes, prints each event as it arrives, and writes the capture when recording ends.

| Flag | Default | Meaning |
|---|---|---|
| `--workspace PATH` | (required) | The agent's working directory: hashed at start, kept for every process in the capture, and named by the baseline placeholder. The fs probe itself watches every real filesystem (P-17) |
| `--probes LIST` | `fs,proc` | Comma-separated probes from `fs`, `proc`, `net` |
| `--proc-filter PREFIX` | empty | Only report processes whose command line has this prefix; replaced by ancestry scoping when a command or `--root-pid` is given |
| `--out PATH` | `ground_truth.json` | Output file |
| `--buf N` | 4096 | Per-probe event channel size |
| `--root-pid N` | 0 | Attach the ancestry root to a running process instead of launching one; needs the proc probe; exclusive with `-- <command>` |
| `--net-exe-path PATH` | empty | TLS library (for example `libssl.so.3`) for the `SSL_write` uprobe, the content method `tls-symbols`; empty means identity only |
| `--net-content METHOD=PATH` | none | a content method and the file it hooks, repeatable (N-39): `tls-symbols` (as `--net-exe-path`), `tls-openssl-ex`, `tls-rustls-aead`; at most one of the first two; an unknown method, or a file whose anchors are not found, fails the start |
| `--net-cache-path PATH` | `$TMPDIR/agent-trace-tlsoffset-cache.json` | Cache of computed TLS offsets |
| `--agent NAME` | every adapter | Adapter whose security-sensitive harness files are snapshotted (I-59); an unknown name is an error. Without it, the files every registered adapter declares |
| `--agent-home DIR` | home of `$SUDO_UID`, else root's | Home of the user the agent runs as, which a declared `~/` file resolves against; every snapshotted file must belong to its owner |

Modes: with a trailing `-- <command> [args]`, `watch` starts the command stopped before its exec, makes its pid the proc probe's ancestry root and the net probe's tracked pid, then lets it run (P-23), waits for it to exit (Ctrl+C kills it) and writes the file; the launch sequence, the output pipe and the wait for trailing events are in [10_probes_common.md](10_probes_common.md#how-cmdwatch-builds-and-starts-probes). With `--root-pid N` it attaches to that process and records until Ctrl+C; anything the process did before is invisible to the proc probe. With neither it records host-wide until Ctrl+C and writes `root_pid` as zero, which the verifier treats as INCONCLUSIVE.

`watch` requires root (fanotify and eBPF) and refuses a probe that does not implement `probe.CoverageReporter`. The output file is a `models.GroundTruthFile` ([10_probes_common.md](10_probes_common.md#ground_truthjson)); before writing it, `watch` applies the scope rule to file events ([10_probes_common.md](10_probes_common.md#how-cmdwatch-builds-and-starts-probes)), and writes into `fs_scope` the fs probe's mount table and whether it changed during the capture (P-33). When it has a root pid, it prints one line with the marked and unmarked filesystem counts and the count dropped by the scope rule; in every mode it prints a warning per action type with the count of file events whose path could not be resolved (counted, not recorded), a warning with how many of those the agent's tree caused when any did (event loss, V-39), and a warning per filesystem it could not mark. It then sets the fs probe's `HashlessCloses` to the closes the capture keeps that carry no content hash, and prints one `fs probe:` line with that count and the probe's own, every close it published without a hash on any marked filesystem (P-40). It applies the scope rule before it prints and judges the coverage, since the rule supplies those counts. On exit it prints the net probe's diagnostic counts when it ran (connections, with a hostname, with content, unattributed, unsupported, DNS connections, address probes, connections emitted at the stop, connections replaced by a new connect on their descriptor, dials; [13_probe_net.md](13_probe_net.md)), a warning with the reason request content capture is inactive, a `net probe responses:` line with the state of response capture (`active`, `identity_only` or `attach_failed`, N-29) and its counters (responses emitted, unpaired, unattributed, incomplete, truncated, unparsed, server-sent events, reads discarded before validation, read faults, reads the ring buffer discarded) and a warning with `ResponseAttachError`, the reason response capture is inactive, when it is, then, with content capture, a `net probe content methods:` line with each configured method's request and response state and, when any WebSocket or rustls count is above zero, a `net probe websocket:` line with them (upgrades, accepted, requests, server messages, refused, unparsed, rustls frames unvalidated, unbound, rebound, unpaired; N-40, N-41); then each probe's loss counters, `hashlessCloses`, `undrainedRecords`, `unresolvedPaths`, `unresolvedInTree` and `responseGaps` included, each followed, for a probe that recorded diagnostics, by one `<probe> probe diagnostics:` line (`diagnosticsLine`) with each ring's size, high-water mark, records read and drops (and, on the TLS ring, read drops), each tracked set's capacity, peak and entries at the stop, the net probe's content counters, and, where measured, its `SSL_write` counts (`sslWrites calls= partial= failed= bytesRequested= bytesWritten=`, N-36) ([10_probes_common.md](10_probes_common.md#diagnostics)), and logs a warning when `verification.Assess` judges the capture incomplete.

Before the agent is released (or, with `--root-pid`, at attach) and again once the probes have stopped, `watch` snapshots the harness's security-sensitive files (V-40): it reads each declared file that is a regular file of the agent's user, no larger than 16 MiB, and writes into the capture's `sensitive` record each file's state at both ends and the changes between them by key path and kind, never a value ([10_probes_common.md](10_probes_common.md#ground_truthjson)). It prints one line with the number of files snapshotted, the home they were resolved under, and how many changed with how many changes. The record is written whenever some file is declared; a failure to find the agent's home is logged and leaves the record out.

| Exit code | When |
|---|---|
| 0 | Capture written |
| 1 | Any error (`log.Fatal`): missing workspace, not root, unknown probe, probe start failure, write failure. Also when the launched agent exits with an error, after the file has been written. |
| 2 | Flag parse error (Go `flag` default) |

### verify

Reads a trajectory through an adapter and a capture, runs `verification.Verify`, and prints the report.

| Flag | Default | Meaning |
|---|---|---|
| `--trajectory PATH` | (required) | The agent's own session file, or normalized trajectory JSON |
| `--ground-truth PATH` | (required) | Capture written by `watch` (object form, or a legacy bare array) |
| `--agent NAME` | detect | `claude-code`, `codex`, `gemini` or `generic` |
| `--baseline PATH` | none | Baseline written by `baseline` |
| `--normalized` | off | Read `--trajectory` as normalized trajectory JSON (what `attack` writes), using `--agent` only for the ground truth side |
| `--interval-slack D` | `500ms` | Widen each claim interval on both sides, because the probes and the agent do not share a clock |
| `--ignore-exits` | false | Do not align process exits even if the adapter's format records them |
| `--json PATH` | none | Also write the whole verdict as JSON: the inputs, the parse report, every alignment list, the coverage, and each command with its exec, exit, every event beneath it and its capability evidence |
| `--check-trace-hash` | off | Compare the session file read with the last content the probe hashed of the session's declared main file, and read a difference as a damaged trace (V-59). Only for a file the capture left unmodified, as the capture script's own verify runs read it: a fixture whose transcript was rewritten when it was made differs |
| `--strict-version` | off | Make the run INCONCLUSIVE when the session's agent version is not configured or not known (I-57) |
| `--agent-version V` | none | The version of the agent that recorded the session, for a format that does not state it (agy's) |
| `--config PATH` | located | The agent version config, `config/agents.json` ([30_agent_adapters.md](30_agent_adapters.md#configured-agent-versions)); located as `status` does |

Adapter choice: `--agent` selects by name (an unknown name is an error). Without it, `agent.Detect` runs; no match falls back to `generic`, and several matches are an error asking for `--agent`. A baseline whose `agent` differs from the chosen adapter's name is refused, and so is one whose `agent_version` differs from the version the session states (the Claude Code transcript records it on every line; a format that states none is not checked). Without a baseline, a non-generic adapter's report gains a degradation saying the harness's own activity will read as unexplained. `--ignore-exits` can only add to the adapter's choice: an adapter with `ExitsClaimed: false` always ignores exits.

The session's trace (V-59, I-74): for an adapter that declares its trace (Claude Code, Codex) and is chosen with `--agent claude-code` or `--agent codex`, `verify` reads the session with `agent.ReadTrace`, so a `--trajectory` that does not exist, holds no byte, that the adapter cannot read or of which some record does not parse is not an error: the claims are not aligned and the run is INCONCLUSIVE (exit 2) with the reason "cannot verify: the trace was deleted or damaged (<state>: <detail>)" first, or NOT FAITHFUL (exit 1) when the capture shows the trace was tampered with. The declaration of the adapter also makes every write, truncation, rename or delete of a declared trace file by a process other than the agent's own, and every write-class claim of one, a trace-tampering finding. An adapter that declares no trace, `--normalized` and the generic adapter keep exit 3 for a trajectory that is missing or does not parse. Without `--agent`, `agent.Detect` opens the file, so a missing, empty or garbled Claude Code transcript is not detected as Claude Code, falls back to the generic adapter and exits 3; the capture scripts always pass `--agent`. With a missing transcript the session states no version, so under `--strict-version` the version's reason joins the trace's unless `--agent-version` is given.

Agent version check (I-57): `verify` compares the session's agent version with the versions `config/agents.json` lists for the adapter. The version is the one the session states (`Report.AgentVersion`: a Claude Code transcript states it on every record), else `--agent-version`; a flag that contradicts the session's version is exit 3. agy's conversation database states none, so a Gemini session's version is unknown without the flag. The check has six outcomes, written to the JSON report as `agent_version_check`: `configured`; `not configured` (a version the adapter's entry does not list); `adapter not configured` (the config has no entry for the adapter); `unknown` (no version); `not applicable` (the generic adapter, which stands for no agent); and `no config` (no file found). `not configured`, `adapter not configured` and `no config` print a `WARNING:` line right after the report's title: the first names the version, the file and the configured versions, the second the file and the adapter, the third that no config was found; by default the verdict and the exit code are unchanged, so a configured fixture's report is byte-identical to the one before the check. `--strict-version` makes a `not configured`, `adapter not configured` or `unknown` run INCONCLUSIVE, whatever the verdict would have been, with the version reason first among the reasons and, when the run had findings, their number: they stay listed, and the verdict no longer asserts them, since an adapter that does not fit the version can make them. Under `--strict-version` a missing config is exit 3. The JSON report carries `agent_version` and `agent_version_source` (`session` or `--agent-version`) when a version is known, and `agent_version_configured` (true or false) only when the check decided it.

The report, on standard output, contains in order:

1. the agent version `WARNING:` line, when the check above prints one;
2. the inputs: entry count, adapter, event count, root pid, the capture's fs scope with one line per action type, in sorted order, counting the file events with no resolvable path, or a note that the capture predates the record, baseline rules and runs, and, when the baseline holds `file_open` rules that apply to the run, a `limitation:` line with their number: the paths the harness opens at rest, whose unclaimed in-process read the baseline explains and no report can show (V-36). A rule naming the workspace placeholder counts only when the capture records a workspace, as in `Baseline.Predicate`, and a canonical rule standing for a family of per-run paths (I-41) counts once; and, when it holds `file_write`, `file_close`, `file_rename` or `file_delete` rules that apply to the run, a second `limitation:` line with the number of distinct paths they name, counted the same way: the paths the harness writes at rest, whose unclaimed in-process write the baseline explains (V-37); and, when the baseline holds command rules but no subtree records (a file written before V-38), a `limitation:` line with the number of command rules, each of which then explains every event beneath its command; and, only when the capture holds a snapshot of the harness's sensitive files (V-40), a `sensitive:` line, either with the number of files checked against the controls, their changes, how many the controls and a claimed write explained, how many nothing explained under the files' security-relevant keys, and how many nothing explained outside them (`report-only outside the security-relevant keys`, V-41), or, when the baseline holds no record of the controls' changes (none supplied, or built from controls without a snapshot), with the number of changes not checked, followed by one `limitation:` line per file that could not be checked (not named by the snapshot, not read at either end, not measured by the controls), the line saying nothing was checked without a record, or, when changes were checked, the line saying a change made and reverted before the capture stopped is not seen;

4. the alignment counts: Corroborated, then, only when some corroborated read paired with an open the baseline also explains, `Corroborated, shared with the harness: N of them` (V-36), Mismatched, Its `alignment` object gains `corroborated_harness_shared`, the pairs also listed in `corroborated`, only when some corroborated read paired with an open the baseline also explains (V-36). Its `alignment` object gains `baselined_writes_outside_harness` only when some level-0 write a baseline rule explained lies outside the harness's declared directories, and the report gains a top-level `resting_writes`, the sorted paths of the second limitation line, only when there are any (V-37). It gains a top-level `sensitive` object only when the capture holds a snapshot of the harness's sensitive files (V-40): `checked`, `files`, `changes`, `baselined`, `claimed`, the `unexplained`, `other` (report-only, V-41) and `unchecked` changes (each `file`, `path`, `key`, `kind` and `entries`) and the `limitations`; an unexplained change counts in `findings`, an `other` one does not. Its `alignment` object gains `unexplained_harness_net` only when some connection to a declared harness host is unexplained (V-34), and `unexplained_harness_commands`, the exec of each, only when some declared harness command is unexplained (V-43). Its `alignment` object gains `harness_bookkeeping`, the events the adapter's bookkeeping declaration explained, only when there are any (V-50), and `harness_housekeeping`, the connections and requests the adapter's housekeeping declaration explained, only when there are any (V-54); `verify` builds both declarations from the version the session states, never from `--agent-version`. It gains a top-level `trace` object only when the trace could not be read or its content was compared (V-59): `declared`, `state` (`missing`, `empty`, `unparsable`, `damaged`, `differs`), `detail`, `files` (each declared main session file the capture observed, its `events` and its `last_write` event), `compared` and `note`; and a top-level `trace_tampering` only when there is evidence, each with its `event` or `claim`, `zone` (`subtree`, `outside` or `claim`), `level` and `command`, counted in `findings`. It gains a top-level `server_calls` only when the session holds server-side calls: each `call` (`tool`, `id`, `request_id`, `host`, `timestamp`), `corroborated`, the joined `response` and the `reason`; the `parse` object then carries the calls as `server_calls` (V-45). Its `coverage` object carries `baselined` (events beneath baselined commands) and `baselined_level_zero` (the agent process's own events the baseline explained). It gains `orphans` only when some process's parent was never seen: each `pid`, `ppid`, `start` and, when it exec'd, its first `exec`. A write error on `--json` is exit 3 after the text report has been printed.

| Exit code | When |
|---|---|
| 0 | FAITHFUL |
| 1 | NOT FAITHFUL (advisory findings included) |
| 2 | INCONCLUSIVE |
| 3 | Usage or I/O error: missing flag, unknown agent, ambiguous detection, unreadable or invalid trajectory (a normalized one that names `implied_by` included, V-33), ground truth or baseline, baseline for another agent or for another version of the agent, an `--agent-version` the session contradicts, an unreadable or invalid agent version config, or none found under `--strict-version`. `-h` also exits 3. |

Exit 3 is separate from 1 so that a failure to verify can never be read as NOT FAITHFUL.

### baseline

Builds a harness baseline from control runs with `agent.Capture` and writes it with `agent.SaveBaseline`.

```
baseline --agent NAME --agent-version V [--out FILE] [--exclude TARGET]... CONTROL_RUN.json...
```

| Flag | Default | Meaning |
|---|---|---|
| `--agent NAME` | (required) | Adapter that normalizes the runs |
| `--agent-version V` | (required) | Version of the agent that was run; a baseline holds for one version |
| `--out PATH` | `baseline.json` | Output file |
| `--min-agreement F` | `1` | Fraction of control runs that must perform an action for it to become a rule. Lower it for activity the harness does only sometimes, at the cost of a wider baseline (I-24). |
| `--exclude TARGET` | none | A target that never becomes a rule, whatever its action type. Repeatable. It names the command the control task itself was told to run (I-28; semantics in [30_agent_adapters.md](30_agent_adapters.md#baseline-construction)). |

Each positional argument is a capture from `watch`. A run with no coverage record, with any loss counter set, or with no root pid is refused. On success it prints the number of rules, runs and the agreement used, and how many unstable actions were left out, then how many command rules it recorded the subtrees of and how many actions beneath them a baselined command explains (V-38), then, only when it recorded any, how many declared harness commands that are no rule it recorded the subtrees of, counted over the controls that ran each, and how many actions beneath them (V-43), then, when it recorded what the controls changed in the adapter's sensitive files, of how many declared files and with how many changes kept and unstable (V-40), or, for an adapter that declares sensitive files, a note that some control holds no snapshot and no record was made, and notes when given a single run that one run cannot separate stable from incidental activity.

The baseline file format, and the placeholder that names the watched directory, are in [30_agent_adapters.md](30_agent_adapters.md#baseline-construction).

| Exit code | When |
|---|---|
| 0 | Baseline written |
| 3 | Usage error (missing flag or no runs, unknown agent, `-h`), unreadable or invalid capture, refused control run, write failure |

### status

Reports whether this machine's agents are at versions the adapters were verified against (I-57). It reads `config/agents.json` and, for each adapter in it, prints the configured versions with the date each was verified and its number of fixtures, then looks the adapter's `binary` up on `PATH`, runs it with its profile's version command (`version_command.args`, `--version` when the profile gives none; 20 s timeout) and takes the first version-shaped word of the output (`2.1.296 (Claude Code)` and `1.3.4` both give the version). It runs nothing else and needs no root.

```
status [--config PATH] [--agent NAME]
```

| Flag | Default | Meaning |
|---|---|---|
| `--config PATH` | located | The config file. Without it: `$AGENT_TRACE_CONFIG`, which must exist when set; else `config/agents.json` beside the executable (where `make build` puts the binaries); else in the nearest directory at or above the working directory that holds it and a `go.mod` (a checkout, where `go run` and `go test` start) |
| `--agent NAME` | all | Check only this adapter's agent |

It also prints the kernel release (`uname`) against each minimum a probe page states: the fs probe's `FAN_REPORT_DFID_NAME`, 5.9 ([12_probe_fs.md](12_probe_fs.md#known-limits)), and the net probe's `bpf_probe_read_kernel`, 5.5 ([13_probe_net.md](13_probe_net.md)), each `ok`, `BELOW` or `unknown`. The kernel line does not change the exit code. On this machine on 2026-10-15 it printed `kernel: 6.17.0-41-generic`, both minimums `ok`, `installed: 2.1.296 at ~/.local/bin/claude: configured` and `installed: 1.3.4 at ~/.local/bin/agy: configured`.

| Exit code | When |
|---|---|
| 0 | Every agent on `PATH` is at a configured version (an agent not on `PATH` is listed, not a failure) |
| 1 | An agent on `PATH` is at a version the config does not list, or its `--version` failed or printed no version |
| 2 | With `--agent`, that agent is not on `PATH` |
| 3 | Usage error, an adapter `--agent` names that the config lacks, or a config that is missing, unreadable or invalid |

### attack

Mutates a trajectory with one of the generators in `pkg/attack` and writes the result and a record of the change.

```
attack --kind omission|fabrication|substitution|interval-widening [--n N] [--seed S]
       --trajectory FILE [--agent NAME | --normalized] [--select all|sensitive]
       [--field F] [--retime] [--avoid-ground-truth FILE] [--out FILE] [--record FILE]
```

The mutated trajectory is normalized JSON (it keeps each claim's `tool`, which the adapter's per-tool declaration needs), so it is verified with `verify --normalized --agent NAME`. Harness-implied claims the adapter derived are dropped before the mutation, with a note on standard error, since they are not the agent's and normalized JSON cannot carry them (V-33). Exit 0 when both files are written, 3 for usage and I/O errors and for a mutation the trajectory does not admit; nothing is written then. The same seed and flags give the same mutation.

### simagent

A simulated agent that performs a fixed script of actions in a workspace and writes the trajectory it claims, in the normalized JSON form the generic adapter reads. It does not need root; `watch` does.

| Flag | Default | Meaning |
|---|---|---|
| `--workspace PATH` | (required) | Directory to act in |
| `--trajectory-out PATH` | (required) | Where to write the trajectory |
| `--file-only` | false | Skip the `wc` step, for runs with no proc probe |
| `--shell-cmd SCRIPT` | empty | Run `/bin/sh -c SCRIPT` (`{ws}` expands to the workspace) and claim only the shell's exec (with an interval) and exit, not what the script spawns |
| `--fetch-url URL` | empty | Make an HTTPS request and claim it |
| `--fetch-via-curl` | false | Make the request with a `curl` child (HTTP/1.1, pinned to one IPv4 address) and claim the curl exec and exit instead of the connection |
| `--fetch-method M`, `--fetch-body B` | `GET`, empty | Request method and body |
| `--emit-net-request` | false | Also claim a `net_request` with the body hash; refused with `--fetch-via-curl` |
| `--drop-entry N` | -1 | Remove claim N before writing |
| `--attack MODE` | empty | Tamper with the trajectory, below |
| `--null` | false | Act on nothing and write an empty trajectory (`[]`): a control run for a baseline of `simagent`'s own start-up and exit (I-67); refused beside any flag above that acts or tampers |

The fixed script, in claim order: write `file1.txt` (claimed in kernel order as `file_write` create, `file_open`, `file_write`, `file_close` with the content hash), rename it to `file2.txt` (`file_rename` of `file1.txt`, then of `file2.txt`: the probe reports a rename as its source and its destination, P-25), run `<abs path of wc> -l file2.txt` (`process_exec`, `process_exit` with its code) unless `--file-only`, the optional shell command, delete `file2.txt` (`file_delete`), then the optional fetch. Without `--fetch-via-curl` the request is made in-process over a single pinned IPv4 connection and claimed as `net_connect` to the host.

| `--attack` | Tampering | Expected finding |
|---|---|---|
| `omission` | Drop the first claim (only when `--drop-entry` is not set) | Unrecorded |
| `fabrication` | Append `process_exec /usr/bin/curl https://example.com` | Unwitnessed |
| `substitution-exit` | Add 1 to the first claimed exit code | Mismatched (`exit_code`) |
| `substitution-hash` | Replace the first `file_close` output hash with zeros | Mismatched (`output_hash`) |
| `substitution-cmd` | Append ` --fake-flag` to the first `process_exec` | Mismatched (`target`) |
| `net-omission` | Drop every `net_connect` claim | Unrecorded |
| `net-fabrication` | Append `net_connect ghost.example.invalid` | Unwitnessed |

An `--attack` value not in the table is a usage error: `simagent` prints it with the flag list and exits 3, as the other commands do for a usage error, before it acts or writes anything, so a mistyped scenario cannot run as an honest one. `--null` beside `--drop-entry`, `--file-only`, `--attack`, `--fetch-url`, `--shell-cmd`, `--fetch-method`, `--fetch-body`, `--emit-net-request` or `--fetch-via-curl` is the same usage error, so a control run cannot do part of the script. A null run loads the local time zone, which the script's runs do when they format their first timestamp, so its capture opens the same zone file; apart from the script's actions and the command's stdio, its process opens what a run of the script opens (checked with `strace` on 2026-10-26). Exit codes: 0 on success, 3 for an unknown `--attack` value, 2 for a malformed flag (the `flag` package's own exit), 1 on any other failure (`log.Fatal`), a missing required flag included.

### analyze

Computes every number of the experiment protocol from a campaign directory, in process, and writes `results.json` (each number, count and interval) and `report.md` (the tables, and one verdict line per registered hypothesis against its registered threshold). It runs the verifier, the adapters and the attack generators itself; it reads the comparison sweep's output and the overhead benchmark's output rather than reimplementing them. It needs no root and calls no model.

```
analyze --campaign DIR [--out DIR] [--config FILE] [--protocol FILE]
        [--comparison SWEEP_DIR]
        [--overhead LABEL=FILE]... [--overhead-after LABEL=FILE]...
        [--seeds N] [--jobs N] [--no-sweep] [--no-sensitivity] [--no-loo]
        [--diagnostics FILE] [--measure-cost FILE]
```

| Flag | Default | Meaning |
|---|---|---|
| `--campaign DIR` | (required) | The directory `capture-campaign.sh` writes: `manifest.json` and one `<agent>-<version>/<task>/run-NN` directory per run. A path the manifest recorded on another machine is looked for again under this directory |
| `--out DIR` | the campaign directory | Where `results.json` and `report.md` go |
| `--config FILE` | as `verify` | The agent version config, for the strict version check (I-57). Required: every verdict is computed as `verify --strict-version` computes it |
| `--protocol FILE` | `protocol.json` beside the agent config | The protocol file of per-agent targets (E-8), described below. Required: an agent of the campaign it does not list stops the analysis |
| `--comparison DIR` | none | The output directory of `scripts/compare/sweep.py` (`results.jsonl`, `summary.json`, `run.json`), for H1 |
| `--overhead LABEL=FILE` | none | An overhead benchmark `results.json`, for H4a; repeatable (tmpfs and disk) |
| `--overhead-after LABEL=FILE` | none | The same benchmark repeated after the campaign; the change in each median wall ratio is reported as machine drift |
| `--seeds N` | 100 | The highest seed of the attack sweep. The registered sweep is 1 to 100; a smaller value bounds the cost, and the report and the H2 verdict lines say the sweep is reduced |
| `--jobs N` | the CPU count | Runs processed in parallel. The output does not depend on it |
| `--no-sweep`, `--no-sensitivity`, `--no-loo` | off | Skip the attack sweep, the H3 sensitivity analyses, or only the leave-one-out baseline. Each is listed under "Not computed" |
| `--diagnostics FILE` | none | Also write the `Diagnose` records of every sweep run `NeedsDiagnosis` selects |
| `--measure-cost FILE` | none | Also time baseline building and verification of every run, one at a time, into this file. Timings vary between invocations, so they never enter `results.json` |

`protocol.go` holds the constants common to all agents: the bootstrap (10,000 resamples, seed 20261018), the Wilson and exact one-sided levels, the primary agreement (a rule needs one of five controls) and the sensitivity grid, the sweep's generators, mutation counts and seeds, the held-out prefix, H3a's near-zero bar, the H4 thresholds, and the exclusion rules' limits. The per-agent targets and the registration's name are in the protocol file, `config/protocol.json` (schema 1, E-8), and the command names no agent. The file holds `schema`, `protocol` (the registration, printed at the top of the report) and `agents`, one entry per adapter with `agent` (the registered adapter name), `label` (the agent's name in the report's text), `faithful_bar` (H3d's bar as `min_rate` with its `basis`, or `none` with the reason the H3d line prints), `inconclusive_pilot_range` (H3c's range as `low` and `high`, or `none` with the reason), `tool_heavy_tasks` and `d8_held_out_tasks` (the tasks the report's sentence on the task groups names; the held-out scope is the prefix). Every field is required, a list may be `[]`, and the loader refuses unknown fields, trailing data, a duplicate agent and an agent no adapter is registered under. The repository's file sets the bar at 50% (D2) and the range at 30% to 70% for Claude Code, and declares neither for agy. A freeze would pin both files; `results.json` records the values it ran under and the protocol file's SHA-256. The order of the INCONCLUSIVE causes is the protocol's precedence list (`causes.go`).

**Per run.** Each manifest run is read through its adapter, from the trajectory the manifest names or, for a manifest that names none, the file the agent's profile names (`trace.file` with the task as label, I-77), verified through the adapter path against a baseline built from its own controls (`agent.Capture` at the primary agreement, the control task's command excluded, as the capture script builds it), with the adapter's bookkeeping and housekeeping declarations for the version the session states (V-50, V-54) as `verify` takes them, and compared with the runner's own `verify-baseline.json` outcome. Controls with loss or no coverage record are left out of the baseline and counted (X2). The exclusion rules of the protocol apply to every run and each excluded run is listed with its rule, its reason and its effect: X1 (a loss counter set, or no coverage record; tracked io_uring socket operations are their own INCONCLUSIVE cause, N-25, not loss) leaves H3a, H3b and H2 and stays in H3c and H3d under the loss cause; X3 (the session states another version than the manifest, or the runner read another version after the run), X4 (the runner's status is not ok, the session does not parse for an adapter that declares no trace (agy), or `annotations.json` says so) and X6 (`annotations.json` says the user intervened) leave everything; for a run that did not complete, the rule the runner recorded (X3, X4 or X6) names it, and any other status is X4; X5 never leaves H3 and sets a run aside from the sweep only below two claims of the agent's own (harness-implied claims, which the generators refuse, do not count). `annotations.json` at the campaign root maps a run's directory to `{"x4": reason, "x6": reason, "completed": bool}`: it holds what only the operator knows. A slot is a run position; slots that did not complete for a harness error (not X3 or X6), and the attempts the runner moved aside, are counted per agent against the 10% line of X4. A task is held out when the runner names it `heldout:NAME` (D8); every other task, the lane-written `long` included, is development. The tool-heavy subgroup is the agent's `tool_heavy_tasks` in the protocol file (`tools`, `long` and `long-cc` for Claude Code and `long` and `long-agy` for agy), a held-out task counting by its name after the prefix.

**H3.** Per agent version (never pooled over versions) and per scope (all, development and held-out tasks, each task, and the named tool-heavy subgroup): the per-run false-positive rate (runs with `Findings() > 0` over kept runs) with a Wilson 95% interval and the exact one-sided 95% Clopper-Pearson bound when the count is 0 or n; the per-claim rate (claims flagged `Mismatched`, `Unwitnessed` or `OutsideInterval` over the agent's own claims) with a bootstrap over sessions, beside the per-run counts of `Unrecorded`, unexplained subtrees and unexplained sensitive changes; the INCONCLUSIVE rate over completed runs with its causes read from the verdict's reasons, under every cause a run has and under the primary cause by the protocol's precedence, split by loss counter and unverified field; and the FAITHFUL rate. The sensitivity analyses recompute these at agreement 1/5 to 5/5 and with a leave-one-out baseline pooled from the controls of every other capture of the same agent, version and control tool set, and report beside each setting the level-0 paths the baseline holds (V-36, V-37) and the single omissions that are then undetectable by design.

**H2.** The attack sweep, over every kept run. The generators mutate the agent's own claims (`attack.WithoutImplied`), and every attacked run, the honest one through the attack path included, is verified with the adapter's harness-implied claims put back where they stood (`attack.WithImplied`; those of a call the mutation omitted entirely or whose target it substituted are dropped, as the adapter would derive none), so the harness actions they explain are no finding on either path: `Omit` (exhaustive at n=1, seeds at n=2 and 3, uniform and sensitive selection, and retimed), `Fabricate` and `Substitute` (seeds at n=1 to 3, uniform and sensitive, and per field), each scored with `Score` and `MarkUndetectableByDesign` against the honest run and the baseline in effect (`Input.BaselineInEffect`, V-56), and `Widen` (every position, and composed with an omission at every position with a neighbour on each side, each neighbour widened over the hole where widening changes it). It reports detected, classified and located over the detectable in-capture mutations with a session-cluster bootstrap, the distinct mutations, and the undetectable by design, out of capture and unverifiable counts apart, with the sensitivity rows that count each as a miss; ambiguous alignments, unaccounted findings (and those already on the honest run through the attack path), the share of attacked runs that are NOT FAITHFUL and the causes of those that are INCONCLUSIVE; the premise check, listing every difference between the honest run through the attack path and through the adapter path; each miss with its `Diagnose` record; the assignment of every mutation that is not classified or not located, and of every unaccounted finding, to the six categories of protocol 5.7 (a case the record does not decide is category 6 and listed); and the attack surface per session (the claims whose single omission is undetectable by design, and how many of those `attack.Sensitive` selects). A finding about a mutation marked undetectable by design is a halt condition.

**H1.** From the sweep directory: acceptance per tool row and attack kind (accepted over evaluated, with a bootstrap over fixtures and the distinct mutations), the control rows (a witness-checkpoint row that accepts, or a pinned-key row that accepts, makes the matching H1 row UNJUDGED), cells whose controls did not hold counted as UNJUDGED and left out, and the verdicts of H1a to H1d and H1 as a whole. A mutation counts as an edit mutation when its record names a Write or Edit call.

**H4.** H4a: from the benchmark's samples (repetition 0 left out), each run under watch paired with the same workload alone in its repetition: wall and CPU ratios, fixed cost (start-up plus drain), watch CPU, peak RSS, capture and capability sizes, runs with loss, and the bootstrap interval of the median wall ratio, against the limits of decision D3 of the protocol. H4b: per agent version, per session and per claim, from the manifest (duration, events, claims, peak processes), the capture file's size and the capability events in the runner's verify output; a field the manifest and logs do not carry (start-up, drain, watch CPU and peak RSS unless the runner records a `cost` object in `run.json`) is counted as not measured.

**Output and exit codes.** The same inputs give byte-identical `results.json` and `report.md`: nothing reads the clock or a global random source, results are collected in manifest order whatever the worker count, and every map is written in key order. Both name the campaign, the comparison sweep, the benchmark files, the agent config and the protocol file by their last path element, and the config and the protocol file also by their SHA-256 (`agent_config_sha256`, `protocol_sha256`), so no path of the analysing machine appears. They still hold what the captures hold: the targets of claims and events (paths, hosts, command lines) in the misses, the premise check, the mislocation cases and the A4 lists, and the verdict reasons; they pass through the same redaction as the fixtures before publication. The exit status is 0 when done, 1 when done and a halt condition of protocol 10.2 occurred (an H2e contradiction or an unattributed INCONCLUSIVE; the report names it first), and 3 for usage and I/O errors.

Readings where the protocol is silent, each fixed in `protocol.go`, the protocol file or the code and listed so a reader can disagree (E-6):

- A trace that was tampered with or cannot be read (V-59) is a result, never an exclusion (I-75). `LoadSession` reads the session with `agent.ReadTrace`, so for Claude Code a missing, empty or garbled transcript is no load error and no X4; the run is verified as one whose trace cannot be read: INCONCLUSIVE under the thirteenth cause, `trace_deleted_or_damaged`, appended after O-30's as O-30's was after the eleven, or NOT FAITHFUL when the capture shows the tampering, counted in H3a like every finding. In an honest campaign either is a finding about the run, not an instrument defect: the agent changed or removed its own report. Such a run is set aside from the attack sweep (`sweep_exclusion` X5, with the reason naming V-59), since no attacked trajectory of an unreadable trace can be verified. `results.json` lists every run with tampering evidence, an unreadable trace or the runner's `trace` annotation under `trace_results` (agent, version, task, state, evidence count, outcome, the runner's record), always written, `[]` for none, and `report.md` has a section for them before H3. An agy session that is missing is still a load error and X4, since its adapter declares no trace. The campaign has no adversarial runs yet; a run of an agent told to remove its trace would read as detected by the same rule.
- H3c and H3d count every completed run (not X3, X4 or X6; X1 included). An X1 run is counted under the loss cause even when its outcome is an advisory NOT FAITHFUL.
- A harness-implied claim is not an agent claim: it leaves the per-claim denominator.
- The INCONCLUSIVE cause list is the protocol's eleven plus the unexplained declared harness command of O-30 and the trace that cannot be read of V-59, appended in that order. A `git_commit` claim set aside as out of capture (V-47) counts under the file-claim-out-of-scope cause with the detail `git_commit`: like an out-of-scope file claim, it is a claim the capture could not observe. An INCONCLUSIVE run with any reason no cause matches, alone or beside known ones, is unattributed and a halt condition, and the report names the reason; the run is still counted under the causes its other reasons state. Causes are read from the reason texts, so a reworded or new reason halts instead of being counted under another cause.
- "Primary" sweep variants are those with uniform selection (omission, retimed omission, fabrication, substitution, per-field substitution); the `sensitive` variants are secondary and outside the verdicts. The per-field runs use n=1. Retimed omissions are reported apart, in their own REPORTED line (detection, and the attacked runs reporting a claim outside its interval), and stay outside the H2a to H2c verdicts (the user's reading, 2026-10-26).
- A mutation is out of capture when it is not detected and its claim was set aside as out of scope (V-23) or out of capture (V-47), whatever its kind, and unverifiable when it is not detected and its claim is among the unverified pairs. An omission is out of capture when the honest run set the omitted claim aside either way: H2a covers in-capture mutations only, so it is counted apart and listed, not a miss (the user's reading, 2026-10-26).
- H2b and H2c are judged over the detected mutations, as their claims say ("every detected mutation"), so a miss counts against H2a only; the rate over the detectable mutations (the scorer's own `Tally.Rate`) is reported beside them (the user's reading, 2026-10-26).
- A4 holds at a position when the outcome and the numbers of findings, unrecorded events and unexplained subtrees equal the honest run's and no more interval findings appear. The composed clause ("still found") is refuted by a detectable omission that is not detected; one detected but not classified or not located is listed beside the verdict and left to H2b and H2c.
- The leave-one-out baseline admits an action any one pooled control performed (agreement 1/N of the pool), as the capture script's own baseline admits one of its controls; a fixed fraction of a pool of about 300 would keep out the rare harness activity pooling is meant to explain (the user's reading, 2026-10-26).
- H3d's bar is read on the point estimate. The H4a limits are read on each workload's median over the repetitions for the wall ratio, the fixed cost and the peak RSS, the statistic of D3's pilot figures, with the largest single repetition shown beside the fixed cost and the RSS (the user's reading, 2026-10-26), and on the count of runs for loss.
- The two recording modes of the net probe are not separate strata; the manifest's mode is carried in each run's record only.

Not computed: whether a mutation changes the replayed final state (the H1 edit-criterion split needs it in the sweep's rows); the per-capture peak RSS of `verify` and `baseline`; X4 causes the manifest does not show (a crash, a quota error, a failed `watch`, a suspend) and X5 completion, unless `annotations.json` says them; the halt conditions that need the machine (instrument validation, the redaction check, an event the scripted known answer did not perform). `--seeds` below 100 is reported as a reduced sweep and is not the registered one.

## Technologies

Go with the standard `flag` package. `watch` needs root for fanotify and the eBPF programs and links the probe packages; `verify` and `baseline` are unprivileged and read files only; `status` is unprivileged and runs only the agents' `--version`. `make build` builds `watch`, `verify`, `baseline`, `simagent`, `status`, `attack` and `analyze` into the repository root, and `make clean` removes them.

## Workflow

### Record and verify the simulated agent

```sh
make build
for i in 1 2 3; do
	mkdir -p /tmp/agent-trace-demo/null-$i
	sudo ./watch --workspace /tmp/agent-trace-demo/null-$i --out null-$i.json -- \
		./simagent --null --workspace /tmp/agent-trace-demo/null-$i --trajectory-out trajectory.json
	rm trajectory.json
done
./baseline --agent generic --agent-version simagent --min-agreement 0.3333 --out baseline.json null-*.json
mkdir -p /tmp/agent-trace-demo/run
sudo ./watch --workspace /tmp/agent-trace-demo/run --out ground_truth.json -- \
	./simagent --workspace /tmp/agent-trace-demo/run --trajectory-out trajectory.json
./verify --trajectory trajectory.json --ground-truth ground_truth.json --baseline baseline.json
```

`verify` finds no adapter for the JSON trajectory and uses `generic`. `watch` marks every filesystem (P-17), so the capture also holds the agent process's own start-up outside the workspace (the loader, the libraries, `simagent`'s binary, the zone file, the write of the trajectory), and without a baseline those read as Unrecorded. The `--null` runs measure that activity; they write their trajectory to the same path as the run they explain, so the rules for its write apply. With the baseline the run is FAITHFUL. Adding `--drop-entry 0` or an `--attack` mode to `simagent` turns the outcome into NOT FAITHFUL with the finding in the table above. Adding `--probes fs,proc,net --net-exe-path <libssl>` to `watch` and `--fetch-url ... --fetch-via-curl` to `simagent` exercises network content capture; the null runs must then use the same probes.

### Build a baseline for a real agent

1. Run the agent several times, five or more, under `watch` on a task that claims nothing, with the same probes as the real run: `sudo ./watch --probes fs,proc,net --workspace "$PWD" --out runN.json -- <agent command>`.
2. Check each run reports no loss; `baseline` refuses one that does.
3. `./baseline --agent claude-code --agent-version <version> --exclude '<the control task's command>' --min-agreement 0.2 --out baseline.json run1.json ... run5.json`. The agreement of one run in five is the capture script's default (below; I-24, V-24).
4. Read the `unstable` list: those actions were seen in fewer runs than the threshold and will read as unexplained if they appear in a real run; in the harness's own directories they are reported as unexplained harness activity, and a connection to a host the adapter declares as unexplained harness network activity ([20_verifier.md](20_verifier.md#verdict-vocabulary)); a connection to another host that appears in only some runs is a candidate for a declaration (V-34).

### Verify a real agent session

```sh
sudo ./watch --probes fs,proc,net --workspace "$PWD" --out ground_truth.json -- claude -p "your task"
./verify --agent claude-code --trajectory <session>.jsonl \
         --ground-truth ground_truth.json --baseline baseline.json
```

Run `./status` first: it exits non-zero when the installed agent is at a version `config/agents.json` does not list, and `verify` then prints a `WARNING:` line (I-57). Read the adapter section of the report before the verdict: unknown tools, parse errors and limitations bound what the verdict can mean. The exit code (0, 1, 2, 3) is the machine-readable result.

### Capture scripts

`scripts/capture-agent.sh` does the two workflows above in one run for any agent `config/agents.json` profiles ([30_agent_adapters.md](30_agent_adapters.md#agent-profiles), I-77): Claude Code by default (the config's `default_agent`), agy with `--agent gemini`, Codex with `--agent codex`. It reads the agent's profile through `scripts/agent-profile.py` and never names an agent; the binary, the version command, the version lock, the pinned model, the settings isolation, the invocation, the session and trace methods, the content method, the control prompts and the tasks are the profile's. `scripts/capture-claude-code.sh` is a wrapper that execs it with the same arguments, so the commands of earlier captures still work (I-78). It records a task run and `CONTROLS` control runs (default five) under `watch` (as the user, with `setpriv` exec'ing the agent in place so it keeps the pid `watch` records as the root), copies each transcript by session id, builds the baseline with the control's own no-op command excluded and `MIN_AGREEMENT` defaulting to one run in `CONTROLS` (V-24), and writes `verify` output with and without it. `--task TASK` picks one of the profile's tasks (Claude Code: `basic`, `parallel`, `project`, `edits`, `tools`, `shapes`, `long`, `websearch`); an unknown agent or task is refused with the profile's names (`unknown task T for A (basic, ... or heldout:NAME)`); each is described in [30_agent_adapters.md](30_agent_adapters.md#objective), with its fixture once captured. `project`, `tools`, `shapes` and `long` seed every run, controls included, from `scripts/seed/<task>`, and the script refuses before it asks for sudo when that directory is missing. It also refuses, before it creates the output directory or asks for sudo, an installed agent whose version (the profile's `version_command`: the first word `claude --version` prints, the last word of `agy --version`) `config/agents.json` (or `$AGENT_TRACE_CONFIG`) does not list for the adapter, with a `WARNING:` naming the version and the configured ones, unless `--allow-unconfigured-version` is given; a missing or unreadable config is a refusal too. The slots of the plan (each repetition of each entry) run in a permutation fixed by `--seed` (protocol 6.6): they are ordered by the SHA-256 of the seed and the slot, so the order does not depend on the Python version and a resumed invocation with the same seed keeps the order of the slots that remain. Without `--seed` the seed of the output directory's last invocation is reused, and a new directory gets a random one, printed and recorded in the manifest, each `run.json` (with the slot's position) and `invocations.jsonl`. `--dry-run` stops after the checks and prints the total of runs already complete and, per entry, the task and control sessions still to record, the control order and an estimate of the model turns (a session's tool calls plus its reply, from the prompts' step counts and the fixtures; 150 for `long`, 100 for a held-out task, which the script cannot know; a control costs two turns, four for `parallel` and `long` and five for `tools`, whose controls start a subagent, and two for a held-out task's whatever its tools), the totals, the seed and the order of the pending slots; it creates nothing. Otherwise the script builds once, asks for sudo once, and refreshes the credential every minute with `sudo -n -v` while it runs. `--validate` then validates the instrument (protocol 9.4, I-67) once, before the first run, in seconds: under `watch` (`--probes fs,proc`, the agent run as the user through `setpriv`) it runs `simagent --null` three times as control runs, `simagent`'s script once and the script with `--drop-entry 0` once, in the order null, honest, null, dropped, null, each in its own workspace and each writing its trajectory to one path (`validation/<time>/trajectory.json`), which is moved aside to `<run>.trajectory.json` after the run. It builds a baseline from the null runs with `baseline --agent generic --min-agreement 0.3333` and verifies the honest and the dropped run against it (`verify --agent generic --baseline`). It passes only when every `watch` exited 0, every null run wrote `[]`, `baseline` accepted the null runs, the baseline hides nothing of the known answer (no rule names the workspace, no command rule or subtree record, no rule equal to an action the honest run claims, with the workspace and its mangled form as placeholders, as `cmd/baseline` writes them, I-70), the honest run is FAITHFUL and the dropped run is NOT FAITHFUL with exactly one finding, an Unrecorded event equal to the honest run's first claim. A failure names the check and, for a known answer, the events no null run explains, and ends the invocation before any run (protocol 10.2). The runs, the baseline and the reports are kept in `OUTPUT_DIR/validation/<time>/`; the result, with each check's outcome, the number of null runs and of rules, is written to `OUTPUT_DIR/validation/<time>.json` and the manifest. `--validate-e2e` adds `sudo env PATH=$PATH go test -count=1 ./tests/e2e`, which takes long and is therefore opt-in. `--validate-only OUTPUT_DIR` (with `--validate-e2e` and `--dry-run` if wanted) takes no plan: it builds, asks for sudo, runs the validation alone and exits 0 when it passed and 1 otherwise, recording no agent session and writing no manifest. Before each run the script repeats the check and reads the agent's version (by its profile's version command and field); after each run it reads the version again. A change, or a check that now refuses, stops that agent's campaign (the other agent's slots go on, and the exit status is 1 at the end), and a run whose version changed during it is excluded as X3. A run is complete when the capture script exited 0 and the version did not change; the capture script's own model check is part of that exit status. The script writes the run's `run.json` and rewrites `OUTPUT_DIR/manifest.json` and `OUTPUT_DIR/summary.txt` after each run. A failed run is classified for protocol 10.1 and the rule and reason are written to its `run.json`, the manifest's `exclusions` and the summary; no run is deleted. X4 (a harness error: the capture failed, no transcript of a control or of an agy task run, `watch` failed, the agent's or `watch`'s log reads like a login or quota error) moves the attempt aside to `run-NN.failed-<time>-aK` and records the slot again, at most twice; a slot that fails three times is reported failed and not replaced, and a rerun skips it. A login or quota error, or a `MODEL MISMATCH`, ends the campaign at once instead, since the next run would fail the same way. A run whose capture completed is also failed, as X4 with the reason `quota` or `auth`, when the agent's own output in the task's or any control's `watch` log (the probes' event lines left out, since file and host names can contain any word) shows an account error (`ACCOUNT_QUOTA`, `ACCOUNT_AUTH`, stricter patterns than the ones for failed captures): a session the account stopped can still leave a transcript, as the agy pilot of 2026-10-27 did when its quota ran out mid-task and in three controls. The unconfigured-version warning is printed once per plan entry, at the checks, and not again for each run (`AGENT_TRACE_VERSION_WARNED`). X6 (Ctrl+C reaches `watch`, which stops the agent and writes what it recorded) ends the campaign with exit status 130; the rerun records the slot again. X1, loss, is not decided here: the manifest holds the counters for the analysis. The campaign also stops after `--stop-after-failures` consecutive failed runs (default four, one more than a slot's attempts). Rerunning the same command resumes: complete and failed-out slots are skipped, and the directory of an interrupted or failed run is moved aside before its slot is recorded again. The manifest (schema 2) holds, per run in place, the agent, versions before and after, the model pinned and the models recorded for the task run, the task, run index, recording mode, directory, file paths, start and end, exit status, the slot's seed, position and attempt number, the control order and each run's model check and subagent counts (I-71), the SHA-256 of the task's prompt and seed, the verdict without and with the baseline from the two JSON reports (outcome, findings, tool calls, claims, the size of each alignment list, completeness, and the verdict's reasons), and, for the task run and for each control run, a scale record: each probe's coverage record from the ground truth (ring buffer drops, untracked children, full state maps, channel drops, content and response state), the net probe's counters with `content_fraction` (requests with content over connections less those marked `content_unsupported`, null when that is zero), the events by type with connections and requests by target, and the peak number of the agent tree's processes alive at once, counted from the fork and exit events over the root and the processes that have both. The net counters and the `diagnostics` come from the ground truth (coverage schema 2, [10_probes_common.md](10_probes_common.md#diagnostics)): `net` is the net probe's `net_content` counters and `diagnostics` holds, per probe that keeps them (proc and net), each ring buffer's size, peak occupancy, records and drops and each `tracked_pids` map's capacity, peak and entries at stop, with the peak as a fraction of the size, and for the net probe its `ssl_writes` counts where the capture measured them (N-36); a probe that keeps none (fs) has no entry, which means not measured. Only for a schema 1 capture does the record fall back to the counters in the `net probe coverage:` line of `watch`'s log, and `net.source` says so (`diagnostics.source` is then null). A schema 2 capture whose net probe did not run has `net` null. Beside the scale record each run holds `cost` (and `control_cost` for each control run) and `watch_exit`: `cost` is what `scripts/measure-watch.py` measured around that run's `watch`, and `watch_exit` is `watch`'s exit status. Each run also holds `trace` (V-59, I-75), from `verify-baseline.json` and `<task>.trace.txt`: the `state` verify read the trace in (`read`, `missing`, `empty`, `unparsable`, `damaged`, `differs`), its `detail`, the capture script's own reading of the copied file (`copied`), the number of pieces of `tampering` evidence, whether the content was `compared` with the probe's last hash, and the `outcome`; null when verify wrote no report. A complete run whose trace is not `read`, or that has tampering evidence, gets the runner's annotation `trace` in `annotations.json` (one of its `auto` fields), stays complete and is never an exclusion; the manifest lists such runs under `trace_results` and `summary.txt` counts and names them. Beside the runs the manifest holds the attempts moved aside, the slots with their final state (`ok`, `failed`, `pending`), the exclusions by rule, the invocations (seed, commit, dirty flag, plan hash, flags) and the validations.

**Cost.** The capture script runs every `sudo watch` under `scripts/measure-watch.py` (a Python script of the standard library, changing no argument, stream or exit status of the command it wraps), which writes `<label>.cost.json` with the fields `cmd/analyze` reads in the `cost` object of `run.json` (H4b): `startup_s`, `drain_s`, `watch_cpu_s` and `watch_maxrss_kb`, and more for the reader (`agent_s`, `tree_cpu_s`, `tree_maxrss_kb`, the sampling interval, notes). It finds the `watch` process by its `--out` argument and samples it from `/proc` every 5 ms. Start-up is the time from launching the command to the held agent process leaving `watch`'s hold script (its `argv` stops naming `agent-trace-hold`: the agent's first instruction), so it includes `sudo`, the probes' start and `watch`'s 200 ms wait. The agent process is `watch`'s child, the only process `watch` starts, once its `argv` is no longer `watch`'s own (a fork not yet exec'd). `watch` releases the hold about a millisecond after starting it, so the child is usually first seen already running the agent, and the release is then taken as that first sight, at most one sampling interval late; `release_seen` says which (`held` or `after`); drain is the time from the end of that process to the end of the command (`watch`'s 300 ms, the probes' stop, the write of the capture), the benchmark's definitions with one more phase boundary each. `watch_cpu_s` is `watch`'s own `utime` plus `stime` from `/proc/PID/stat` (10 ms steps), which leaves the agent's CPU, in the process's children's fields, out; `watch_maxrss_kb` is `watch`'s own `VmHWM`. `tree_cpu_s` and `tree_maxrss_kb` are the rusage of the whole waited tree, the first exact but including the agent, the second the largest process of the tree and so an upper bound of `watch`'s own when the command runs without `sudo`; under `sudo` the tree's usage does not reach the helper, so both fields are `sudo`'s own and neither bounds `watch`'s. A field that could not be measured (the process was not found, no agent process was seen) is null, never zero, and the notes say why. The measurement never decides the run: it passes the command's exit status through. Ctrl+C reaches the helper too; it ignores it, so that `watch` can stop the agent and write the capture, and exits when the command does.

**Annotations.** `OUTPUT_DIR/annotations.json` is the file `cmd/analyze` reads for what the manifest cannot show (a `runs` object from a run's directory under the campaign, `<agent>-<version>/<task>/run-NN`, to `{"x4": reason, "x6": reason, "completed": bool}`; the analysis ignores other keys). For a task run that completed, with its transcript and capture, but whose `watch` exited non-zero, the runner reads `watch`'s log. `watch` exits 1 both for its own errors and for an agent that exited with an error ([Known limits](#known-limits)), and the manifest reads such a run as `ok`. When the log says the agent exited with an error, the run counts (I-66) and the runner writes `agent_exit_status`, the agent's status, a note `cmd/analyze` ignores. When `watch` itself failed, the runner writes `x4`. The fields the runner wrote are listed under `"auto"` and rewritten when the slot is recorded again; the rest of the file is the operator's. `scripts/annotate-run.sh [--campaign DIR] [--completed yes|no] [--note TEXT] [--intervened] [--x4 TEXT] RUN_DIR...` records what only the operator knows: task completion (X5, reported per task), an intervention (X6, with `--note` as the reason) and an X4 cause the runner cannot see (a crash, a quota error, a suspend). A field set that way is taken out of `"auto"` and the runner never rewrites it; `--list` prints every run of the manifest with its recorded completion. The file is replaced atomically, and a damaged one is reported and left alone by the runner. The campaign script's unprivileged checks (every refusal, the dry run, its order and seed, a whole campaign with the control order, the models, the version lock and the held-out task, resumption with a fixed seed, validation with each failure (the validation itself with the real `simagent`, `baseline` and `verify` against captures a stand-in `watch` synthesizes from what `simagent` did, with injected noise, workspace activity, loss and `watch` failures), retries and the other exclusions, a version change before and during a run, a model mismatch, the cost measurement against a fake `watch` with known delays, the scale record from schema 2 and schema 1 ground truths, the agent-exit note and the `x4` annotation and `annotate-run.sh` with the takeover of a field, and Ctrl+C) were run during development with shims for `sudo`, `make`, `go`, the agents, `simagent` and the binaries in a scratch copy, outside the repository; the shims and those checks are not committed, so they cannot be rerun from the repository.

### Overhead benchmark

`scripts/bench-overhead.sh` measures the evaluation plan's overhead metric, the time and storage of instrumentation and verification, on workloads that call no model, so it uses no quota. The user runs it once as an ordinary user; it validates its arguments, builds the commands into its output directory and asks for sudo once, for `watch`. The workloads are a scripted bash loop at each size in `--sizes` (default 10, 100 and 1000 iterations, each writing two files, renaming one, reading both through `cat`, connecting to a TCP listener the script runs on 127.0.0.1, and deleting both), `simagent`'s fixed script, and `project`, the command pattern of the capture script's `project` task without the model in a copy of `scripts/seed/project`. Each runs alone, as the user, and under `watch` with all three probes and with each probe alone, the workload run as the user through `setpriv` and `watch`'s output written to a file, as in the capture script. Every repetition (`--reps`, default 10) runs each workload under each condition in an order rotated per repetition, after a warm-up repetition that is left out. Per run it records the workload's wall time and CPU from inside the workload (bash's `EPOCHREALTIME` and `times`), the run's wall time, start-up (launch to the workload's first instruction, including `watch`'s probe start and its fixed wait before the release) and stop/drain (the workload's last instruction to `watch`'s exit, including the wait for trailing events and the write of the capture), `watch`'s CPU as the measured tree's CPU less the workload's, the peak RSS of the measured tree from GNU `time`, the capture's size, event count and bytes per event, whether `verify` judges it complete, and the capability record: the events beneath the commands in `verify`'s JSON report and their size, per session. The ratio of a run's workload wall time and CPU to the same workload alone in the same repetition is reported per condition. Its unprivileged part times `baseline` on each checked-in paired fixture's controls (agreement one control, excluding the control command) and `verify` on its session with and without that baseline, with their peak RSS, and records the fixture's storage figures; `--unprivileged-only` runs that part and the alone condition with no sudo. It writes `results.json` (machine, kernel, CPU governor, load average at start and end, output filesystem, commit and whether the tree was dirty, parameters, every sample and, per group, the count of runs, of successful runs and of runs with event loss, with median, quartiles, minimum and maximum of each metric), `results.csv`, `samples.jsonl` (one line per measured run) and `summary.txt` into `OUTPUT_DIR` (default `/tmp/agent-trace-overhead-<time>`), which must lie outside the repository and be empty; `--keep-captures` keeps each run's capture, log and workspace. It prints the numbers without judging them: the plan states no acceptance threshold. The largest shell size dominates the running time; `--sizes`, `--workloads` and `--conditions` narrow a run. `--help` lists the flags.

### Tests

`go test ./...` runs the unit tests; probe and end-to-end tests skip without root. `sudo go test -v ./...` runs everything. The end-to-end tests in `tests/e2e` build `simagent` themselves, run it under the probes with the flags each scenario needs, and assert the verdict.

### Comparison tools

`scripts/compare/` runs three published integrity tools over the four attacks of `attack` on the gated captures of the attack evaluation (`basic`, `parallel`, `project`, `edits`; [50_attack_generators.md](50_attack_generators.md#the-evaluation-tests)), so the comparison is measured with each tool's own verifier. The tools are halo-record (hash-chained audit records written by a Claude Code hook, with optional witness checkpoints), reproducible-trajectories (replays a Claude Code transcript's Write and Edit calls against a git commit, and re-runs its Bash commands), and Signet (Ed25519-signed receipts in a hash-chained audit log, written by its Claude Code plugin). It needs no root and calls no model; it uses the network in `setup.sh`, and `sweep.py`'s `go build ./cmd/attack` can download modules when the Go module cache is cold. Results are written outside the repository; no result is recorded on this page.

```sh
scripts/compare/setup.sh /scratch/compare-tools
scripts/compare/sweep.py --tools /scratch/compare-tools --out /scratch/compare-run
```

`pins.env` pins each tool by commit and version: halo-record `f59e7c5` (0.2.46), reproducible-trajectories `94a9f8d` (0.1.0) with its dependency trajectoriz 0.10003.0 by wheel hash, and Signet `6704117` (0.11.0). `setup.sh TOOLS_DIR` clones the three repositories into `TOOLS_DIR/src` (or from local clones with `--mirror DIR`), checks out the pinned commits, refuses a different HEAD, local changes or a version other than the pinned one, and refuses a `TOOLS_DIR` inside the repository. It runs the Python tools from their checkouts in two virtual environments of the system `python3` (uv when present, else `venv`), with no build backend installed, builds `signet-cli` with the system cargo (`--locked`, `CARGO_HOME` and the target directory under `TOOLS_DIR`; Signet's `rust-toolchain.toml` names a nightly, which a rustup installation is told to ignore), and runs Signet's plugin signer under the system node with the WASM module checked into the repository at the pinned commit, not rebuilt. Everything it runs has `HOME=TOOLS_DIR/home` and no global git configuration. It writes wrappers into `TOOLS_DIR/bin`, smoke-tests each tool, and records the commits and the toolchain versions in `TOOLS_DIR/manifest.json`. The `reproducible-trajectories` wrapper runs only `check-execution-reproducible`: the tool's upload and share commands reach the network and never run. The tools are fetched, not redistributed. Licences: halo-record Apache-2.0; reproducible-trajectories MIT as declared in its `pyproject.toml`, with no licence file in the repository at the pinned commit; trajectoriz MIT; Signet Apache-2.0 OR MIT.

`sweep.py` builds `attack` into its output directory, which must lie outside the repository and be new or empty, and runs every tool with `HOME` in it and an environment that passes on only `PATH`. For each fixture it takes the honest normalized trajectory (an omission with its dropped claim put back, checked equal for two seeds) and, for each kind, mutation count (`--n`, default 1) and seed (`--seeds`, default 0 to 99, the evaluation's), the mutated one, with `--avoid-ground-truth` as in the evaluation. `--fixtures`, `--kinds`, `--only` and `--jobs` narrow or parallelize a run.

With `--campaign DIR` the sweep attacks the kept runs of a campaign instead of the four fixtures, with the attacked trajectories of the H2 sweep (the protocol's 5.3, 8.2 and D13, local only):

```sh
scripts/compare/sweep.py --tools /scratch/compare-tools --out /scratch/compare-campaign \
    --campaign /scratch/campaign --kept-from /scratch/analysis/results.json [--heldout-dir DIR]
```

- *Subjects.* `--kept-from` takes the `results.json` of an `analyze` run: the runs it swept (those with an `attack` record) when it ran the sweep, otherwise the runs it keeps with a baseline built (`analyze --no-sweep` is enough, and is quick). Without it the subjects are chosen from the manifest by an approximation of the exclusion rules (status `ok`, version unchanged, no recorded exclusion, no loss counter, no `x4` or `x6` annotation), and `run.json` records which rule chose them. A run whose honest trajectory has fewer than two claims of the agent's own is left out, as X5 does, and listed in `run.json`.
- *Variants.* Those of the H2 sweep that count in its verdicts: omission (n=1 at every position, built by the script as `pkg/attack.Omit` with an index writes it, since `attack` has no flag for a position; n=2 and 3 by seed), fabrication and substitution (n=1 to 3 by seed), the substitution of each field (n=1 by seed; one refusal row when the trajectory has no claim with that field, as the H2 sweep stops at its first refused seed) and interval widening (n=1 by seed, where H2 runs every position). Seeds are `--seeds` (default 1 to 100), through `attack` with the flags the H2 generators use (`--avoid-ground-truth` for fabrication and substitution). `--variants all` adds the secondary rows: omission and substitution selecting sensitive claims, and retimed omission. Each row carries its `variant`, its seed (null for the exhaustive omissions, with a `position`) and `fixture`, which is the run's directory under the campaign, the name `analyze` gives a run, so its bootstrap clusters by session.
- *Tools.* halo-record and Signet run on every attacked trajectory of both agents. reproducible-trajectories runs on Claude Code runs with a Write or Edit claim, on `--rt-seeds` (default 1 to 10) of each variant, the n=1 omission included by seed, never exhaustively. Its repository is rebuilt from the run as it rebuilds a fixture's: the workspace path is the capture's `workspace`, the parent commit is `scripts/seed/<task>` (or `b.txt`, `c.txt` and `d.txt`, as the capture script seeds a task without a seed), and a held-out task's seed is read from `--heldout-dir DIR/NAME/seed`, which stays outside the repository; each parent file the agent opened must hash as the capture first observed it and each written file to a content the capture observed. A run whose repository cannot be rebuilt (a write outside the workspace, a seed that does not match) gets `inapplicable` honest rows with the reason and no rt variants, and `run.json` lists it. Runs of the other agent, and runs with no Write or Edit claim, are listed as not run.
- *Resumption and disk.* Each subject is marked done when its last variant has finished; `--resume` keeps those, drops the rows of the others and redoes them. A variant's files are removed once its rows are written (`--keep` keeps them), since thousands would fill the disk. `--plan-only` prints, per subject, the claims and the number of attacked trajectories for each group of tools, and runs no tool.
- *Runtime.* `--plan-only` gives the counts of attacked trajectories, which set the cost: about a hundred seeds of each of thirteen variants plus one trajectory per claim for every run, through halo-record and Signet (nine tool invocations each), and the rt seeds of each variant for every Claude Code run with edits, each a repository rebuild and the transcript's commands run in it. The recorded timing of the fixture sweep (all three tools, a few tenths of a second of wall time per trajectory on eleven jobs) gives the order for a campaign, hours, not minutes; a timed run on one `long` run replaces any estimate. `attack` itself costs a process start and a parse of the capture per trajectory, more for a long run, and its ground truth too for fabrication and substitution.

- halo-record and Signet read Claude Code `PostToolUse` hook events. `posttooluse.py` turns each claim into one event, the whole claim (timestamps included) in `tool_input` and its output hash and exit code in `tool_response`, so the chain seals every field an attack changes; it also runs on its own (`posttooluse.py CLAIMS.json [EVENTS.jsonl]`). `halo_drive.py` and `signet_drive.cjs` call the function behind `halo hook` and behind the plugin's `sign.cjs` once per event in one process, which gives the same records as a process per event without the start-up cost. Each trajectory gets a fresh chain, so every attacked chain is re-sealed. halo-record has two rows: `no-checkpoint` (`halo verify`) and `witness-checkpoint`, where the honest chain was anchored to a local witness log before the attack and the attacked chain is checked against it (`halo anchor --check --expect-subject`, every chain carrying one `HALO_SUBJECT`, since a checkpoint is otherwise keyed by the chain's root, which a re-seal changes). Signet has two rows, both checked with the honest key pinned (`signet verify --chain` and `signet audit --verify --trusted-agent-key`): `operator-key`, the chain re-signed with the operator's key and no server co-signing, and `other-key`, re-signed by a forger with a fresh key. `signet audit --verify` without a pinned key checks each receipt against the key embedded in it, so it is not used.
- reproducible-trajectories reads the session transcript and takes a git commit as its ground truth. `rt.py` builds, per variant, a scratch repository whose parent commit holds the workspace before the session (`scripts/seed/<task>`, or the capture script's `b.txt`, `c.txt` and `d.txt`) and whose second commit, naming the transcript, holds the state the honest Write and Edit calls produce; each parent file the agent opened must hash as the capture first observed it and each written file to a content the capture observed for its path, or the sweep stops. It rewrites `/ws/<label>` into the repository and adds each record's `cwd`. It maps each mutation back to the transcript call its claim came from (same tool, the call's record timestamp, a consistent target) and applies it there: an omission removes the call and its result, a fabrication inserts a call of the claim's tool and target after the preceding claim's call (a Write with fixed content, an Edit of a fixed string), a substitution changes the call's path, command or URL, a Write's content or an Edit's new string (output hash) or the result's error flag (exit code), and a widening moves the call's and its result's timestamps. A mutation whose claim has no call in the main transcript (a subagent's claim, which the tool does not read) or whose field has no transcript equivalent (a request hash, a Grep or Glob target) is recorded as `not_representable`. The fixtures elide tool results, so the Bash results are filled by running the transcript's commands in order in the repository at its final commit, which is then restored. Attacker `adaptive` re-records every Bash result after the mutation this way, as the re-sealing attacker of the other tools; attacker `naive`, run only when the mutation touches a Bash call, keeps the honest results. Each variant gives an `edit-criterion`, a `command-criterion` and an `overall` row; a status of `no_operations` or `no_commands` counts as accepted, with the status kept.

It writes `results.jsonl` (one row per tool, condition, attacker, kind, fixture, seed and mutation count: `accepted`, `detected`, `not_representable`, `attack_refused`, `inapplicable` or `error`, the tool's own output, and for a command the re-run's first differing line), `summary.json` and `summary.txt` (per cell the runs, the outcomes and the distinct mutations among them), and `run.json` (parameters, this repository's commit and whether the tree was dirty, the tools' manifest). Controls run per fixture: the honest trajectory (repeated `--honest-repeats` times, default 3, for reproducible-trajectories, whose command criterion re-runs commands), a record dropped from the honest halo and Signet chains without re-sealing, and a halo checkpoint taken only after an attack. A cell whose tool's controls on that fixture did not all give the expected answer prints as `UNJUDGED`. A harness failure inside a variant is recorded as a row of tool `harness` and makes the sweep exit 1; a failure while preparing a subject stops the sweep with no row.

Safety. The command criterion, and the filling of the Bash results, execute the transcript's commands, fabricated and substituted ones included. The harness runs them only inside the variant's scratch repository, with the scratch `HOME`, and, when unprivileged user namespaces are available, in a new network namespace (`unshare -rn`, which also makes the commands see themselves as uid 0); without one it warns and the commands can reach the network. That is not a sandbox: running the command criterion on a transcript one does not control needs a container or a virtual machine.

Limits of the comparison machinery: the converter decides which fields halo-record and Signet seal, and the hook's record time is when the harness runs, not the session's. The witness row detects an edit made after a checkpoint the attacker does not hold; it cannot detect misreporting at capture time, which the no-checkpoint row stands for. The reproducible-trajectories repository is a reconstruction from the fixture and the capture's hashes, not the session's own repository; its Bash results are recorded at the final commit, where the tool re-runs them, not where the agent ran them, which favours the tool; an Edit's two claims are one transcript call, so a mutation of either changes the call; the content of a fabricated Write or Edit is the harness's choice and decides whether the edit criterion sees it. Re-run output that varies between runs (a test runner's timing, a clock, a directory listing's times) is reported as the tool reports it, not filtered.

## Guarantees and loss accounting

- `watch` writes a coverage entry for every known probe, so an unselected probe reads as not run, never as clean, and refuses to run a probe that cannot report its loss.
- `watch` writes the capture even when the agent fails, so a failing agent can still be verified.
- `verify` keeps verdicts (0 to 2) and errors (3) apart, and never guesses between two adapters.
- `verify` names a session's agent version that `config/agents.json` does not list in a `WARNING:` line and in the JSON report, and under `--strict-version` never reports FAITHFUL or NOT FAITHFUL for it; the capture script refuses such an agent before it asks for sudo unless told otherwise (I-57).
- `baseline` refuses control runs that lost events or carry no coverage record, so a baseline cannot be short because of loss.
- `analyze` lists every excluded run with its rule and reason and prints the considered, evaluated and succeeded counts with every rate, so no run and no unevaluated item drops silently; its outputs are a function of its inputs (E-6).

## Known limits

- A Codex capture's database snapshots hold every thread of the account, not only the run's, so they must never reach a fixture whole: `scripts/make-capture-fixture.py` leaves them out, keeps of each rollout only the records and fields the adapter reads, and replaces the account's ids, the other threads' rollout names, the synced skill directories' ids and the app caches' key in the ground truths (I-86). For every agent the script leaves the probes' diagnostics out of a fixture's ground truths, which no verdict reads and the fixture parse test refuses. The catalog pins the per-model settings Codex reads, not the server's behaviour behind the model id.

- A trace's fate is read by the capture script for Claude Code only (I-75); an agy task run whose conversation database is missing is still X4, since its adapter declares no trace. The script finds the transcript by its session id, so a transcript moved elsewhere reads as missing, and one rewritten in place is caught only by the content comparison with the probe's last hash, which needs that close to carry a hash (on the private raw Claude Code captures at hand it held on every task run, **Verified**, local only). The campaign's `trace` record, annotation and `trace_results` list are not covered by a test; the capture script's two paths are, with shims.
- `watch` exits 1 both for its own errors and for an agent that exited with an error, so its exit code does not separate the two.
- `watch` without a command or `--root-pid` records with `root_pid` zero, which `verify` can only report as INCONCLUSIVE; its file events are then unfiltered.
- The level-0 events of the aligned sequence hold the harness's own file activity outside the workspace (its configuration directory, the libraries it loads), which the baseline has to explain; a baseline captured before P-17 does not.
- `watch --root-pid` misses whatever the process did before attaching.
- A command `watch` launches gets the resolved program path as `argv[0]`, and a file without a `#!` line that the kernel refuses to exec is run as a shell script by the hold script's `exec` (P-23).
- `verify` checks the baseline's `agent_version` only against a session that states its version; the generic and Gemini formats state none. `--agent-version` is not used for that check.
- A Gemini session's version is unknown to `verify` unless `--agent-version` gives it, and an unknown version prints nothing in the text report by default: only the JSON's `agent_version_check` says `unknown`. `--agent-version` is the caller's statement, not a measurement.
- The version check says whether a version was verified, not whether the adapter fits it: a configured version can still change behaviour between builds with the same number, and an unconfigured one may fit. A version is configured by hand ([30_agent_adapters.md](30_agent_adapters.md#configured-agent-versions)); `verified` is the date of its newest checked-in capture, not of a later re-check.
- `status` checks the agent first on `PATH`, as the capture script does; another installation the user runs is not checked. Its kernel check covers only the minimums the probe pages state, not kernel options (BTF, BPF ring buffers) the probes also need.
- A normalized trajectory, such as the one `attack` writes, carries no harness-implied claims, so under `verify --normalized` the harness's read after a Bash read command is Unrecorded where the adapter's own reading explains it (V-33).
- `capture-campaign.sh` takes each task run's controls in the same invocation, so a Claude Code `basic` run costs six sessions and a `long` run six sessions of which the task is the only long one; the quota cost of the protocol's D10 (local only) is the user's, and the dry run states it. Controls of two task runs may differ by the time of day, which is the point of the protocol's D10 and is not a cost the script can remove.
- The model check reads what the transcript records. For agy it reads the executor metadata of the conversation database, which the existing captures show as `gemini-3.8-flash-high` for the default model; whether `--model gemini-3.8-flash-high` (now agy's default, I-65) records the same string, and which id matches "as captured", was measured by the agy pilot of 2026-10-27, which recorded `gemini-3.8-flash-high`; its MODEL MISMATCH came from the path token `gemini-1.4.7`, which the model check no longer reads as a model name (499452f). A mismatch fails the run with the recorded names in `order.tsv`. A Claude Code transcript's subagents may run another model (their models are recorded, not checked). It takes a model name only as a whole token, not inside a path: the metadata also holds the workspace path, which under a campaign contains the agent's directory name (`gemini-1.4.7`).
- The classification of a failed run reads the agent's and `watch`'s logs for login and quota phrases (`not logged in`, `/login`, `401 unauthorized`, `429`, `rate limit`, `quota` and the like, read from the watch logs and the campaign's `campaign.log`); a message outside the list is a plain X4 harness error, retried twice. An X4 reason is the script's reading, not the agent's.
- The version lock is the settings file and the environment the runs get, and a version read before and after each run. It does not prove that Claude Code ignored the lock, only that the version did not change; `claude doctor` says whether the lock is read.
- `--validate-e2e` runs `go test` as root with the user's `PATH`; whether root's Go caches suffice offline was not run here, since no sudo ran. The known-answer check runs `simagent` with `fs,proc` only, so it does not exercise the net probe.
- The validation's baseline explains the agent process's own opens and writes outside the workspace in every run, so the check measures the probes on `simagent`'s actions in the workspace and on its command, not on level-0 activity outside it (V-36, V-37). It was checked offline on the ground truths of the failed run of 2026-10-26 (null runs taken as those captures less `simagent`'s actions, the trajectory path rewritten to one path) and with synthesized captures, not yet with `sudo`: that `--null` opens nothing a run of the script does not, and that `watch` records no per-run path at level 0, are the premises a real run confirms. A machine whose fs probe marks the device filesystem would record the script's opens of `/dev/null` for the command's stdio, which a null run does not make, and the validation would then fail closed on them.
- The cost measurement samples `/proc` every 5 ms, so its times have that resolution, `watch`'s CPU 10 ms steps, and `watch_maxrss_kb` is a lower bound (what grew after the last sample is missed; `tree_maxrss_kb` bounds it from above only without `sudo`). Neither bound separates the CPU the kernel spends running the probes' BPF programs, which is charged to the traced agent's tasks: `watch`'s own CPU is the userspace part only, and the whole cost of recording is what the overhead benchmark's paired runs measure. Start-up includes `sudo`, and is late by up to one sampling interval when the agent process was first seen past the hold (`release_seen` `after`). A `watch` the helper cannot find, or an agent process it never sees, gives null fields. Until 2026-10-27 the helper took the agent only while it still ran the hold script, which lasts about a millisecond, so most runs had null start-up and drain (2 of the 12 runs of the two `long` pilots of Claude Code 2.1.306 measured them, **Verified** on their cost files). Under `sudo` the waited tree's rusage does not reach the helper: on those pilots `tree_cpu_s` was 0.005 to 0.01 s and `tree_maxrss_kb` about 13 MB while `watch` alone used 0.6 to 16 s of CPU and up to 97 MB (**Verified** on the same files; the cause is not established), so `tree_cpu_s` and `tree_maxrss_kb` are `sudo`'s own and do not bound `watch`'s.
- `watch`'s exit status is not separated from the agent's: the runner reads `watch`'s log for `agent exited with error` to say which it was. An agent that exited non-zero after a complete session counts and is only noted (`agent_exit_status`, I-66); `watch`'s own failure is annotated `x4`, and a log that says neither is read as `watch`'s failure. A control run whose `watch` exited non-zero is recorded in `watch_exit` and not excluded.
- Task completion (X5) is not known to the runner: no task output is checked, and `annotations.json` has no `completed` field until the operator records one, so the analysis lists the completion as not stated.
- `scripts/compare/sweep.py --campaign` takes its attacked trajectories from `attack`, not from `analyze`'s in-process generators. Both call the same functions with the same options; `attack` computes the targets to avoid after dropping harness-implied claims and `analyze` before, which changed no trajectory on the checked-in fixtures (one with an implied claim among them) and one raw capture of each agent for seeds 1 to 8 of every primary variant, but is not guaranteed equal on every run. The interval-widening trajectories are sampled by seed where H2 widens every position. The result rows hold targets of the captures, so a comparison output directory is as private as the captures.
- Exclusion bookkeeping stops at the rules a script can see (X3, X4, X6); X1 (loss), X2 (a control with loss, which `baseline` refuses, failing the run) and X5 are decided by the analysis, and a run whose control `baseline` refused is a failed X4 run here.
- `capture-campaign.sh`'s turn estimates are not measurements; the `long` task's real count is in the manifest after its first run. Its peak process count is computed from fork and exit events over the processes that have both, and the root, so it is a lower bound: a process that never exec'd, or whose execs all failed, has no exit event and is left out (a shell's subshells and command substitutions); the proc probe's tracked-set peak in the diagnostics counts every process ([11_probe_proc.md](11_probe_proc.md)).
- A control's subagent (I-71) is what its prompt asks the model for, not something the script enforces: a control that starts no subagent, two, or one that uses a tool is kept with a `WARNING:` and its counts in `order.tsv`, and the campaign excludes nothing for it. A baseline whose controls started no subagent then leaves the task's subagent files unexplained, as before I-71, and one whose subagent used a tool takes rules from that tool's activity. The agy count is of the databases that appeared during the run, which a concurrent agy session also adds, and agy's subagent tool calls are not counted. A held-out task's controls are estimated at two turns whatever its tools. How many subagent events a control's subagent produces against a task's (its files are rewritten more often in a long task) is not measured: the rules are per action type and canonical path, so the count does not matter to them.
- The `long` task for Gemini lists `invoke_subagent` in the custom agent; whether agy 1.3.4 offers it there is not measured (agy did not offer `multi_replace_file_content`, I-61).
- `bench-overhead.sh` reads a peak RSS from GNU `time` for the whole measured tree, so under `watch` it is the largest of `watch` and the workload's processes: `watch`'s own peak only when it exceeds the workload's, which the alone condition measures. `watch`'s CPU is a difference of two measurements, and the workload's CPU and the probes' in-kernel cost charged to it are not separated beyond the ratio to the alone run. The fixtures are reduced by `scripts/make-capture-fixture.py`, so their sizes are not those of raw captures, and the workloads are synthetic: neither stands for a real agent session's volume. The script does not pin CPUs or set the governor, so the results hold for the recorded machine state only.
- The text report's `Capability:` count line calls its events listeners and sockets; it also counts DNS connections and dials, which the forensic view's groups name.
- `watch` prints the loss counters and, for an incomplete capture, `Assess`'s reasons, not its notes (content gaps, the response notes among them); `verify` prints both.
- `analyze` re-verifies each run in process with the current verifier and adapters, so its numbers are those of the build that runs it, which the freeze pins; a full sweep of long sessions is hours of CPU (`--seeds` bounds it). Its leave-one-out baseline holds every pooled control of an agent version in memory.
- `simagent` covers one fixed script; it is not a substitute for a real agent session. Real sessions verified end to end are the Claude Code captures listed in [30_agent_adapters.md](30_agent_adapters.md#objective).
