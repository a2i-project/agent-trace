# Network probe

Checked against commit 04cb380 on 2026-11-01.

## Objective

The network probe (`pkg/probe/net`) records which remote endpoints the agent's process tree contacted and, when content capture is enabled, which HTTP requests it sent over TLS and which responses came back. It has two layers. N0, identity, is `net.bpf.c`: syscall hooks that see connects, listeners, every send, datagrams sent to an explicit address, and the first bytes of each connection, from which userspace extracts the TLS SNI hostname or the DNS question. N1, content, is `tls.bpf.c`: a uprobe and uretprobe pair on `SSL_write` that captures, at the call's return, the plaintext the call wrote before encryption (N-37), and a uprobe and uretprobe pair on `SSL_read` that captures it after decryption (N-29), located by `pkg/tlsoffset` and parsed by `pkg/tlsparse`. These are the content method `tls-symbols`; the agent's profile can choose instead `tls-openssl-ex` (OpenSSL's `SSL_write_ex` and `SSL_read_ex`) and add `tls-rustls-aead` (rustls's AEAD record methods, with the socket of each record followed through the thread's syscalls), N-39 and N-40; on the streams of any method a WebSocket upgrade switches both directions to WebSocket frames (N-41). A request is verified by its hash (`net_request`); a response is attested, never compared with a trajectory (`net_response`, N-11). The common contract, clocks and coverage format are in [10_probes_common.md](10_probes_common.md). The reasons behind the design are in [../decisions/network.md](../decisions/network.md) (N-D1 to N-D5, N-6 to N-41).

In `tls.bpf.c`: its own `tracked_pids` (hash, 4096), `tracked_stat` and `tracked_seeded`, `ssl_events` (ring buffer, 4 MiB, both directions), `ssl_read_args` (LRU hash, 8192, an `SSL_read` call's `ssl` and `buf` from entry to return, keyed by pid and tid), `ssl_write_args` (LRU hash, 8192, an `SSL_write` call's `ssl`, `buf` and length asked, from entry to return, N-36, N-37), `ssl_write_counting` (array of one, set by userspace once the write offset validated, N-36), `ssl_write_stat` (per-CPU array of one `ssl_write_counts`: calls, partial, failed, bytes asked and written, N-36), `ssl_read_counting` (array of one, set once an `SSL_read_ex` offset validated, so a rejected candidate's faulting byte-count pointer is not counted), `ssl_heap` (a header and 32 KiB, twice the copy, as slack for the chunked rustls copy), `faulted_reads`, `drop_count`, `untracked_count`, `read_fault_count`, `read_drop_count`, and for `tls-rustls-aead` `aead_cfg` (array of one: the `Ok` discriminant and whether it is known), `aead_events` (ring buffer, 4 MiB, one page when the method is not configured), `aead_drop_count`, `aead_dec_args` (LRU hash, 8192, a decrypt call's result pointer, object and input record by pid and tid), `pending_enc` (LRU hash, 8192, a thread's latest encrypter until its next send), `last_recv` (LRU hash, 8192, a thread's latest receiving socket) and `aead_bound` (LRU hash, 8192, the socket each encrypter was last bound to).

An `ssl_frame` header carries `ts_ns`, `ssl` (the `SSL*` of the call, or the rustls encrypter or decrypter object), `sock` (the socket inode number of a rustls read frame or bind record, else 0), `tgid`, `tid`, `len` (bytes copied), `total` (bytes the call wrote or read), `dir` (0 write, 1 read, 2 a rustls bind record with no payload) and `method` (0 the SSL side, 1 rustls).

Record types in `net.bpf.c`: `NET_CONNECT` 1, `NET_HELLO` 2, `NET_BIND` 3, `NET_CLOSE` 4, `NET_SOCK_BIND` 5, `NET_SOCK_LISTEN` 6, `NET_UNIX_CONNECT` 7, `NET_SEND` 8, `NET_DGRAM` 9, `NET_HELLO_MORE` 10. `NET_BIND` is never emitted and the observer ignores it, a leftover of the abandoned write-bracket join (N-D1). The header's `sock` field carries the socket inode number on `NET_CONNECT`, `NET_HELLO`, `NET_SEND`, `NET_CLOSE` and `NET_DGRAM` and is 0 on the others; its `sotype` field carries the socket's type (`SOCK_STREAM` 1, `SOCK_DGRAM` 2, `SOCK_RAW` 3) on the same records, 0 when unknown; its `tgid` and `fd` are the caller's, which on a send or close need not be the process that connected. Its `flags` field has one bit, `NET_FLAG_HELLO_MORE` (1), set on a `NET_HELLO` or `NET_HELLO_MORE` record when further sends of the same ClientHello follow (N-31); `conns` keeps `hello_left` and `hello_parts` for that.

`Config` fields: `TrackedPID`, `EventBufSize`, `ExePath` (enables N1 with `tls-symbols`), `Content` (content methods by name with the file each hooks: at most one of `tls-symbols` and `tls-openssl-ex`, the SSL side, and `tls-rustls-aead`; `planContent` refuses an unknown method, a method without a file and two SSL-side methods), `CachePath` (default `$TMPDIR/agent-trace-tlsoffset-cache.json`), `ValidationTimeout` (default 5 s), and the test-only overrides `TrackedPIDsMax` and `ConnsMax`.

## Technologies

Raw tracepoints (`sys_enter` with tail calls, `task_newtask`, `sched_process_exit`, `io_uring_submit_req`), uprobes and uretprobes through cilium/ebpf, two ring buffers, ELF parsing with `debug/elf`, x86_64 instruction pattern matching for the offset scan. See [10_probes_common.md](10_probes_common.md) for code generation and the constant-size rule.

## Workflow

### Scoping

Every program in both objects starts with `is_tracked(tgid)`. There is no host-wide mode: an observer with no tracked pid sees nothing. `TrackPID` writes the pid into the net map and, when N1 is loaded, into the TLS map. The observer remembers whether a pid ever entered the net map (`Config.TrackedPID` at `New`, or a successful `TrackPID`); `CaptureCoverage` reports `Ran=false` when none did, so a capture that watched no process does not read as a complete record of no network activity (N-26, `TestObserver_HostWideRunIsNotRan`). Each object then follows children through its own `handle_fork` (with the `CLONE_THREAD` guard) and removes exiting thread group leaders in `handle_exit`. As in the proc probe (P-34), `handle_fork` inserts with `BPF_NOEXIST`, counts a new entry in `tracked_stat` and raises its peak; `handle_exit` subtracts one when its delete succeeds; `New` and `TrackPID` count the pids they insert in `tracked_seeded` (N-33).

### N0: identity

0. Every syscall hook runs behind one raw tracepoint on `sys_enter` (N-32). `trace_sys_enter` switches on the syscall number (x86_64: `connect`, `bind`, `listen`, `write`, `sendto`, `sendmsg`, `sendmmsg`, `writev`, `pwritev2`, `sendfile`, `splice`, `close`, `dup2`, `dup3`, `io_uring_setup`) and returns at once for any other, checks `tracked_pids`, returns for a 32-bit syscall (`TS_COMPAT` in `thread_info.status`), counts `io_uring_setup` in `iouring_setup_count`, and tail-calls the syscall's program through `sys_enter_progs`; a tail call that fails counts in `drop_count`. Each program reads its arguments from the saved user registers (`rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9`). `New` fills the program array (`sysEnterPrograms`) before it attaches `handle_fork`, `handle_exit` and the dispatcher (`netRawTracepoints`). The steps below name the programs by syscall.
1. `fd_socket` turns a descriptor into a socket (N-24): it reads `task->files->fdt`, checks the fd against `max_fds`, reads `fd[fd]`, and returns the file and `f_inode->i_ino` when `i_mode` says socket. All reads are CO-RE `bpf_probe_read_kernel`, which kernel 5.5 already provides for the `bpf_probe_read_user` calls; no newer kernel is required. Every connect, send and close hook below uses it, so a connection is found from any tracked process that holds it: a child after `fork`, a receiver of `SCM_RIGHTS`, or a duplicate descriptor.
2. `trace_connect` reads the address family with a 2-byte read. For `AF_UNIX` it reads `sun_path` (a pathname with `bpf_probe_read_user_str`, an abstract name with a fixed 108-byte read trimmed by `addrlen`) and emits `NET_UNIX_CONNECT`. For `AF_INET` or `AF_INET6` it reads 16 or 28 bytes and resolves the descriptor; a descriptor that is not a socket (the connect fails) is skipped, and a failed kernel read is counted in `state_lost_count`. `record_connect` stores family, address, port, the socket type (`sock_type`: `type` of the `struct socket` in the file's `private_data`), the connecting tgid and time in `conns` under the socket inode number and emits `NET_CONNECT`. Other families are ignored.
3. `trace_bind` records the address in `binds` and emits `NET_SOCK_BIND`; `AF_UNIX` binds carry the path in the payload. `trace_listen` looks the fd up in `binds` and emits `NET_SOCK_LISTEN` with that address, or with family 0 when the socket was never bound through `bind()`.
4. The send hooks (N-23) look the socket up in `conns`. `trace_write` and `trace_sendto` call `capture_hello` with their buffer. `trace_writev`, `trace_pwritev2` (offset -1 only; any other offset fails on a socket), `trace_sendmsg` and `trace_sendmmsg` (its first message) call `capture_hello_iov`, which concatenates up to eight iovecs (`HELLO_MAX_IOV`, an unrolled loop) to at most 4096 bytes. The first send with readable bytes on a connection emits `NET_HELLO` with up to 4096 bytes (`HELLO_CAP_LEN`) and marks the entry captured. `hello_follow` then decides whether later sends continue a ClientHello (N-31): on a connection that is not a datagram socket and not to port 53, when the send was captured whole and begins a handshake record (`0x16 0x03`) carrying a ClientHello (handshake type 1, or a send of 2 to 8 bytes too short to tell), the bytes still to come are those up to the end of the record when the message fits in it, or up to 16389 bytes in all (`HELLO_FOLLOW_MAX`, one full record) when the message is longer than its record or the header is incomplete. While bytes remain, each later send on the connection is captured by `capture_more` or `capture_more_iov` as `NET_HELLO_MORE` with at most the remaining bytes and at most 4096, for at most eight records (`HELLO_MAX_PARTS`); the record's `NET_FLAG_HELLO_MORE` says whether more follow. A send not captured whole (over 4096 bytes, or past the eighth iovec), or a faulted read (counted in `hello_fault_count`), stops the following. `trace_sendfile` (`sendfile64`) and `trace_splice` (its `fd_out`) read no bytes and call `mark_sent`, which emits a header-only `NET_SEND` once per connection. A hello read that faults (the buffer, an iovec or the `msghdr`) also emits `NET_SEND` and counts in `hello_fault_count`; an iovec copy that yields no bytes emits `NET_SEND` without counting. Either way the entry stays uncaptured so a later send gets another attempt. A zero-length send is ignored. On a datagram socket connected to port 53 every send is captured, not only the first (`dns_per_datagram`): each datagram is one DNS query (N-27).
5. A send that names its destination (N-28): `trace_sendto` with an address, and `trace_sendmsg` and `trace_sendmmsg` (first message) with `msg_name`, call `addressed_send` before the connection path. `read_peer` reads an `AF_INET` address of at least 16 bytes or an `AF_INET6` address of at least 24; other families (netlink, `AF_UNIX`) are left to the connection path. On a `SOCK_DGRAM` or `SOCK_RAW` socket, connected or not, the send goes to that address: it emits `NET_DGRAM` with the destination, the socket type and up to 4096 bytes of the datagram (the buffer, or up to eight iovecs through `copy_iov`), once per socket and destination (the `dgrams` LRU map), except that every datagram to port 53 on a datagram socket is emitted. A faulted read emits the record without bytes and counts in `hello_fault_count`. On a `SOCK_STREAM` socket the kernel ignores the address unless `MSG_FASTOPEN` asks it to connect (TCP Fast Open); a socket not yet in `conns` is then recorded through `record_connect`, and the send's bytes become its hello as in step 4.
6. `trace_close`, and `trace_dup2` and `trace_dup3` for a `newfd` they replace (when `oldfd` is open and differs), call `release_fd`. It deletes the fd from `binds`. For a socket in `conns` it emits `NET_CLOSE` and deletes the entry only when the descriptor holds the last reference to the socket's file (`file_last_ref`: `f_ref` from kernel 6.13, `f_count` before, chosen by `bpf_core_field_exists`). While another descriptor still holds the socket, the entry stays, so a later send by that holder still marks it.

7. `trace_iouring_submit`, a raw tracepoint on `io_uring_submit_req`, runs once per operation a tracked process submits through io_uring, in the submitting task or the ring's SQPOLL thread (same thread group), before the operation runs (N-25). It counts every operation in `iouring_ops_count`, and a network operation in `iouring_net_count`: an opcode that works only on sockets (`SENDMSG`, `RECVMSG`, `ACCEPT`, `CONNECT`, `SEND`, `RECV`, `SHUTDOWN`, `SOCKET`, `SEND_ZC`, `SENDMSG_ZC`, `BIND`, `LISTEN`, `RECV_ZC`), or a data opcode (`READV`, `WRITEV`, `READ_FIXED`, `WRITE_FIXED`, `READ`, `WRITE`, `SPLICE`, `TEE`, `READ_MULTISHOT`, `READV_FIXED`, `WRITEV_FIXED`) whose target may be a socket. The opcode is read from the request (`req->opcode`, CO-RE, guarded by `bpf_core_field_exists`); a request whose opcode cannot be read counts as network. `iouring_target_may_be_socket` reads the low byte of `req->flags` and `req->cqe.fd` (CO-RE, each guarded the same way): a registered file (`IOSQE_FIXED_FILE`), a missing field or a failed read counts, a negative fd does not, and otherwise `fd_socket` decides. The dispatcher counts the rings tracked processes set up (`io_uring_setup`, step 0). Nothing is emitted: the operations are not recorded (O-18). `New` skips `io_uring_submit_req` when the kernel has no such tracepoint; when it is missing and tracefs shows io_uring events (`kernelHasIOURing`, which says yes when tracefs is not mounted), `Coverage` adds every ring to `IOURingNetOps`.

Userspace (`correlate`, a single goroutine fed by `netFeed` and `sslFeed`) keeps a `connection` per socket inode number (the header's `sock`), holding the tgid that connected. Every event of a connection carries that tgid as `PID`, whichever process sent or closed (`TestHandleNetRecord_RecordsFromAnotherProcessFollowTheSocket`).

- `NET_CONNECT` opens the entry and counts `Connections`. An entry already open for the same socket and not yet emitted belongs to a socket connected again (a datagram socket pointed at a new peer); it is emitted first, stamped with its connect time and by the same rules as at a close, and counted in `Coverage.Replaced` (`TestHandleNetRecord_ReplacedConnectionIsEmitted`).
- `NET_SEND` marks the entry as written (`wrote`).
- `NET_HELLO` on a connection to port 53 marks the entry as written and runs `dnsQuery` (N-27): `parseDNSQuery` reads the first question of a standard query (QR 0, opcode QUERY), with the two-byte length prefix on a stream socket (tried after the datagram form when the type is 0), and `dnsName` reads its name within the captured bytes, following compression pointers only backwards past the header, at most 16 of them, with labels of at most 63 bytes and the name at most 255. When it parses, `net_dns` is emitted at once, stamped at the send, with target `<name>/<type>[/<class>]@<resolver ip:port>`: the name in presentation form, with every byte other than a letter, digit, `-` or `_` written `\DDD`, as sent (case kept), `.` for the root; the type as its mnemonic (`A`, `AAAA`, `TXT`, `HTTPS`, ...) or `TYPE<n>`; the class only when not `IN`. It counts `DNS` and `DNSNamed`, and the connection is marked emitted, so its close adds nothing; each further query on a datagram socket is another event. Bytes that do not parse count `DNSUnparsed` and nothing is emitted for them.
- `NET_HELLO` on any other connection marks the entry as written and keeps its bytes. When its `NET_FLAG_HELLO_MORE` is set and the bytes do not yet hold a complete ClientHello (`tlsparse.ClientHelloComplete`), the hello is pending and counted in `Coverage.HellosFollowed`; each `NET_HELLO_MORE` appends its bytes, until a record without the flag arrives, the bytes hold the complete message, or they reach 16389 bytes. `NET_HELLO_MORE` for a connection whose hello is not pending is ignored. `resolveHello` then runs `tlsparse.ParseClientHello`, which joins the payloads of the handshake records at the start of the bytes into the first handshake message (`TestParseClientHello_SNIPastTheFirstKiB`, `TestHandleNetRecord_HelloAcrossSends`). With an SNI name it stores host and ALPN, counts `WithHostname` (and `ContentUnsupported` when ALPN offers `h2`), and emits `net_connect` with the hostname as `Target`, stamped at the first hello record. A hello still pending when its connection is emitted (its close, a new connect, the end of the capture) is parsed from the bytes that arrived; a name found there is the target, stamped at the hello.
- `NET_CLOSE` (the last tracked descriptor closed, or replaced by `dup2` or `dup3`: `TestObserver_ConnectionClosedByDup2IsEmitted`) emits a connection that has not been emitted yet, stamped at the close: `net_connect` with `ip:port` as `Target` if a `NET_HELLO` was received for it, or a `NET_SEND`, or `net_dial` with the same target, ground truth only, if neither was (the losing half of a dual-stack connect, a probe; N-22). A send through any hooked path by any tracked holder counts (N-23: `TestObserver_SendsWithoutWriteAreConnections`, `TestObserver_HelloAcrossIovecsYieldsSNI`, `TestObserver_ForkedChildWriteMarksConnection`, `TestObserver_SCMRightsReceiverWriteMarksConnection`). `Coverage.Dials` counts the latter.
- When both feeders have closed, `flushOpenConnections` emits every connection still open, in connect order and stamped with its connect time, and counts them in `Coverage.OpenAtStop` (N-21).
- `NET_DGRAM` (`handleDatagram`) is treated as a connection to the destination that sent the datagram (N-28), with the sender as `PID`, stamped at the datagram, and counted in `Coverage.Datagrams`. To port 53 on a datagram socket it runs `dnsQuery`, and a datagram that did not parse is emitted as `net_dns` with the resolver's address alone. To any other port it is emitted once per socket and destination (a record the kernel repeats after an LRU eviction is dropped) as `net_connect` by address, since it carried data and has no name; port 0 is not address selection here.
- `emit` turns a connection to port 53 that wrote and yielded no question into `net_dns` with the `ip:port` target, ground truth only like a listener (N-20), and counts it in `Coverage.DNS`. One that wrote nothing falls to the dial rule below (N-27: Go's address selection connects a datagram socket to port 53 of each candidate address and sends nothing). A connection to port 0 (the resolver's source-address selection, N-19) is counted in `Coverage.AddressProbes` and not emitted. Each is marked emitted so its close does not retry.
- `NET_SOCK_BIND` and `NET_SOCK_LISTEN` become `net_bind` and `net_listen` with target `host:port` (IPv6 in brackets), `unix:<path>`, `unix:@<abstract>` or `unbound`. `NET_UNIX_CONNECT` becomes `net_unix_connect`. These types, with `net_dns` and `net_dial`, are ground truth only; `models.ClassifyBindTarget` grades a listener as loopback, wildcard, interface, local socket or unknown.

Every N0 event carries `PID` (the tgid; for a connection, the tgid that connected). None carries `PPID`, and none a level: the verifier places each event by its `PID` in the process forest (V1).

### Stop

`Stop` ends the capture without dropping what the rings hold (N-32, `TestObserver_StopDrainsRingsPromptly`). It detaches the net hooks, then flushes the net ring: `netFeed`, woken with `ErrFlushed`, sets its reader's deadline to now, reads every record already committed and returns at the first empty read (`drainRead`). It flushes the TLS ring, which ends a write validation in progress (the validation then tries no further candidate and reports that the capture stopped), waits for `Start` to return, detaches the `SSL_write` entry and return probes and the TLS fork and exit hooks, and flushes the TLS ring again; `sslFeed` drains it the same way, and ignores a flush that arrives before the write side is detached. `correlate` returns once both feeders have, after `flushResponses` and `flushOpenConnections`. `Stop` then closes `readStop`; `validateRead` accepts its candidate if a status line was read during the drain, and otherwise gives up and detaches the read probes. The kernel counters are snapshotted and the readers and maps closed. Raw tracepoints detach without waiting for a grace period; the uprobes, attached through perf events, wait for one each.

### N1: content

1. `prepareTLS` (in `New`, when a content method is configured) loads `tls.bpf.c`, seeds its `tracked_pids`, attaches its fork and exit tracepoints, and prepares each side; a side that cannot be prepared fails `New`, so a configured method is refused, never dropped. `prepareSSL`, for `tls-symbols`, calls `tlsoffset.Scan` (for `tls-openssl-ex`, `tlsoffset.ScanOpenSSLEx`, with the `_ex` programs and the cache key `<build id>/tls-openssl-ex`). For each of `SSL_write` and `SSL_read` it returns the symbol if present; otherwise it finds the `ssl_lib.cc` string, scans `.text` for RIP-relative `lea` and absolute-immediate references to it, walks back to each referencing function's start (`endbr64` after padding, or the byte after `int3` padding), and ranks functions by reference count, ties by address; both functions sit in that cluster, so without symbols both lists are the cluster. It reads each section in windows of 4 MiB (`scanChunk`), each with the few bytes around it that a pattern reads, and the 4 KiB before each reference, never a whole section, so its memory does not grow with the size of the executable (N-35). A cached offset for the ELF build ID is tried first for each. It then opens the executable and the `ssl_events` reader, attaches the `SSL_write` pair at the first write candidate (`firstLinks`) and the `SSL_read` pair at the first read candidate (`firstReadLinks`); a failed attach is left to validation. A tracked process's `SSL_write` and `SSL_read` between `New` and `Start` are therefore captured and wait in `ssl_events`.
2. `Start` runs `correlate` and then `attachAndValidateTLS`, which blocks. For each write candidate it attaches the `SSL_write` entry and return probes at that file offset (the first candidate's are those `New` attached) and waits up to `ValidationTimeout` for a write frame from a tracked process; read frames met while waiting are held (up to 256, the rest counted in `ReadsUnvalidated`) and do not decide. The candidate is accepted only if the first write frame matches `^[A-Z]{2,10} \S+ HTTP/1\.[01]\r\n` (runtime validation is authoritative, N-D4). The accepted offset is stored in the cache, keeping a cached `SSL_read` offset, and the held read frames and the validating frame are replayed into the correlator in ring order, so a single write is not lost. It then sets `ssl_write_counting`, so the return probe counts calls from the accepted offset only, since at a rejected candidate it counted another function's returns (N-36); a failed update leaves the counts unmeasured and changes nothing else. If no candidate validates, N1 is disabled, `TLSAttachError` explains whether frames arrived at all, and the probe continues identity-only.
3. `startRead`, still in `Start`, removes the validated `SSL_write` offset from the read candidates (with the frames held from read probes there) and starts `validateRead` in a goroutine; `Start` does not wait for it. `validateRead` gives each read candidate a window of `ValidationTimeout` (the first one's probes are those `New` attached) and accepts the candidate in whose window `correlate` saw a read from a tracked process that begins with `^HTTP/1\.[01] [1-5][0-9]{2}[ \r]`. Until then `correlate` discards reads (`ReadsUnvalidated`). An accepted offset is cached with the write offset. When every candidate fails, or `Stop` comes first, `ResponseAttachError` says so and responses are not captured.
4. `probe_ssl_write` reads `ssl`, `buf` and `num` from the first three arguments and, for a `num` above zero as a signed int, stores them in `ssl_write_args` by pid and tid. `probe_ssl_write_return` takes them back at the return. Once `ssl_write_counting` is set it counts the call in `ssl_write_stat`: one call and `num` bytes asked; a return of zero or less as failed (an error, or `SSL_ERROR_WANT_WRITE`, after which the caller must retry with the same bytes); otherwise the bytes returned as written, and a return below `num` as partial (N-36). For a return above zero it copies that many bytes (never more than `num`), at most 16 KiB (`SSL_CAP_LEN`), from `buf` and emits an `ssl_frame` with tgid, tid, time, `ssl`, the bytes copied and the return; a failed call emits nothing, so its bytes enter the stream once, from the retry that wrote them (N-37). `probe_ssl_read_entry` stores `ssl` and `buf` in `ssl_read_args`; `probe_ssl_read_return` takes them back, and when the call returned more than zero copies that many bytes, at most 16 KiB, into a read frame. A faulting read increments `faulted_reads` (write) or `read_fault_count` (read) and emits nothing (N-D5).
5. `correlate` keeps a `tlsConn` per (tgid, `SSL*`) (N-30): the request stream, the response parser, the latest request not yet answered, and the host of the latest attributed request. At most 4096 are kept; past that, the one seen least recently is closed. `handleSSLFrame` appends each write to the connection's `tlsparse.Stream` and calls `ParseHTTP1` until it needs more bytes. A malformed request discards that connection's buffer and counts `FramesUnattributed`. A request line is malformed unless it is a method of two to ten capital letters, a target in an RFC 9112 form (`/...`, `http://` or `https://`, `*` for `OPTIONS`, host and port for `CONNECT`) without control bytes, and `HTTP/1.0` or `HTTP/1.1`, so bytes left ahead of a request never become its method (N-34). A write that begins with the HTTP/2 client connection preface (`PRI * HTTP/2.0`, RFC 9113) on a connection with no buffered bytes counts the connection in `H2Preface` and marks it h2 until a request parses on it (an `SSL*` reused for HTTP/1.1); every write on a connection so marked, the preface's included, counts in `FramesH2`. The frames are handled as before: the preface fails `ParseHTTP1`, and binary frames end in `FramesUnattributed` or stay buffered (N-33). During offset validation, a write frame that begins with the preface counts in `H2PrefaceUnvalidated`: validation accepts HTTP/1.x only, so these are h2 connections seen while content capture was not active. A write larger than the copy (`total` above `len`) leaves a hole the request cannot be read across: the buffer is discarded and counted in `FramesTruncated` and `FramesUnattributed`.
6. `emitNetRequest` takes the host from the `Host` header, or from the newest SNI hostname of the same tgid when the header is absent, and counts `FramesUnattributed` when neither exists. It emits `net_request` with `Target` = `models.CanonicalNetTarget(method, host, port, path, query)` (form `METHOD https://host[:port]path[?query]`, host lowercased, port omitted when 443) and `RequestHash` = SHA-256 of the body when there is one. The plaintext is not kept (N-D3). The request becomes the connection's latest request, with an empty target when it could not be attributed.
7. `handleSSLRead` feeds each read to the connection's `tlsparse.ResponseParser`, with the bytes the read returned beyond the copy. The parser reads the status line and header block (at most 64 KiB), skips interim `1xx` responses, and frames the body by `Transfer-Encoding: chunked` (chunk lines at most 4 KiB, trailer at most 64 KiB), `Content-Length` (repeated values must agree), no body (`204`, `304`, the answer to a `HEAD`), or the end of the connection. After `101` it stops parsing the connection; it records the response's `Upgrade` and `Sec-WebSocket-Extensions` headers (lowercased, at most 128 bytes; an extensions header longer or not printable reads `?`) and keeps the bytes after the head for `TakeUpgraded`. It hashes the body with the transfer coding removed and the content coding kept, as it streams, and keeps none of it. A `text/event-stream` body is split into events as it streams (WHATWG framing: CRLF, LF or CR line ends, `:` comments, a blank line dispatches an event that had a `data` line); events are counted by their `event` field, at most 16 names of at most 64 printable bytes, the rest under `(other)`, and a line over 1 MiB stops the count (`Overflow`). A gzip or deflate event stream is buffered (at most 8 MiB) and decoded at its end; another coding leaves the stream uncounted. Bytes that do not parse count `ResponsesUnparsed`; the connection's reads are then skipped until one begins with `HTTP/1.`, and a response in progress is emitted as incomplete. Missed bytes inside a body of known length are counted into the body and mark it truncated; anywhere else they lose the framing the same way. A read that begins with `HTTP/1.` while a body runs to the end of the connection ends that body, since the `SSL*` was reused.
8. `emitNetResponse` emits each response as `net_response`, ground truth only, stamped when its status line was read, with `PID` the tgid and the record `models.ResponseAttestation` in `Response`: `Status`, `RequestID` (the `request-id` header, else `x-request-id`, at most 256 printable bytes), `ContentType` (media type, lowercased), `ContentEncoding`, `BodyBytes`, `BodyHash` (`sha256:<hex>`, only when the body ended by its framing with no byte missed), `End`, `Complete`, `Truncated`, `Paired` and `SSE` (`Events`, `Types`, `Overflow`). Its `Target` is that of the connection's latest request, which it answers (`Paired`); with none, the connection's host as `https://host[:port]` (`ResponsesUnpaired`); with no host either it is not emitted (`ResponsesUnattributed`). When both feeders have closed, `flushResponses` emits every response still in progress as incomplete, stamped with its connection's last read.

The anchor locators of N-38 find the hook points of a stripped executable without symbols for the content methods `tls-openssl-ex` and `tls-rustls-aead`. Both read the sections through windows of `scanChunk` (N-35), take function boundaries from the sorted table of `.eh_frame_hdr` (binary-searched in place, never a guess at prologues) and refuse with `ErrNoAnchor` when an anchor is missing. `ScanOpenSSLEx` returns the `SSL_write_ex` and `SSL_read_ex` symbols when present; otherwise it finds the function-name strings `ssl_write_internal`, `ssl_read_internal`, `SSL_write` and `SSL_read` (each followed by a NUL, a merged string tail included), the functions that load them by a RIP-relative `lea`, the direct callers (`call` or `jmp`) of the two internal functions other than the two public functions named by their own strings, and the functions that call or tail-jump to one of those. It ranks them by evidence: an address stored by a relative relocation (a GOT slot or a method table) adds 1000, a direct caller 500, a tail-jump wrapper 300, a calling wrapper 100, less one per 16 bytes of function size up to 99; validation decides (N-D4). `ScanRustlsAEAD` finds the source paths `rustls-<v>/src/crypto/{aws_lc_rs,ring}/{tls13,tls12}.rs` in `.rodata`, the panic locations naming them (a relative relocation to the path's start whose stored length ends it), the functions that load a location (the encrypter and decrypter constructors), the vtables those functions load (`drop_in_place` a function or null, a size below 4 KiB, an alignment of 1 to 16, a function as first method), and classifies each first method from its first 0x50 bytes, never past its end: `cmp qword [rdx], 0` is encrypt, a load of `[rdx+8]` compared within 12 bytes with 16 or 24 is decrypt. It refuses a rustls outside 0.23 (`SupportedRustls`), whose record layouts the probes would read, and reads the `Ok` discriminant of decrypt's result from the literal store after the `ProtocolVersion` word in the TLS 1.3 decrypt methods (`OkTag`, -1 when they disagree or none has one).

`tlsparse.WSStream` parses one direction of a WebSocket connection (RFC 6455) from the bytes after the upgrade. It reads each frame header across any chunking, requires the client's frames masked and the server's not, unmasks as it streams, joins a text or binary frame with its continuations into a `WSMessage` (payload length, frames, SHA-256 of the unmasked payload, first and last frame times) and passes the opcode of each control frame (ping, pong, close; unfragmented, at most 125 bytes, allowed between fragments). Of a text message it keeps only the first 4 KiB until its end, to read the string value of a top-level JSON `type` member (at most 64 printable bytes). A frame with RSV1 set (`ErrWSCompressed`: an extension such as permessage-deflate compresses it), any other protocol error (`ErrWSProtocol`: RSV2 or RSV3, a reserved opcode, a length with the top bit set, a wrong mask, a continuation with no message, a message inside a fragmented one, a long or fragmented control frame) or missed bytes (`ErrWSMissing`) end the stream, and a close frame ends it cleanly; nothing after is parsed. `IsWebSocketUpgrade` recognises a `GET` whose `Upgrade` names `websocket` and whose `Connection` names `upgrade`; `IsWebSocketAccept` a `101` whose `Upgrade` names `websocket`.

`tls-openssl-ex` (N-39) runs the steps above with `SSL_write_ex(SSL *s, const void *buf, size_t num, size_t *written)` and `SSL_read_ex(SSL *s, void *buf, size_t num, size_t *readbytes)`: the entry probes also store the byte-count pointer (the fourth argument), the return probes read the count through it when the call returned 1 and copy that many bytes, at most 16 KiB, into the same frames; a return other than 1 emits nothing. A fault reading the count is counted in `faulted_reads` or `read_fault_count` only once the write offset validated (`ssl_write_counting`) or the read offset did (`ssl_read_counting`, set by `validateRead`), since before that a rejected candidate's fourth argument need not be a pointer. The `SSL_write` counts (N-36) count calls the same way, a return of 1 with its count as written, anything else as failed.

`tls-rustls-aead` (N-39, N-40) needs no offset validation before its frames are read, and runs beside the SSL side. `prepareAEAD` calls `tlsoffset.ScanRustlsAEAD`, writes the `Ok` discriminant to `aead_cfg`, attaches `aead_sys_enter` to `sys_enter`, then `probe_aead_encrypt` at every encrypt method and `probe_aead_decrypt_entry` and `probe_aead_decrypt_return` at every decrypt method (21 probes on Codex 0.166.0), and opens the `aead_events` reader; `aeadFeed` reads it from the start, and `Stop` detaches these links and drains the ring like the others. Both methods take the result by hidden pointer (RDI), `self` (RSI), the message by reference (RDX) and the sequence number (RCX), in the rustls 0.23 layouts the locator checks (N-38). `probe_aead_encrypt` reads the `OutboundPlainMessage` and, for application data (content type tag 3) only, copies its plaintext at the entry: one slice, or the `[start, end)` range of up to 8 chunks of a vectored write, at most 16 KiB (a record holds at most 16 KiB of plaintext); it emits a write frame with `ssl` the encrypter and stores the encrypter in `pending_enc` for its thread. `probe_aead_decrypt_entry` stores the result pointer, the decrypter and the input record's pointer and length; the return reads the result and emits a read frame only for an `Ok` (when the discriminant is known) holding application data whose plaintext slice lies inside the input record (decrypted in place), with `sock` the thread's `last_recv`. `aead_sys_enter` returns after a switch on the syscall number unless the syscall is `read`, `readv`, `recvfrom`, `recvmsg` or `recvmmsg` (a receive) or `write`, `writev`, `sendto`, `sendmsg` or `sendmmsg` (a send) by a tracked 64-bit thread on a socket: a receive sets the thread's `last_recv`; a send by a thread with a `pending_enc` binds that encrypter to the socket, clears `pending_enc`, and emits a bind record when `aead_bound` held no binding or another one. `handleAEADRecord` discards write frames until one begins with an HTTP/1.x request line and read frames until one begins with a status line, counting them in `AEADUnvalidated` (the first frame of each direction validates the located methods and their layouts, N-D4). A write frame goes to the connection state of its encrypter; a bind (`aeadBind`) makes that state the socket's too, the first binding of an encrypter standing (a later one to another socket counts `AEADRebound`; a socket whose reads already have a state of their own counts `AEADUnpaired`); a read frame goes to its socket's state, or, with no socket, to its decrypter's (`AEADUnbound`). From there the frames run through `handleSSLFrame` and `feedRead` as the SSL side's do.

WebSocket (N-41), on the streams of any method: when a parsed request is a WebSocket upgrade (`tlsparse.IsWebSocketUpgrade`), the connection's request stream switches to client frames (`WebSockets`), its target becoming `WS https://host[:port]path[?query]` (the upgrade's, with the method `WS`), and the bytes after the request are its first frames. When a response accepts a WebSocket (`IsWebSocketAccept`, `WSAccepted`, after the `101` was emitted as before), the read side switches to server frames with the bytes after the head; with no upgrade request seen, the target names the connection's host alone (`WS https://host`, unpaired). An accept that negotiates any extension (`Sec-WebSocket-Extensions`, in practice permessage-deflate) refuses both directions (`WSRefused`): nothing more of the connection is parsed. Each client message is emitted as `net_request` with the WebSocket target and `RequestHash` the SHA-256 of its unmasked payload, stamped at its first frame (`WSRequests`); it carries the bytes of that message only. The server's messages between two client messages form a turn (`WSServerMessages` counts them), emitted as `net_response` when the next client message or a close frame (from either side) ends it, or when the connection's state closes: `Status` 101, `BodyBytes` the payload bytes of its data frames, `BodyHash` the SHA-256 of those bytes concatenated in order (only for a turn that ended at a message or a close with no server message cut off and no byte missed), `End` its last message, `Paired` when the upgrade request was seen, and `WebSocket` (`Messages`, and `Types` by each text message's top-level JSON `type`, `(text)` or `(binary)` without one, at most 16 names, the rest `(other)`); stamped at its first server byte. A malformed frame or missing bytes end that direction's parsing (`WSUnparsed`, or `WSRefused` for a compressed frame); missing server bytes also emit the turn in progress as truncated.

`Coverage` (in `correlator.go`) holds the diagnostic counts `Connections`, `DNS`, `DNSNamed`, `DNSUnparsed`, `Datagrams`, `AddressProbes`, `OpenAtStop`, `Replaced`, `Dials`, `WithHostname`, `HellosFollowed`, `WithContent` (one per request emitted), `FramesUnattributed`, `FramesTruncated`, `ContentUnsupported` (connections whose ClientHello offered `h2`), `H2Preface`, `H2PrefaceUnvalidated`, `FramesH2`, `IOURingOps`, `IOURingRings`, the ring drops split by ring (`NetRingDrops`, `TLSRingDrops`, summed in `RingbufDrops`), the response counts `Responses`, `ResponsesUnpaired`, `ResponsesUnattributed`, `ResponsesIncomplete`, `ResponsesTruncated`, `ResponsesUnparsed`, `SSEEvents`, `ReadsUnvalidated`, the WebSocket counts `WebSockets`, `WSAccepted`, `WSRequests`, `WSServerMessages`, `WSRefused`, `WSUnparsed`, the rustls counts `AEADUnvalidated`, `AEADUnbound`, `AEADRebound`, `AEADUnpaired`, `AEADRingDrops` (summed into `RingbufDrops`), plus the kernel counters, `ReadFaults` and `ReadDrops` among them. `cmd/watch` prints `Connections`, `WithHostname`, `WithContent`, `FramesUnattributed`, `ContentUnsupported`, `DNS`, `AddressProbes`, `OpenAtStop`, `Replaced` and `Dials`, and on a line of their own the state of the read side, the response counts, `ReadsUnvalidated`, `ReadFaults` and `ReadDrops`, with `ResponseAttachError` as a warning, then, with content capture, a line with each configured method's request and response state and, when any WebSocket or rustls count is above zero, a line with them; only the kernel counters other than the two io_uring diagnostics reach `ProbeCoverage` under their own names; `ReadFaults`, `ReadDrops`, `ResponsesUnparsed`, `ResponsesTruncated` and `ResponsesUnattributed` reach it summed as `ResponseGaps`, and the state of the read side as `Responses`. `CaptureCoverage` also writes the diagnostics (N-33, [10_probes_common.md](10_probes_common.md#diagnostics)), which no verdict reads: the `net_events` ring, with content capture the `ssl_events` ring and with `tls-rustls-aead` the `aead_events` ring (size, high-water mark sampled by `netFeed`, `sslFeed` and the write validation at every record, records read, drops, and on `ssl_events` the read drops apart), the `net` and, with content capture, `tls` tracked sets (capacity, peak, entries at the stop), and every correlator count above under `net_content`, with `ReadFaults`, and, once the `SSL_write` offset validated and counting was switched on, the `SSL_write` counts under `ssl_writes` (`calls`, `partial`, `failed`, `bytes_requested`, `bytes_written`), read live from `ssl_write_stat` and snapshotted by `Stop` before the maps close (N-36), and, with content capture, each configured method's request and response state under `content_methods` (N-39). `cmd/watch` prints them at the end of the net diagnostics line. `TestNetContentCounts_CopiesEveryField` checks that each field of the record is copied from the counter of the same name. As root, `TestObserver_NetRingHighWaterMark` opens 32 connections before the reader starts and requires a mark of at least their connect records, `TestObserver_NetTrackedSetPeak` keeps 24 children alive and requires a peak of 25 and one entry at the stop, matching the map's own entries while they run, and `TestObserver_CountsUntrackedChildren` requires a peak equal to the capacity when the map fills. `TestObserver_SSLWriteCountsPartialWrites` builds a small C client against the system `libssl` (through `dlopen`, so no OpenSSL headers are needed; skipped without a C compiler), which after the validating request head writes a 1 MiB body, the rest of it after 100 bytes with `SSL_MODE_ENABLE_PARTIAL_WRITE` on a non-blocking socket with a 4 KiB send buffer to a server whose 4 KiB receive buffer it does not read for half a second; it requires partial or failed returns in the client's own tally, and `ssl_writes` equal to that tally (the validating call added when its return came after the attach).

On live Claude Code 2.1.306 sessions with content capture (the `long` pilots of 2026-10-27, **Verified** from their capture records), every request carried content, no connection offered or used HTTP/2, every response to the model API was read complete and parsed, and its event stream was counted; the rings stayed far below their sizes with no drops. On a `websearch` capture of the same version (2026-10-27), a `WebSearch` call's `requestId` joined a response's `request-id`, and the call was corroborated (V-45).

## Guarantees and loss accounting

The hostname comes from the ClientHello the client sent, so it needs no plaintext and no cooperation from the agent, and it works for any TLS client. Request and response content is hashed, never stored. A response is attestation: its status, request id, volume, timing and body hash say what came back, and nothing compares it with a trajectory (N-11, N-29).

## Known limits

- All N0 syscall hooks run at `sys_enter`, so socket operations submitted through io_uring or Linux AIO (`io_submit`) are not recorded. A connection without a name whose data went only that way is emitted as `net_dial`: capability evidence, never aligned and never a finding (N-22, O-18). io_uring network operations by tracked processes are counted in `IOURingNetOps`, which makes the run INCONCLUSIVE (N-25); Linux AIO is not counted.
- `IOURingNetOps` also counts a read or write of a registered (fixed) file through io_uring, since the probe does not resolve the ring's file table, so a file-only program that uses registered files makes the run INCONCLUSIVE. A `SPLICE` or `TEE` is classified by its output descriptor only. `IORING_OP_URING_CMD` (socket options among other commands) is not counted.
- On a kernel without the `io_uring_submit_req` tracepoint, every io_uring ring a tracked process sets up counts in `IOURingNetOps`, whatever it was used for.
- A capture written before `IOURingNetOps` existed has no `io_uring_net_ops` field, which reads as zero.
- Only tracked processes are hooked. A connection whose descriptor leaves the tracked tree (passed over `SCM_RIGHTS` to an outside process) and is written only there is a `net_dial`.
- The send hooks fire at syscall entry, so a send that then fails still marks the connection as written.
- `sendfile` and `splice` mark a connection written without reading its bytes, so a ClientHello sent that way yields no name and the connection is reported by address.
- The hello is read from at most eight iovecs (`writev`, `pwritev2`, `sendmsg`, and the first message of `sendmmsg`). When the copied iovecs are all empty, the connection is marked written with no hello, and a later send gets a capture attempt.
- One record holds 4096 bytes: a ClientHello sent in one call is captured whole up to that size. A hello split over sends or TLS records is followed up to 16389 bytes and nine sends (the first and eight more); past either bound, or after a send larger than 4096 bytes or spread over more than eight iovecs, the rest is not captured, and an SNI extension in it is lost: the connection is reported by address (N-31).
- A hello is followed only when its first send begins a TLS handshake record; a client whose first send is a single byte of the record header is not followed. A followed hello is emitted when it is complete, so its connection appears in the event stream at the last part, with the time of the first.
- A ClientHello sent after other bytes on the same connection (a proxy `CONNECT`, STARTTLS) is not the first send and is not read, so such a connection is reported by address.
- A faulted hello read leaves the hello to a later send, which is usually not a ClientHello, so the connection is reported by address. `HelloFaults` counts such reads (`TestObserver_FaultedHelloReadIsConnectionAndCounted`); it counts every faulted read, including one on a connection whose later send still yields the hello, so it bounds the connections affected from above.
- A capture written before `HelloFaults` existed has no `hello_faults` field, which reads as zero.
- A connection or datagram to port 53 is capability evidence, never a finding: an agent can move data over it and the report shows it, with the question of every query that parses, but no trajectory can claim it. Address-selection probes to port 0 are counted and not recorded.
- Only the first question of a query is read, and only standard queries (opcode QUERY) parse; an UPDATE, a NOTIFY or a response sent to port 53 names the resolver alone.
- On a stream socket to port 53 only the first query is read; later queries on the same TCP connection are not recorded.
- `sendmmsg` is read for its first message only: glibc's `getaddrinfo` sends its A and AAAA queries in one call, so only the A query is recorded, and a batch of queries, or of addressed datagrams to other destinations, shows only its first.
- A lookup through `nss-resolve` (varlink to systemd-resolved) or `nscd` leaves the tracked tree over a Unix socket: it is a `net_unix_connect`, and the name is not seen. A lookup through the systemd-resolved stub at 127.0.0.53 names that stub as the resolver, not the upstream server. DNS over TLS or HTTPS is an ordinary connection to port 853 or 443.
- An addressed datagram to a port other than 53 is recorded once per socket and destination: the report shows that data went there, not how much, and a QUIC (HTTP/3) connection is reported by address, its name being in the encrypted Initial packet. A sender that opens a new socket per datagram yields one event per datagram. The userspace set of recorded destinations grows with the number of distinct ones.
- A datagram on a raw or ICMP socket is reported with whatever port field the caller put in the address.
- No byte counts are recorded for connections; only a response read over TLS from the hooked executable has its body length.
- Encrypted Client Hello would hide the SNI name.
- `connect` is recorded at syscall entry, so a failed connect still appears as a connection.
- A connection without SNI is emitted when its last tracked descriptor closes (`close`, `dup2`, `dup3`), or at the end of the capture otherwise, then with its connect time; `Coverage.OpenAtStop` counts every connection emitted at the end, whatever type it became. The end of the capture is where a connection lands when its last reference goes without a hooked call: process exit, `close_range`, an exec under `O_CLOEXEC`, a holder outside the tracked tree, or a message carrying the descriptor that is never received. It is late but not lost (N-21, N-24).
- The last-reference test reads the file's reference count, which a syscall running at that moment in another thread on the same socket also holds. A close during such a call is not seen as the last, and the connection is emitted at the end of the capture.
- `conns` entries for sockets released without a hooked call are never deleted in the kernel and occupy a slot until the probe stops.
- `net_connect` is stamped at the hello or the close, not at the connect, except for a connection emitted at the end of the capture or when a new connect replaced it, which carries its connect time.
- `SSL_write` and `SSL_read` capture is capped at 16 KiB per call. A larger write drops the request it belongs to (`FramesTruncated`); a larger read marks its response truncated, unhashed, or loses the connection's framing. TLS records carry at most 16 KiB, and BoringSSL and OpenSSL return one record per `SSL_read` (**Reported**), so a larger read is not expected.
- With `tls-symbols` only `SSL_read` is hooked on the read side: a client that reads through `SSL_read_ex` or `SSL_peek` alone is not seen; `tls-openssl-ex` hooks `SSL_write_ex` and `SSL_read_ex` instead, and then a client that writes or reads through `SSL_write` or `SSL_read` alone is not seen. Without symbols the read candidate may be a function `SSL_read` calls with the same arguments (BoringSSL's `SSL_peek`), which returns the same bytes.
- Response capture is validated by the first read that begins with a status line after a request; responses before it are discarded (`ReadsUnvalidated`). Without symbols or a cached offset each failing read candidate costs a `ValidationTimeout` window during which responses are discarded. A status-line read that arrives just after a candidate's window can validate the next candidate, which then yields reads that do not parse (counted); the cache is only ever used after a new validation.
- A write frame is stamped at the call's return (N-37). A call whose entry came before the `SSL_write` probes attached, a call still running when they detach at the stop, and a call whose thread exited inside it are not captured, and the last leaves its stash in the LRU map. A response read on another thread of the same `SSL*` before the writing call returned would reach the correlator before its request and pair with the request before it.
- A response pairs with the latest request on its `SSL*`, which holds for HTTP/1.1 without pipelining. Under pipelining a response is paired with the later request and the earlier one's response is unpaired. A connection whose `SSL*` the allocator reuses continues the earlier connection's state; a body delimited by the end of the connection is ended by the next read that begins with `HTTP/1.`, and is never complete.
- The response body hash is of the bytes with the content coding kept, so the same content served gzip and identity hashes differently. A brotli or zstd event stream is hashed but its events are not counted. Events are counted, never kept: the query and results of a server-side web search inside the model API stream are not recorded, so a corroborated server call says the response that issued it was received whole, not what the search returned (V-45).
- Read frames share the TLS ring with write frames: a burst of responses can fill it, and a write frame then lost counts as event loss in `RingbufDrops`.
- At most 4096 connections keep content state; the least recently seen is closed past that, which emits its response in progress as incomplete.
- Content is parsed as HTTP/1.1 only; an h2 connection is counted in `ContentUnsupported` and its frames end in `FramesUnattributed` or stay buffered, producing no `net_request`, and its reads end in `ResponsesUnparsed`.
- `ContentUnsupported` counts the connections whose ClientHello offered `h2`, not those that negotiated it, since the server's choice is not captured: a connection that offered `h2` and spoke HTTP/1.1 is counted there and also yields its requests. `H2Preface` counts negotiated h2 from the plaintext, but only while content capture is active, and only when the preface begins a write; a preface split across writes is missed. An h2-only client never validates an offset (below), so its connections show only in `H2PrefaceUnvalidated`, at most one per candidate tried.
- `WithContent` counts requests, `Connections` connections, and requests are joined to connections by `Host` header, not by socket, so `WithContent` equal to `Connections` minus `ContentUnsupported` is not a test of content coverage: a connection with several requests counts several times, and one with none counts nothing.
- The rings' high-water marks are sampled by the readers, short of the true peak by at most one record, and the tracked sets' peaks can fall short when inserts race on two CPUs (P-34). The TLS ring's mark covers what the write validation and `sslFeed` read; a ring whose validation failed is no longer read, so its mark stops there.
- The `SSL_write` counts (N-36) start when the offset validated: calls before, the validating one included, are not counted. A call still running at the stop, or whose thread exited inside it, is not counted. The counts cover the function hooked, as the content does: writes that do not pass through it are in neither. Without symbols the write candidate is validated by its first frame, not by its return value, so a validated candidate whose return is not `SSL_write`'s would count other returns; the counts are diagnostics, which no verdict reads.
- The aggregate `Content` and `Responses` are active only when every configured method's are: with `tls-openssl-ex` and `tls-rustls-aead` together, a run whose agent made no OpenSSL request before the write validation gave up reads `attach_failed` although its rustls content was captured; `content_methods` in the diagnostics says which.
- The SSL side's write validation needs its first request within `ValidationTimeout` per candidate (N-D4): an agent whose first OpenSSL request comes later (Codex's, if any) is not captured on that side, while the rustls side is unaffected.
- `tls-rustls-aead` reads rustls 0.23's record layouts at fixed offsets; the locator refuses another rustls version, and the first frame of each direction validates them, but a compiler that laid out the same version otherwise would show as frames that never validate (`AEADUnvalidated`), not as wrong content.
- A rustls record's socket comes from its thread: the latest receive before a decrypt, the first send after an encrypt. A record decrypted from bytes another thread received, or an encrypter whose first send left from another thread (a task moved between threads after `WouldBlock`), is bound to the wrong socket or none: a wrong first binding mispairs a turn with the requests of another connection, which `AEADRebound`, `AEADUnpaired` and `AEADUnbound` bound from below only. Records are kept per encrypter or socket, so a TLS 1.3 key update, which replaces the encrypter, starts a new state for the rest of the connection, unbound until its next send.
- A vectored rustls write of more than eight chunks makes a truncated frame, which drops its stream. Only application data is captured on the rustls side; a decrypt result that is an error, or of a decrypt whose `Ok` discriminant the locator could not read and whose stale result passes the range checks, is not told apart beyond those checks.
- A WebSocket request record carries the hash of one client message, not of the conversation: a client that sends only what changed since its previous message (Codex sends incremental requests that name the previous response) has request hashes that attest each increment alone. How a verifier should read such records is not decided here.
- WebSocket turns are delimited by client messages: a server message cut by a client message is split between two turns, and a turn's hash is of the concatenated payloads without message boundaries (`Messages` gives the count). A permessage-deflate connection, or any connection that negotiated an extension, is refused, not decoded: its messages are not recorded at all. An upgrade request switches the client direction at once, so a rejected upgrade's later requests on the same connection end in `WSUnparsed`.
- Offset validation needs an HTTP/1.x request from a tracked process within the timeout, so an h2-only client cannot enable N1.
- Attribution of a request to a host relies on the `Host` header and per-connection (`SSL*`) reassembly, with no join from `SSL*` to the socket, so a `net_response` and its `net_request` are not tied to the `net_connect` of their socket.
- The request reassembly buffer of a connection has no size bound.
- `trace_sendmsg`, `trace_sendmmsg`, `trace_writev` and `trace_pwritev2` assume the x86_64 user layout of `msghdr`, `mmsghdr` and `iovec`, the dispatcher uses x86_64 syscall numbers and argument registers, and `probe_ssl_write`, the `SSL_read` probes, the `_ex` probes and the rustls probes assume the x86_64 calling convention; `aead_sys_enter` assumes x86_64 syscall numbers.
- A 32-bit (ia32) syscall by a tracked process is not seen, as the per-syscall tracepoints did not see it either: a 32-bit program's connections are not recorded.
- The `sys_enter` dispatcher runs for every syscall of every process on the host, and returns after a switch on the number for the syscalls it does not hook; its cost is part of the overhead benchmark's workload ratio.
- A hook program still running on another CPU when `Stop` detaches it can commit a record after the drain has ended; that record is lost uncounted. With content capture, each uprobe and uretprobe (four on the SSL side, 21 for `tls-rustls-aead` on Codex 0.166.0) waits for a grace period when it is detached.
- AF_UNIX pathnames are reported as given, not resolved against the caller's working directory.
- No `PPID` is recorded, so network events rely on proc fork and exec records for placement in the tree.
